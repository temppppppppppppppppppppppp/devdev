## 0. 현황 진단

### 현재 Treatment 상태

| 프로젝트 | genre_ext | regression_ext | 공통 메타 | 비고 |
|----------|-----------|----------------|-----------|------|
| 재벌물 (`재벌물_tr_full.json`) | **있음** (14필드) | **있음** (5필드) | 있음 | 완성형 |
| 무협 (`팽가 망나니_tr_enriched.json`) | **없음** | **없음** | 없음 | content만 풍부 |

**문제**: 재벌물만 구조화, 무협은 산문형. 장르 간 스키마 불일치.

### Treatment → 파이프라인 연동 현황

```
Treatment Block ──(curr_block 3000자 절삭)──→ Stage 2 (Arc)
                                                  ↓
                                          Arc tactical_doc
                                                  ↓
                                 ──(2000자 절삭)──→ Stage 3 (Blueprint)
                                                  ↓
                                          scene_breakdown
                                                  ↓
                                              Stage 4 (Manuscript)
```

- Stage 2: Treatment 블록 1개만 `curr_block`으로 주입 (3000자 절삭)
- Stage 3: Treatment **미참조** (Arc만 참조)
- Stage 4: Treatment **미참조** (Blueprint + Arc만 참조)
- **genre_ext의 풍부한 데이터가 파이프라인에서 사실상 사장됨**

## 1. 목표 스키마 (C안: 하이브리드)

### 블록 4층 구조

```
Layer 1: Core Content     ─ 모든 장르 동일 (4필드)
Layer 2: Common Meta      ─ 모든 장르 동일 (10필드)
Layer 3: genre_ext        ─ 공통 슬롯 7개 + 장르 오버레이 3~5개
Layer 4: incarnation_ext  ─ 설정 의존 (회귀/빙의/환생/없음)
```

### Layer 3: genre_ext (핵심 변경)

#### 3-A. 공통 슬롯 (모든 장르 동일, 7개)

```json
"genre_ext": {
  "type": "wuxia",

  // ── 공통 슬롯 ──
  "conflict_type": "...",         // 이 블록의 갈등 분류
  "resolution": "...",            // 해결 방식 분류
  "advantages": ["...", "..."],   // 주인공이 활용한 이점
  "opponent": {                   // 적대자 상세 (범용)
    "name": "...",
    "type": "...",
    "weakness": "..."
  },
  "pressure": "...",              // 시간/상황 압박 요소
  "danger_level": "...",          // 위험도
  "special_ability": { ... },     // 특수 능력 (있는 경우만)

  // ── 장르 오버레이 ──
  "wuxia": { ... }
}
```

#### 공통 슬롯 enum 정의

**conflict_type** (갈등 유형):

| 장르 | 가능한 값 |
|------|----------|
| 공통 | `negotiation`, `betrayal`, `revelation`, `survival` |
| 투자 | `deal`, `hostile_takeover`, `market_crash`, `insider_play` |
| 무협 | `duel`, `ambush`, `tournament`, `siege`, `treasure_hunt`, `training` |
| 헌터 | `dungeon_clear`, `gate_break`, `raid`, `pvp`, `rank_test` |
| 판타지 | `quest`, `dungeon`, `war`, `divine_trial`, `expedition` |

**danger_level**:
- `safe` / `minor_injury` / `serious_injury` / `life_threatening` / `catastrophic`

**resolution**:
- `brute_force`, `strategy`, `alliance`, `retreat`, `breakthrough`, `negotiation`, `deception`

## 3. 코드 수정 계획

### 3-1. 새 파일 생성

| 파일 | 역할 |
|------|------|
| `modules/core/stage0/treatment_schema.py` | Treatment 블록 스키마 정의 + 검증 |

**내용물**:
- `TreatmentBlock` dataclass (Layer 1~4 전체)
- `GenreOverlay` 장르별 서브클래스 (investment/wuxia/hunter/fantasy)
- `IncarnationExt` 설정별 서브클래스 (regression/possession/reincarnation)
- `validate_block(block, genre, incarnation_type)` → 누락 필드 경고
- `get_genre_prompt_schema(genre)` → LLM에 줄 스키마 문자열 생성

### 3-2. 기존 파일 수정

#### `modules/core/stage0/story_expander.py`

**현재**: `generate_treatment()` 프롬프트가 장르 무관 (content 4필드만 요구)

**수정**:
1. `generate_treatment()` 호출 시 `genre` 파라미터 추가
2. 프롬프트에 `treatment_schema.get_genre_prompt_schema(genre)` 삽입
3. 장르 오버레이 + incarnation_ext 스키마를 프롬프트에 포함
4. `protagonist_config.special_ability` 있으면 블록별 추적 스키마 추가
5. 배치 확장 시에도 동일 스키마 적용

**주의**: 기존 content 4필드 품질은 유지. genre_ext는 추가 레이어.

#### `modules/core/stage0/reverse_expander.py`

**현재**: 역설계 시 Treatment 생성 없음

**수정**:
- 역설계 후 Treatment 생성은 **별도 태스크** (이번 계획 범위 밖)
- 다만 `extract_episode_bibles()`의 HUD 스냅샷이 genre_ext 오버레이와
  호환되도록 `PresetRegistry` 정규화 확인 필요

#### `modules/domain/agents/arc_ensemble.py` (Stage 2)

**현재**: `curr_block[:3000]`으로 Treatment 블록 통째 주입

**수정안 (2가지 중 택 1)**:

**(A) 분리 주입** — genre_ext를 별도 섹션으로:
```python
# 기존
### [블록 DNA]
{curr_block}

# 변경
### [블록 DNA - 서사]
{curr_block_content}    # content + stakes + power_shift (서사 핵심만)

### [블록 DNA - 장르 컨텍스트]
{curr_block_genre_ext}  # genre_ext 전체 (별도 예산)

### [블록 DNA - 설정 컨텍스트]
{curr_block_incarnation_ext}  # incarnation_ext (별도 예산)
```

장점: 절삭 시에도 genre_ext 보존. 각 섹션 독립적 토큰 예산 할당 가능.

**(B) 우선순위 절삭** — 중요도 순 주입:
```python
# content (필수) → genre_ext (중요) → incarnation_ext → common meta 순
# 3000자 예산 내에서 우선순위 컷
```

**추천: (A) 분리 주입**. genre_ext가 잘리면 Arc 품질 저하 직결.

  ```python
  "ability_level": FieldDefinition("ability_level", "int", 1, ...)
  "ability_unlocked_fields": FieldDefinition("ability_unlocked_fields", "list", [], ...)
  ```
- `protagonist_config.special_ability.has_ability == False`이면 이 필드들 비활성

## 8. 셀프크리틱 & 추가 아이디어

> 계획서 1차 작성 후 자체 검토. 빠진 것, 위험한 것, 개선 가능한 것 정리.

### 우려 1: Treatment ↔ Episode 매핑 불일치 — 블록 간 상태 연속성

Treatment 블록과 에피소드는 1:1이 아님:
```
Block 1~3 → Episode 1
Block 4~7 → Episode 2
```

genre_ext에 `cultivation_before/after`를 블록 단위로 추적하면:
- Block 3의 `cultivation_after = "후천 5성"`
- Block 4의 `cultivation_before`도 `"후천 5성"`이어야 함

**문제**: 60개 블록을 배치 10개씩 생성하면 배치 경계에서 상태 불일치 발생 가능.

**대책**:
- 배치 생성 시 이전 배치 마지막 블록의 `resource_after` → 다음 배치 프롬프트에 `"현재 상태: 후천 5성에서 시작"` 주입
- 생성 후 `validate_block_chain()` — 연속 블록 간 before/after 정합성 자동 검증
- **아이디어**: LLM은 `_after`만 생성, `_before`는 이전 블록에서 자동 복사 → 불일치 원천 차단

### 우려 2: Stage 2의 블록 매핑 — 1개 블록으로 5화 커버?

Arc 1개 = 에피소드 5개 ≒ Treatment 블록 10~15개.
현재 `curr_block`은 **1개만** 주입.

```
Arc 5 (ep 21~25) ← Block 21~35 중 하나만 주입?
```

**문제**: Arc가 5화를 커버하는데 블록 1개의 DNA만 보면 나머지 4화 방향성 누락.

**대책**:
- `curr_block` 대신 `curr_block_range` — 해당 Arc에 해당하는 블록 **요약본** 주입
- 예: Block 21~35의 `title + content.context`만 모아서 Arc 범위 전체 조감도 제공
- genre_ext는 첫/끝 블록 것만 (상태 변동 범위 파악용)
- 이것이 분리 주입(A안)과 결합되면:
  ```
  ### [블록 DNA - 서사 조감도]
  Block 21: "파천검법 습득" - 비급을 발견하고...
  Block 22: "혈도문 추격" - 비급 소식에...
  ...
  Block 28: "화경 직전" - 내공이 임계점에...

  ### [블록 DNA - 장르 상태 범위]
  시작: cultivation=후천5성, martial_arts=[기본검법]
  종료: cultivation=화경, martial_arts=[기본검법, 파천검법]
  ```

### 우려 3: content와 genre_ext 간 중복 → 불일치 리스크

Block의 content.solution:
> "전생의 '만인적' 경지에서 얻은 '초감각'으로 상대의 쾌검 파동을 읽어냄"

같은 Block의 genre_ext.wuxia.martial_arts_delta.used:
> `["초감각", "역근경"]`

**동일 정보가 산문/구조체에 이중 기록** → LLM이 둘을 다르게 쓸 위험.

**대책**:
- **content = 서사** (왜, 어떻게, 감정), **genre_ext = 팩트** (수치, 이름, 변동값)
- 프롬프트에 역할 분리 명시: "content에는 이야기를, genre_ext에는 데이터를"
- 검증 시 genre_ext의 키워드가 content에도 등장하는지 크로스체크 (경고 수준)

### 우려 4: Stage 3가 여전히 Treatment을 안 봄

계획서에서 Stage 2 주입은 개선했지만, **Stage 3(Blueprint)는 Arc만 참조**.

```
Treatment → Stage 2 (개선됨) → Arc → Stage 3 (변화 없음) → Blueprint → Stage 4
```

Arc의 `tactical_doc`이 2000자로 절삭되면서 genre_ext 정보가 사라짐.

**대책**:
- Arc 생성 시 `state_changes`에 genre_ext 핵심 정보를 포함
  - 예: `state_changes.cultivation_progress: "후천3성→5성"`
  - 이미 `skill_acquisitions`가 있으니 확장만 하면 됨
- 또는 Arc에 `genre_context` 필드 추가 — Arc가 Treatment genre_ext를 요약 전달하는 중간 매체

### 우려 5: 토큰 경제학 — 블록 비대화

C안 적용 후 블록 예상 크기:
```
content        ~2000자
common meta    ~500자
genre_ext      ~800자
incarnation_ext ~400자
─────────────────────
합계           ~3700자/블록
```

60블록 전체: ~220,000자 ≒ ~55,000토큰.

배치 10개 생성 시 출력 ~37,000자 → **한 번에 못 나올 수 있음**.

**대책**:
- 배치 크기 10 → **5로 축소** (블록이 커졌으므로)
- 또는 **2단계 생성**: 먼저 content + common meta → 이후 genre_ext/incarnation_ext 별도 호출
- 2단계 생성이 품질 + 안정성 둘 다 나을 수 있음 (각 호출의 집중도 향상)

### 우려 6: special_ability 밸런스 검증 심화

"연속 3블록 같은 narrative_role이면 경고"만으로는 부족.

능력 남용 패턴:
- 매 블록 `used_in_block: true` → 긴장감 소멸
- `remaining_uses: 0`인데 다음 블록에서 사용 → 제한 무시
- `ability_growth`가 매 블록 발생 → 성장 인플레이션

**대책** (`validate_ability_balance(blocks)` 함수):
- **사용 비율**: 전체 블록 중 ability 사용 비율 40% 이하 권장
- **쿨다운 검증**: `remaining_uses: 0` 다음 블록은 반드시 `used_in_block: false`
- **성장 간격**: `ability_growth` 이벤트 간 최소 5블록 간격
- **패턴 다양성**: `narrative_role` 4종류가 고르게 분포

### 추가 아이디어 A: Treatment ↔ Arc 양방향 피드백

현재: `Treatment → Arc` (단방향).

Arc 생성 후 Treatment에서 벗어난 경우:
- Treatment Block 25: "주인공이 화경 돌파"
- Arc 5 결과: "화경 실패, 내상"
→ Block 26~ 전제가 무너짐.

**아이디어**: Arc 생성 후 해당 범위 Treatment 블록에 `arc_override` 태그 추가:
```json
{
  "block_id": "Block 25",
  "arc_override": {
    "arc_no": 5,
    "deviation": "화경 돌파 → 화경 실패+내상으로 변경",
    "cascading_update_needed": true
  }
}
```
후속 블록 생성/수정 시 이 태그를 참조.

**복잡도 높음** → Phase 5 이후 검토.

### 추가 아이디어 B: Stage 1(Volume) 장르 연동

계획서에서 Stage 1이 빠져 있음.

Volume 전략도 장르별로 달라야:
- 투자물: "1~3권 한국 장악, 4~6권 미국 진출, 7~10권 글로벌 패권"
- 무협: "1~3권 가문 재건, 4~6권 강호 진출, 7~10권 천하제패"

**Volume 전략 프롬프트에 장르 오버레이 핵심 필드 주입**하면 더 날카로운 권별 전략 가능.
Phase 3 확장 시 검토.

### 추가 아이디어 C: 장르 크로스오버 처리

MEMORY.md 시나리오: "Block 30에서 fantasy 추가".

Treatment 블록 30부터 genre_ext에 오버레이 2개:
```json
"genre_ext": {
  "type": "wuxia",
  "active_overlays": ["wuxia", "fantasy"],
  "wuxia": { ... },
  "fantasy": { ... }    // Block 30~부터 활성
}
```

**문제**: Stage 2 프롬프트가 오버레이 2개를 동시에 이해해야 함.

**대책**:
- `active_overlays` 필드로 현재 활성 장르 명시
- 프롬프트에 "현재 활성 장르: 무협+판타지" 삽입
- PresetRegistry 동적 활성화와 동일 패턴 (이미 검증된 구조)

### 추가 아이디어 D: 2단계 Treatment 생성 (품질 향상)

블록이 커졌으므로 한 번에 모든 레이어를 생성하면 LLM 부담 증가.

**제안: 2패스 생성**
```
Pass 1: content + common meta (서사 품질 집중)
  → LLM이 스토리에만 집중, 구조 데이터 부담 없음
  → 배치 10개 유지 가능

Pass 2: genre_ext + incarnation_ext (데이터 추출)
  → Pass 1 결과를 입력으로, 구조화된 데이터만 생성
  → content를 "읽고" 팩트를 추출하는 형태
  → 정합성 높음 (서사와 데이터가 같은 소스)
```

**장점**:
- Pass 1은 기존 생성 품질 유지 (하위 호환)
- Pass 2는 "정보 추출" 태스크라 LLM 정확도 높음
- 각 패스의 토큰 예산 독립

**단점**:
- API 호출 2배 (비용 + 시간)
- 하지만 Treatment 생성은 프로젝트당 1회이므로 수용 가능
