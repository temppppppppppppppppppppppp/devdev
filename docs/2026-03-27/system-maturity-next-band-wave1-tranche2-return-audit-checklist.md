## 1. Purpose

This checklist is for the return audit of `system-maturity-next-band-wave1` Tranche 2.

It exists so the next incoming Opus report can be classified immediately as one of:
- `Tranche 2 complete`
- `Tranche 2 still partial`
- `Tranche 2 blocked`

## 2. Gating Rule

Fresh canary evidence is the gating item.

Without fresh canary evidence, Tranche 2 must not be marked complete.

Copied or inherited canary artifacts do not count as fresh evidence.

## 3. Required Deliverables

The return packet is incomplete unless all of the following exist.

1. `docs/2026-03-27/system-maturity-next-band-wave1-tranche2-exception-review-outcome.md`
2. current-dated fresh canary evidence for the new target copy
3. updated canonical execution SSOT:
   - `docs/2026-03-27/system-maturity-next-band-wave1-execution-ssot.md`
4. updated temp execution SSOT mirror:
   - `docs/temp/system-maturity-next-band-wave1-execution-ssot.md`
5. refreshed `docs/temp/queue-state.json`

## 4. Fresh Canary Acceptance Checks

All of the following must pass for fresh canary evidence to count.

### A. New Target Truth

- target copy exists:
  - `projects/canary_0327_stage3_cadence`
- prep artifact exists and belongs to the target:
  - `stage3_canary_prep.json`

### B. Fresh Runtime Truth

- the run was actually executed against the target copy
- a new runtime log or equivalent run transcript exists
- timestamps align with the claimed fresh run window

### C. DB Truth

At minimum, post-run DB truth must no longer remain at the pre-run empty state.

Required checks:
- `stage=3 attempt rows > 0`
- `blueprints rows > 0`

If either remains `0`, fresh canary proof is not established.

### D. Artifact Truth

- new canary summary or proof artifact was generated by the fresh run itself
- copied or source-inherited `stage3_canary_summary.json` is explicitly rejected as non-authoritative

### E. Authority Truth

The report must clearly distinguish:
- verified fresh evidence
- copied/stale artifacts
- partial execution leftovers

## 5. Exception Outcome Checks

The exception review outcome document must say one of:
- bounded exception required and recorded
- no exception required

It must not be omitted or implied only from console text.

## 6. SSOT Update Checks

The execution SSOT update is acceptable only if it:
- reflects the real Tranche 2 state
- does not overclaim fresh canary completion when DB/artifact truth is missing
- records remaining blockers if the canary is still partial

Red flags:
- `Tranche 2 complete` with zero Stage 3 attempts
- `complete` based on copied summary only
- closure-style wording while queue remains active

## 7. Queue Checks

After the Tranche 2 return:
- `docs/temp/queue-state.json` must remain coherent with the actual queue
- `system-maturity-next-band-wave1` may stay `in_progress` if Tranche 3 has not started or if Tranche 2 remains partial
- `roadmap.status` must not be force-closed just because one sub-step finished

## 8. Decision Rules

### Mark `Tranche 2 complete` only if:

- exception outcome doc exists
- fresh canary evidence passes all acceptance checks
- canonical SSOT and temp mirror are updated coherently
- queue-state is refreshed
- validator passes

### Mark `Tranche 2 still partial` if:

- scorecard/sweep are done
- exception outcome may or may not be done
- but fresh canary evidence is incomplete, stale, copied, or inconclusive

### Mark `Tranche 2 blocked` if:

- a concrete blocker prevented fresh canary completion
- the blocker is explicitly documented
- no false completion claim is made

## 9. Immediate Audit Questions

When the result comes back, answer these first:

1. Was the canary actually run on `projects/canary_0327_stage3_cadence`?
2. Did DB truth move off `stage=3 attempts = 0` and `blueprints = 0`?
3. Is the claimed canary summary truly fresh, not copied?
4. Does the exception review outcome doc exist?
5. Did `python scripts/ops_validator.py --strict` pass after the update?

If any of `1-3` fail, Tranche 2 is not complete.
