# 글도비 규모 설명 컨텍스트

Date: 2026-04-27
Purpose: 내부 보고와 설명 과정에서 글도비가 단순 자동화 스크립트로 오해되지 않도록, 프로젝트의 규모와 성격을 설명하기 위한 문맥 정리.

## 핵심 판단

글도비는 챗봇 자동화가 아니라 웹소설 제작용 생산 엔진에 가깝다.

기획안과 리서치에서 출발해 Phase 0, TR, BI, work_guard, style_reference 같은 재료를 표준화하고, 이를 S2, S3, S4 파이프라인에 태워 원고까지 생산한다. 과정상에서는 여러 후보를 만들고, 비교하고, Director 판단을 거쳐 PASS, PWF, PATCH, 회차 재생성, 앙상블 재생성으로 이어지는 보정 구조를 가진다.

즉, 결과물 하나를 뽑는 도구가 아니라 재료 생산, 구조화, 원고 생산, 검증, 재시도, 국소 수정까지 포함하는 제작 시스템이다.

## 현재 공식 단계

글도비의 현재 단계는 `Production Pilot`으로 정리하는 것이 가장 적절하다.

한국어로는 `상업 적용 전 제한 생산 파일럿`이라고 설명할 수 있다. 이는 아이디어, PoC, Prototype 단계가 아니라 실제 산출물 생산이 가능한 단계라는 뜻이다. 다만 정식 상업 운영이나 전사 확장 단계는 아니며, 3아크런, 장기기억 proof, 장르별 supervised run 확대를 통해 pass율, 재시도율, 장르별 안정성, 상업성 편차를 검증해야 하는 구간이다.

단계 표현은 다음처럼 고정한다.

| 단계 | 글도비 상태 |
| --- | --- |
| Idea / Concept | 완료 |
| Research / Feasibility | 완료 |
| PoC | 완료 |
| Prototype | 완료 |
| MVP | 충족권 |
| Production Pilot | 현재 |

| Production / GA | 이후 |

보고용 문장은 다음이 적절하다.

> 글도비는 PoC나 Prototype이 아니라 Production Pilot 단계입니다. 즉, 실제 심사 원고 생산은 가능하지만, 정식 상업 운영 전 검증과 고도화가 남아 있는 상태입니다.

## 운영 방식에 대한 오해 방지

글도비는 사람이 중간에 원고를 직접 고쳐 넣는 편집기가 아니라, DB와 컨텍스트 누적, JSON/dict 기반 handoff를 통해 단계별 산출물을 넘기는 생산 파이프라인이다.

기본 흐름은 `추상화 -> 구체화`의 일방향 구조다. 기획안, Phase 0, TR, BI, work_guard 같은 추상 재료를 먼저 만들고, 이를 바탕으로 S2, S3, S4를 거쳐 점점 더 구체적인 원고로 내려간다. 이 구조에서 사람이 중간에 전개를 직접 바꾸거나, 외부에서 직접 만든 15화를 그대로 넣어 시스템 내부 재료로 되돌리는 `구체화 -> 추상화` 방식은 기본 설계 대상이 아니다.

사람의 개입 지점은 중간 원고를 손으로 갈아끼우는 방식이 아니라, supervised run에서 결과를 검토하고, 실패 원인을 분류하고, 다음 run의 지시와 재료를 보강하는 방식에 가깝다. 외부 원고를 다시 시스템에 태우는 역방향 import나 편집기형 워크플로는 별도 기능이며, 현재 파일럿의 기본 범위로 보는 것은 부정확하다.

## 규모 기준

이번 산정은 `test_mode`, `lite_mode`, BI/TR 산출물을 제외한 기준이다.

| 기준 | 규모 | OpenTTD 대비 |
| --- | ---: | ---: |
| 실행 코드 + 데스크톱 | 약 40.8만 줄 | 약 1.3배 |
| 테스트/검증 포함 | 약 57.8만 줄 | 약 1.8배 |
| config/계약/프롬프트/운영 문서 포함 | 약 84.7만 줄 | 약 2.6배 |

OpenTTD는 OpenHub의 공개 코드 규모 기준으로 약 32.3만 code lines급으로 볼 수 있다. 따라서 "OpenTTD보다 큰 규모"라는 표현은 공개 프로젝트 기준의 정량 비교로 사용할 수 있다.

단, 라인 수는 언어, 카운팅 기준, 포함 범위에 따라 달라진다. 이 숫자는 절대 가치 평가가 아니라, "장난감 스크립트가 아니라 중형급 시스템"이라는 규모감을 설명하기 위한 기준으로 쓰는 것이 맞다.

## 예산과 검증 속도

글도비의 개발 속도와 검증 범위는 투입 예산 및 운영 리소스에 비례한다.

현재 병목은 아이디어 부재나 기본 구조 부재가 아니다. 비용 제약이 없다면 여러 장르와 여러 작품에 대해 supervised run을 병렬로 확대할 수 있고, 이 경우 pass율, 재시도율, 장르별 실패 유형, 상업성 편차를 더 빠르게 수집할 수 있다. 표본이 늘어날수록 실패 유형 분류와 개선 우선순위가 빨라지고, 고도화 속도도 올라간다.

따라서 예산 논의의 핵심은 "사람값"이 아니라 "사업 판단 가능한 검증 표본을 얼마나 빨리 확보할 것인가"다. 월 200만 원 파일럿은 가능성 검증과 생산성 검증의 성격이 강했고, 상업 적용 단계로 가려면 장르별 supervised run 확대, 3아크 연속 실행, 장기기억 proof, 연출 레이어 고도화를 포함한 별도 운영 예산이 필요하다.

보고용으로는 다음 표현이 안전하다.

> 비용이 허용되면 장르별 supervised run을 병렬 확대해 고도화 속도를 높일 수 있고, 현재의 주요 제약은 기술 가능성보다 검증 표본과 운영 예산이다.

## 게임 비유

의사결정자가 게임 문법에 익숙하다면 체감 비유는 RimWorld가 가장 적합하다.

RimWorld는 단순 콘텐츠 묶음이 아니라 상태 관리, 규칙, 예외 처리, 시뮬레이션, 생성형 서사를 다루는 시스템형 게임으로 인식된다. 글도비도 단일 결과물을 만드는 스크립트보다, 재료와 상태를 관리하면서 원고 생산을 반복 가능하게 만드는 제작 엔진에 가깝다.

Stardew Valley 비유도 "중형 인디 상용 프로젝트" 규모감을 전달하기에는 가능하다. 다만 Stardew Valley는 수작업 콘텐츠와 1인 개발 신화의 이미지가 강해, 글도비의 엔진성과 운영 복잡도를 설명하기에는 RimWorld 쪽이 더 적합하다.

RimWorld와 Stardew Valley는 소스가 공개된 비교 기준이 아니므로, "몇 배 크다" 같은 정량 비교로 쓰면 안 된다. 두 게임은 체감 비유로만 쓰고, 숫자 비교는 OpenTTD 같은 공개 코드 기준으로 잡는 것이 안전하다.

## 말해도 되는 문장

- 글도비는 챗봇 자동화가 아니라 웹소설용 제작 엔진에 가깝다.
- 체감상으로는 RimWorld 같은 중형 인디 상용 프로젝트 규모감이고, 공개 코드 규모 기준으로는 OpenTTD보다 큰 수준이다.
- 200만 원 월 파일럿으로 단순 실험을 한 것이 아니라, 재료 생산부터 원고 생산까지 이어지는 중형급 파이프라인을 구축했다.
- 4월 말 기준 연속성 및 생산성 이슈는 거의 닫혔고, 다음 단계는 연출 레이어와 상업성 고도화다.
- 개발 속도와 검증 범위는 예산 및 운영 리소스에 비례한다. 비용이 허용되면 여러 장르의 supervised run을 병렬로 확대해 고도화 속도를 높일 수 있다.
- 글도비는 중간 원고를 사람이 직접 갈아끼우는 편집기가 아니라, 추상 재료를 구체 원고로 내려보내는 handoff 기반 생산 파이프라인이다.

## 피해야 할 문장

- RimWorld보다 몇 배 크다.
- Stardew Valley보다 크다.
- 완전 무인 자동 생산이다.
- AI가 알아서 소설을 쓴다.
- OpenTTD와 기능적으로 같은 수준이다.
- 직접 만든 원고를 아무 단계에서나 넣으면 글도비가 알아서 이어받는다.
- 사람이 중간에 전개를 바꾸면 시스템이 자동으로 상위 재료까지 역반영한다.

## 최종 보고용 문장

글도비는 단순 자동화 스크립트가 아니라 웹소설 제작용 엔진에 가깝다. 규모감은 RimWorld 같은 중형 인디 상용 프로젝트로 설명할 수 있고, 공개 코드 규모 기준으로는 OpenTTD보다 큰 수준의 시스템이다. 월 200만 원 파일럿으로 보기에는 이미 재료 생산, 표준화, 원고 생산, 검증, 재시도 체계를 포함한 중형급 파이프라인까지 도달했다.
