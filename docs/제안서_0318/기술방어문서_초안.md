## 1. 1페이지 요약

이 문서의 질문은 아래 하나로 압축된다.

> **외부 장편 생성 흐름 속에서 글도비는 어떤 구조적 선택을 했고, 그 선택은 왜 기술적으로 합리적인가**

이 질문에 대한 답은 명확하다.

글도비는 `단발 생성기`가 아니라, 장편 서사의 핵심 난제를 별도 공정으로 분해하는 `hierarchy-first production system`을 택했다. 이 선택은 독자적으로 튄 예외 설계가 아니라, 최근 공개 연구와 벤치마크가 반복해서 보여 주는 문제 설정과 정렬된다. 외부 흐름이 장편 생성 문제를 `장기 일관성`, `명시적 계획`, `검증-수정 루프`, `상태 추적`, `평가 분리`의 문제로 옮겨 가는 동안, 글도비는 이를 회사 운영형 파이프라인으로 구현했다.

핵심 선택은 아래 표로 정리된다.

| 문제 축 | 외부 흐름에서 관측되는 선택 | 글도비의 선택 | 왜 이 선택이 합리적인가 |
|---|---|---|---|
| 장기 플롯 유지 | 계층적 아웃라인과 세부 계획을 먼저 세움 | `Stage 0 -> 2 -> 3 -> 4` 계층 파이프라인 | 장기 서사는 처음부터 전량 생성보다 책임 단위 분해가 더 디버그 가능하다 |
| 생성 품질 불안정 | `plan-execute-verify-revise` 또는 self-refine 루프 채택 | Self-Critique, Advisory Chain, Director 재판정, PASS_WITH_FIX | 첫 초안 신뢰보다 반복 보정이 실제 품질 관리에 더 유리하다 |
| 서사 일관성 붕괴 | consistency를 별도 평가 문제로 분리 | Director continuity, contradiction firewall, sidecar 품질 기록 | coherence는 문체 품질과 다른 독립 실패 축이기 때문이다 |
| 컨텍스트 한계 | state tracking, summarization, retrieval를 보조 구조로 사용 | WorldState, FactLedger, episode bible, vec/FTS retrieval | 장기 상태를 프롬프트 내부 암묵 기억에만 맡기지 않기 위해서다 |
| 창작 공정 복잡성 | 역할 분업형 multi-agent 구조 채택 | Analyst, Planner, Builder, Writer, Critic, Director | 창작과 검수의 책임을 분리해야 실패 원인과 수정 지점을 추적할 수 있다 |
| 운영 재현성 | 평가와 생성, 로그와 상태를 분리 | SQLite SSOT, stage_attempts, director_selections, logs | 재현성, 비용 관측, 사후 감사를 위해 명시적 흔적이 필요하다 |

이 문서의 판단은 네 줄로 정리된다.

1. 공개 연구와 벤치마크는 장편 생성 문제를 더 이상 `길게 쓰기`의 문제가 아니라 `계획`, `상태`, `검증`, `평가`의 문제로 다룬다.
2. 글도비는 이 문제 설정에 맞춰 `hierarchy-first`, `explicit state`, `closed-loop verification`, `Director sovereignty`를 택했다.
3. 이 선택은 이론적 주장에 그치지 않고, 로컬 기준선 `00_test_00`과 다수 arc 운용 흔적으로 실제 실행면이 확인되었다.
4. 따라서 글도비는 이상한 방향으로 튄 시스템이라기보다, 외부 장편 생성 흐름이 수렴하는 구조를 운영 가능한 형태로 옮긴 시스템에 가깝다.

이 문서가 주장하지 않는 범위도 분명하다.

- 실프로젝트 상업 검증이 끝났다는 주장
- 250화를 실제로 완주했다는 주장
- 사람 감수 없이 즉시 상업 운영이 가능하다는 주장
- 현재 구조만으로 장기 품질이 자동 보장된다는 주장

## 2. 문제 정의: 장편 생성은 왜 별도 공학 문제인가

장편 서사는 짧은 응답 생성과 다른 종류의 난제를 가진다. 문장 수준의 자연스러움만으로는 충분하지 않고, 수십 화 이상 누적되는 `계획`, `인과`, `시점`, `인물 상태`, `복선`, `회수 타이밍`을 함께 관리해야 한다.

외부 연구가 보여 주는 핵심은 아래와 같다.

| 난제 | 외부 근거 | 공학적 함의 |
|---|---|---|
| 장거리 플롯 coherence | `DOC`는 장거리 coherence를 위해 상세 아웃라인 제어를 앞단으로 이동시킨다 | 장편 생성은 초반 계획 부담을 증가시켜도 계층 분해가 유리하다 |
| consistency bug의 독립성 | `Lost in Stories / ConStory-Bench`는 consistency error를 별도 taxonomy와 checker 문제로 다룬다 | coherence는 부수적 품질 문제가 아니라 독립 실패 축이다 |
| 평가의 어려움 | `WebNovelBench`는 4,000+ 웹소설 기반으로 8개 품질 축을 별도 평가한다 | 장편 창작 평가는 단일 점수보다 다축 rubric이 필요하다 |
| 긴 컨텍스트의 불안정성 | `RecurrentGPT`, `SCORE`는 상태 추적, episode summary, retrieval을 별도 장치로 붙인다 | 장기 상태를 프롬프트 내부 기억에만 맡기기 어렵다 |
| 초안 품질의 불완전성 | `Self-Refine`, `MUSE`는 검증-수정 루프를 전면에 둔다 | one-shot generation보다 iterative refinement가 더 현실적이다 |

즉, 장편 생성은 `좋은 문장을 즉시 뽑는 문제`가 아니라, **긴 시간축 위에서 상태를 보존하면서 반복적으로 수정 가능한 생산 공정을 설계하는 문제**다. 글도비의 구조는 바로 이 문제 설정에 대한 대답으로 읽어야 한다.

## 3. 외부 흐름은 어디로 수렴하고 있는가

### 3.1 계층적 계획과 분해가 앞단으로 이동한다

`DOC: Improving Long Story Coherence With Detailed Outline Control`(ACL 2023)은 장거리 coherence를 높이기 위해 `detailed outliner`와 `detailed controller`를 분리하고, 창작 부담의 상당 부분을 planning stage로 이동시킨다. 논문의 핵심은 단순하다. 장편 서사에서 coherence를 확보하려면 본문 생성 이전에 더 상세한 계층 구조가 필요하다는 것이다.

`Agents' Room`은 장편 fiction 작성을 narrative theory 기반 특화 agent 협업 문제로 모델링한다. 여기서 중요한 것은 특정 에이전트 이름이 아니라, **planning과 writing을 서로 다른 책임면으로 분리한다는 점**이다.

`MUSE`는 장편 오디오비주얼 스토리 문제를 다루지만, 구조적 함의는 분명하다. 이 논문은 긴 시간축의 storytelling을 feed-forward pipeline이 아니라 `closed-loop cognitive orchestration`으로 본다. 매체는 다르지만, 장편 문제를 `미리 계획하고, 실행하고, 검증하고, 다시 수정하는 루프`로 보는 점은 글도비와 같은 방향이다.

이 흐름에서 읽히는 결론은 명확하다.

1. 장편 생성은 거시 구조를 먼저 세우고 하위 단계로 내려가는 편이 안정적이다.
2. planning과 drafting은 하나의 블랙박스보다 분리된 공정이 더 다루기 쉽다.
3. 장기 coherence는 생성 이전의 구조 설계와 생성 이후의 통제 장치가 함께 있어야 유지된다.

### 3.2 검증과 수정은 본문 생성의 바깥 공정으로 분리된다

`Self-Refine`은 LLM이 첫 결과를 내놓은 뒤 같은 모델이 자기 피드백과 자기 수정을 반복하는 구조를 제안한다. 이 논문의 중요한 함의는 `첫 초안은 최종 산출물이 아니라 수정 가능한 intermediate artifact`라는 점이다.

`MUSE`도 같은 방향을 강화한다. 이 논문은 long-horizon story generation의 핵심 문제를 `intent-execution gap`으로 정의하고, 이를 `plan-execute-verify-revise` 루프로 다룬다. 즉, 스토리 생성은 생성 자체보다 생성 결과를 어떻게 제약하고 다시 고치는지가 핵심이 된다.

이 흐름은 장편 생성에서 아래를 뜻한다.

- 검수는 마지막 장식이 아니라 본 공정의 일부다.
- 수정 루프는 실패를 의미하는 것이 아니라 정상 동작 방식이다.
- 따라서 품질 게이트와 재시도 경계가 명시적이어야 한다.

### 3.3 coherence와 평가 문제는 별도 계측 축으로 독립한다

`Lost in Stories / ConStory-Bench`는 장편 스토리의 consistency bug를 5개 error category와 19개 subtype으로 분류하고, evidence-grounded checker로 판단한다. 이 논문은 장편 생성의 취약점이 단지 문체 불량이 아니라, `사실`, `시간`, `인물 속성`, `세계 규칙`의 모순으로 나타난다는 점을 보여 준다.

`WebNovelBench`는 장편 웹소설 평가를 synopsis-to-story generation 과제로 정의하고, 인간 작품 분포 대비 percentile을 포함한 다축 평가를 설계한다. 여기서 중요한 것은 `웹소설`이 이미 독립 평가 대상이라는 점과, 평가가 `한 줄 감상`이 아니라 여러 품질 차원으로 분해된다는 점이다.

즉 외부 흐름은 coherence를 아래처럼 다룬다.

1. 생성 결과를 그냥 읽고 느낌으로 판단하지 않는다.
2. consistency를 taxonomy와 rubric으로 분해한다.
3. 평가를 생성 시스템과 분리된 별도 레이어로 둔다.

### 3.4 memory와 retrieval은 주 구조를 보조하는 인프라로 붙는다

`RecurrentGPT`는 장기 텍스트 생성에서 장기/단기 memory를 분리해 사용하는 구조를 제안한다. `SCORE`는 narrative coherence 향상을 위해 상태 추적, episode summary, retrieval 보강을 결합한다. 두 연구가 공통으로 시사하는 것은 `긴 맥락이 필요하다`는 사실 자체가 아니라, **그 맥락을 별도 구조물로 관리해야 한다는 점**이다.

이 지점에서 중요한 것은 memory가 만능이라는 결론이 아니다. 오히려 외부 흐름은 아래 쪽으로 기운다.

- memory는 장기 상태를 보조하는 장치다.
- retrieval은 필요한 사실을 다시 끌어오는 보조 메커니즘이다.
- 주 아키텍처는 여전히 계획, 생성, 검증, 상태 관리의 분리 위에 서는 편이 낫다.

종합하면, 최근 장편 생성 흐름은 `single-pass direct generation`보다 아래 쪽으로 수렴한다.

1. `hierarchy-first planning`
2. `specialized roles or multi-agent decomposition`
3. `verify-revise loop`
4. `explicit state tracking and retrieval support`
5. `separate evaluation for coherence and quality`

글도비의 구조는 바로 이 다섯 축과 맞물린다.

## 4. 글도비는 무엇을 선택했는가

글도비가 실제로 택한 구조적 선택은 아래 표로 정리할 수 있다.

| 외부 문제 설정 | 글도비의 선택 | 워크스페이스 구현면 | 선택의 성격 |
|---|---|---|---|
| 장편은 거시 계획이 필요하다 | `Stage 0 -> 2 -> 3 -> 4` 계층 파이프라인 | Treatment/Bible -> Arc -> Blueprint -> Manuscript | hierarchy-first |
| writing과 review는 분리되어야 한다 | Analyst, Planner, Builder, Writer, Critic, Director 분업 | role-specific agent chain | specialized roles |
| coherence는 별도 실패 축이다 | Continuity/Advisory/Director gate 분리 | Director continuity, contradiction firewall, quality labels | explicit evaluation |
| 첫 초안은 불완전하다 | PASS / PASS_WITH_FIX / REJECT + retry | Self-Critique 17개, Advisory Chain, fix scope | closed-loop refinement |
| 상태는 외부화되어야 한다 | SQLite SSOT + append/history tables | world_state, fact_ledger, episode_bibles, stage_attempts | explicit state |
| retrieval은 보조 인프라다 | 최근 사건, state, vec/FTS retrieval 결합 | mandatory context, hybrid retrieval, summaries | support memory |
| 운영은 감사 가능해야 한다 | 로그, 선택 이력, 비용 흔적 유지 | llm_calls, director_selections, logs, metrics | observability |
| 최종 품질 결정권이 필요하다 | Director sovereignty | Director pass/fix/reject, audit rules | governance |

이 선택을 한 문장으로 압축하면 아래와 같다.

> **글도비는 장편 서사를 한 번에 잘 쓰게 만드는 시스템이 아니라, 장편 서사를 통제 가능한 단계와 상태로 쪼개어 반복 생산하는 시스템을 택했다.**

이 문장은 단순 비유가 아니라 실제 구현 구조와 대응한다.

```text
Treatment / Bible
  -> Stage 0: 기획 정보 구조화
  -> Stage 2: Arc 설계
  -> Stage 3: Blueprint 생성
  -> Stage 4: 원고 생성 및 심사
```

단계별 책임도 분명하다.

| 단계 | 핵심 책임 | 실패 시 되돌아갈 수 있는 단위 |
|---|---|---|
| Stage 0 | 작품 정체성과 기획 SSOT 확립 | 작품 설정 |
| Stage 2 | arc 목표, 갈등, 진행 방향 설계 | arc |
| Stage 3 | 화별 장면 구조, 회차 목적, 장면 배치 구체화 | episode blueprint |
| Stage 4 | 실제 원고 생성, 검수, 수정, 판정 | manuscript attempt |

즉 글도비의 구조는 `좋은 프롬프트 하나`에 거는 구조가 아니라, **실패가 어디서 났는지 추적하고, 필요한 단계만 다시 돌릴 수 있게 만든 운영 구조**다.

## 5. 왜 이 선택이 합리적인가

### 5.1 hierarchy-first를 택한 이유

장편 서사에서는 거시 계획과 미시 문장 사이의 거리가 길다. 직접 생성 방식은 구현은 간단하지만, 아래 문제가 즉시 발생한다.

1. 실패 원인이 `기획`, `플롯`, `장면 구조`, `문장 실행` 중 어디인지 분리하기 어렵다.
2. 일부 결함을 고치기 위해 전체를 다시 생성해야 할 가능성이 커진다.
3. 장기 플롯과 회차 목적 사이의 연결을 사후에 설명하기 어려워진다.

반대로 hierarchy-first 구조는 아래 이점을 준다.

| 비교 축 | single-pass direct generation | hierarchy-first pipeline |
|---|---|---|
| 실패 원인 분리 | 낮음 | 높음 |
| 부분 재시도 | 어려움 | 단계 단위 가능 |
| 장기 플롯 통제 | 약함 | 상대적으로 강함 |
| 운영 로그 해석 | 불투명 | 단계별 관측 가능 |
| 비용 제어 | 한 번 실패하면 재생성 폭 큼 | 실패 구간만 다시 돌릴 수 있음 |

이 구조가 복잡한 것은 사실이지만, 장편 운영에서 중요한 것은 `겉보기에 단순한 구조`가 아니라 **통제 가능한 복잡성**이다. 글도비는 바로 그 복잡성을 선택했다.

### 5.2 역할 분업과 Director 중심 거버넌스를 둔 이유

외부 연구가 multi-agent 구조를 채택하는 이유는 단순 병렬화가 아니다. planning, drafting, critique는 서로 다른 판단 기준을 필요로 하기 때문이다. 글도비 역시 같은 이유로 역할을 나눴다.

- Analyst/Planner는 구조적 판단을 맡는다.
- Builder는 회차/장면 설계를 구체화한다.
- Writer는 원고 실행을 맡는다.
- Critic/Director는 생성 품질과 coherence를 판정한다.

이때 중요한 것은 분업 자체보다 `최종 권위면`이다. 글도비는 `Director sovereignty`를 두어, 여러 초안과 검수 결과가 충돌해도 최종 판정 권한이 하나의 품질 게이트로 수렴되게 만들었다. 이는 장편 운영에서 필수적이다. 권위면이 없으면 `좋은 문장`, `좋은 회차`, `좋은 작품`의 판단 기준이 서로 다른 단계에서 분산되기 때문이다.

즉, Director 구조는 취향이 아니라 **품질 기준의 일관성을 유지하기 위한 운영 장치**다.

### 5.3 상태를 프롬프트 안이 아니라 시스템 바깥에 둔 이유

장편 운영에서 가장 위험한 것은 모델이 `기억하고 있을 것`이라고 가정하는 순간이다. 상태를 프롬프트 내부 암묵 기억에만 맡기면 아래 문제가 발생한다.

1. 어떤 사실이 왜 사라졌는지 추적하기 어렵다.
2. 요약이 언제 왜곡되었는지 관찰하기 어렵다.
3. retrieval miss와 모델 해석 실패를 구분하기 어렵다.
4. 장기 플롯 누락이 발생해도 사후 감사가 어렵다.

그래서 글도비는 WorldState, FactLedger, episode bible, stage attempt log를 별도 SSOT로 둔다. 이는 `memory를 안 쓴다`는 뜻이 아니라, **memory를 관측 가능한 구조 위에 얹는다**는 뜻이다.

이 선택은 `RecurrentGPT`, `SCORE`가 시사하는 바와도 맞는다. 장기 생성에서는 상태가 별도 구조물이어야 하며, retrieval은 그 구조물을 읽어 오는 방식으로 붙는 편이 안정적이다.

### 5.4 검증-수정 루프를 본 공정으로 둔 이유

글쓰기에서 첫 초안은 본질적으로 불완전하다. LLM 기반 장편 생성에서는 이 사실이 더 강하게 드러난다. 문체, 리듬, 장면 전환, continuity, 수치 정합, POV, 복선 회수는 서로 다른 오류 양상을 가진다.

따라서 글도비는 아래를 택했다.

1. Self-Critique 17개 체크
2. Advisory Chain 분리
3. PASS / PASS_WITH_FIX / REJECT
4. fix scope별 수정 경로
5. Director 재판정

이는 `Self-Refine`과 구조적으로 같은 방향이다. 핵심은 `수정을 한다`가 아니라, **수정 경계와 판정 조건이 명시되어 있다**는 점이다. 장편 운영에서 반복은 피할 수 없는 비용이고, 그 반복을 통제 가능한 절차로 바꾸는 것이 시스템의 역할이다.

### 5.5 왜 pure rolling-memory writer를 주 구조로 두지 않았는가

`rolling memory writer`는 짧은 실험이나 보조 맥락 공급에는 유용하다. 그러나 장편 운영의 주 아키텍처로 두기에는 아래 약점이 크다.

1. 요약 드리프트가 조용히 누적된다.
2. retrieval miss가 뒤늦게 발견된다.
3. 장기 arc 보상 구조와 플롯 의도가 흐려진다.
4. 실패 원인이 `요약`, `retrieval`, `prompt`, `generation` 중 어디인지 분리하기 어렵다.
5. 후반부로 갈수록 memory 갱신 비용과 불안정성이 함께 커진다.

그래서 글도비는 `hierarchy가 뼈대`, `memory/retrieval은 보조`라는 방향을 택했다. 이는 memory를 부정하는 것이 아니라, **memory만으로 장편 구조를 책임지지 않게 한 선택**이다.

이 선택은 외부 흐름과도 맞닿아 있다. 최근 연구가 memory를 강조할 때에도, 그 memory는 대개 planning, state tracking, verification과 결합된 구조 안에서 작동한다. 글도비는 이 지점을 운영형 시스템으로 더 강하게 밀어붙인 사례다.

## 6. 선택은 실제로 구현되었는가: 로컬 검증 근거

외부 정렬성만으로는 충분하지 않다. 실제 워크스페이스에서 그 선택이 구현되었는지도 확인되어야 한다. 이 문서가 의존하는 핵심 로컬 근거는 아래 세 층이다.

### 6.1 end-to-end 기준선

`docs/2026-03-11/00-test-00-stage234-ssot-3pass.md` 기준, `projects/00_test_00`는 Stage 2 -> 3 -> 4 기준선을 실제 실행 흔적으로 남겼다.

| 항목 | 확인값 | 의미 |
|---|---:|---|
| 실행 범위 | Arc 1, ep1~4 | 최소 end-to-end 기준선 |
| Stage 2 | PASS, attempt 1 | arc 설계 공정 확인 |
| Stage 3 | ep1~4 PASS | blueprint 공정 확인 |
| Stage 4 | ep1~4 PASS | 원고 생성 및 판정 공정 확인 |
| stage_attempts | 18 | 재시도/운영 흔적 존재 |
| director_selections | 14 | Director 권위면 존재 |
| 총 토큰 | 1,027,179 | 비용 관측 가능 |
| 총 비용 | `$1.9671` | 실제 호출 흔적 존재 |

핵심은 이것이 단순 데모가 아니라는 점이다. DB, 로그, 산출물, 비용 흔적이 함께 남아 있어 `돌아간다고 주장하는 시스템`이 아니라 `돌아간 흔적이 남아 있는 시스템`으로 확인된다.

### 6.2 다수 arc 운용 흔적

`docs/2026-03-16/project-0-260316-3arc-run-stop-survey.md` 기준, `projects/0_260316`는 단일 샘플이 아니라 다수 arc 운용을 의도한 실행 흔적을 남겼다.

| 계층 | 확정 상태 |
|---|---|
| Arc 설계 | 3개 완료 |
| Blueprint | 11화 완료 |
| Manuscript | 6화 완료 |

이 런은 7화 `Chief Writer` 단계 초입에서 멈췄지만, 중요한 점은 frontier가 `Arc -> Blueprint -> Manuscript` 서로 다른 속도로 전진하는 실제 운영 구조가 존재했다는 점이다. 이는 글도비가 적어도 `1 arc 샘플 데모 전용 구조`는 아니라는 의미다.

여기에 2026-03-19 운영자 직접 보고를 합치면 현재 상태는 더 분명하다.

- 다른 PC에서 5아크런이 계속 진행 중
- end-to-end는 이미 끝난 상태
- 현재 초점은 개선 작업과 하드닝

즉 이 시스템은 `돌아갈 수 있을까`를 묻는 단계보다, **이미 돌아가는 구조를 어떻게 더 오래, 더 안정적으로 굴릴 것인가**를 묻는 단계에 가깝다.

## 7. 남아 있는 한계와 비주장

강한 방어 문서일수록 무엇을 주장하지 않는지도 분명해야 한다. 현재 단계에서 남아 있는 한계는 아래와 같다.

| 항목 | 현재 판단 | 의미 |
|---|---|---|
| 250화 완주 | 미실증 | 장기 검증은 진행 가치가 있으나 완주 증명은 아니다 |
| 상업 운영 | 미실증 | internal validation과 production은 다르다 |
| 사람 감수 축소 | 부분적 | 최종 문장 품질과 문화 맥락 조정은 아직 사람 비중이 남아 있다 |
| 장기 memory 안정성 | 하드닝 필요 | summary 압축, active plots 상한, causal lookback, context budget 관리가 남아 있다 |

`docs/2026-03-10/TF-250-long-serial-scale-audit.md` 기준으로, 현재 남아 있는 핵심 하드닝 과제는 아래 네 축이다.

1. 요약 압축 한계
2. active plots / foreshadow 상한
3. causal graph lookback 한계
4. mandatory context 예산 분리

이 항목들은 무시할 수 없지만, 현재 의미를 정확히 읽어야 한다. 이는 `구조가 틀렸다`는 증거라기보다, **장기 연재 수준으로 끌어올리기 위해 남은 엔지니어링 과제**다. 다시 말해, 현재 발견된 것은 `불가능성`보다 `하드닝 backlog`에 가깝다.

## 8. 결론

이 문서의 결론은 아래 다섯 줄로 충분하다.

1. 외부 장편 생성 흐름은 `계획`, `검증`, `상태`, `평가`를 분리하는 방향으로 수렴하고 있다.
2. 글도비는 이에 맞춰 `hierarchy-first pipeline`, `specialized roles`, `explicit state`, `closed-loop verification`, `Director sovereignty`를 택했다.
3. 이 선택은 취향이 아니라 장편 서사의 장기 coherence와 운영 재현성을 확보하기 위한 공학적 선택이다.
4. 로컬 기준선과 다수 arc 운용 흔적은 이 구조가 문서 설계가 아니라 실제 실행면을 가진다는 점을 보여 준다.
5. 따라서 글도비는 외부 흐름에서 벗어난 이상 구조가 아니라, 현재 공개 연구가 수렴하는 정답에 가까운 형태를 운영형 시스템으로 구현한 사례에 가깝다.

가장 직접적인 문장으로 압축하면 아래와 같다.

> 글도비는 장편 생성 문제를 잘못 정의한 시스템이 아니라, 외부가 이미 `장기 coherence`, `계획`, `검증`, `상태`, `평가`의 문제로 재정의한 바로 그 문제를 회사 운영형 생산 시스템으로 구현한 시스템이다.
