## 상태 태그 정의

| 태그 | 의미 |
|------|------|
| `[완료]` | 문서가 주장하는 코드 변경/조사가 현재 코드베이스에서 확인됨 |
| `[미완]` | 문서가 주장하는 작업이 코드에 반영되지 않았거나 일부만 반영됨 |
| `[추적필요]` | 코드 반영 여부가 정적 분석만으로는 불확실, 런타임 검증 필요 |
| `[참고자료]` | 실행 항목이 아닌 조사/분석/참고 문서 (evidence, inventory, report) |
| `[폐기]` | 후속 문서에 의해 대체됨 또는 대상 자체가 제거됨 |

## 문서 유형별 검증 전략

### A. execution-ssot (실행문서) — ~23건
**검증**: 문서 내 각 패치 항목의 파일:라인을 Grep/Read로 직접 확인
- 코드가 문서 주장대로 변경됐으면 → `[완료]`
- 일부만 반영 → `[미완]` + 미반영 항목 메모
- 해당 파일/함수가 사라졌으면 → `[폐기]`

### B. 3pass-audit (감리문서) — ~20건
**검증**: 대상 부모 문서의 상태를 따라감
- 부모가 `[완료]`면 자동 `[완료]`
- 부모가 `[미완]`이면 `[추적필요]` (재감리 가능성)

### C. survey / deep-global-survey (전수조사) — ~15건
**검증**: 주요 발견사항 3~5개를 코드베이스에서 샘플 교차검증
- 발견사항이 여전히 유효 → `[참고자료]`
- 발견사항이 이미 수정됨 → `[완료]` (조사 목적 달성)
- 조사 범위가 불완전 → `[추적필요]`

### D. evidence / raw data (증거파일) — ~50건 (json, txt)
**검증**: 부모 문서 존재 확인 + 부모 상태 따라감
- 부모 없으면 → `[폐기]` 후보
- 일괄 `[참고자료]` 기본값

### E. opus TF deepdive — 22건 (03-15/opus/)
**검증**: consolidated-ssot의 fix 항목을 코드에서 확인
- all-stage-deepdive-fix-candidates-ssot.md가 마스터
- 개별 deepdive는 마스터 참조 `[참고자료]`

### F. TF 평가 (tf-013~020) — 8건
**검증**: 각 TF의 결론(GO/NO-GO/DEFER)과 코드 현실 비교

### G. 기타 (승인요청서, vertex-ai, release audit 등)
**검증**: 건별 내용 확인

## 작업 순서

1. **[현재] 플랜 문서 작성** → 이 문서
2. **조사 실행** — 워크스트림 A~G 순서, 병렬 에이전트 활용
   - execution-ssot 23건 → 코드 교차검증 (핵심)
   - evidence/raw 50건 → 부모 매핑 일괄 처리
   - survey/deepdive → 샘플 검증
3. **재감리 3pass** — 조사 결과에서 오탐 제거
   - pass 1: 초안 태그 부착
   - pass 2: 의심 항목 재검증 (Grep 재확인)
   - pass 3: 최종 확정 + 근거 메모
4. **SSOT 실행문서 제작** — 전체 결과를 1개 마스터 문서로
5. **태그 부착** — 각 문서 맨 앞줄에 `[상태]` 삽입

## 제약

- **코드 수정 금지** — 읽기/검색만
- **pytest 금지** — 정적 분석(Grep, Glob, Read)만
- **3pass 감리 후에만 태그 확정** — 초안 태그로 섣불리 확정하지 않음
