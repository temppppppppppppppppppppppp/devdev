## 1. 1페이지 요약

### 먼저 보는 전제

`2026년 최소 생산 목표 작품 = 27개`다. 이 승인서는 `월 3작품 x 9개월 = 총 27작품`을 기준 단위로 비용, 매출 분위, 회수 가능성을 읽는 `27작품 포트폴리오 승인서`다. 개별 작품 1개의 손익 추정서가 아니다.

### 1. 무엇을 승인해 달라는가

LLM 기반 IP 개발 시스템 「글도비」를 `개인·사비 개발 체계`에서 `회사 운영·회사 개발 체계`로 전환하기 위한 `운영 전환 1단계 승인`을 요청한다. 요청 범위는 `2026-04~12 기본 예산 약 2,200~2,900만원 + a 상한`, `Vertex AI 운영 계정·예산 한도·Batch API 활용 승인`, `월 3작품 기준 MVP Validation 운영`, `19금 성인 HL 요구 프로젝트 발생 시 선택적 Grok +a 예외 분기`, `결과물 권리 구조와 운영 책임 체계 확정`이다. 이 시스템은 소설을 대신 쓰는 AI가 아니라, **IP를 대량으로 테스트하는 생산 인프라**다.

| 항목 | 월 비용 | 검토 기간 합계 / 기준 단가 | 비고 |
|------|--------:|------------:|------|
| 운영용 개발/감리 툴 `(Codex + Claude Code)` | 약 52만원 `($400 수준)` | 약 520만원 | 전처리·유지·감리·교차검증 |
| Vertex AI API | 약 132~210만원 | 약 1,190~1,890만원 | 기본 생산비 |
| 개발비/서버비/기타 | 약 50만원 | 약 500만원 | 인프라·예비 |
| Grok API(선택) | +a | +a | 19금 HL 예외 |
| **합계** | **약 234~312만원 + a** | **약 2,200~2,900만원 + a** | 2026-04~12 |

### 2. 왜 천만 단위 예산인가

이 승인 범위는 작품 1개가 아니라 `27작품 포트폴리오` 운영 전환이다. 자사 내부 `60개월 매출 추적 자료` 기준 `27작품 포트폴리오`의 `출시 후 12개월 누적 순매출 보수적 하한선(P25)`은 약 `4,503만원`으로 기본 총원가 `약 2,200~2,900만원`보다 높다. 즉, 이번 예산은 완성품 구매가 아니라 **검증 속도를 늦추지 않기 위한 운영 전환 비용**이다.

### 3. 왜 지금 승인해야 하는가

1. 지금까지는 사실상 `Google API 범위 + 개인 부담 중심`의 `사비개발` 성격이 강했다. 이제 필요한 판단은 기능 추가가 아니라, 이 체계를 `회사 돈`, `회사 권한`, `회사 운영 책임` 아래로 올릴지 여부다.
2. 현재 단계는 `아이디어 탐색`이 아니라, `1 arc 기준선 + 10 arc 연속 통과`를 거친 `MVP Validation 진행 단계`다.
3. 미승인 시 `회사 자산화`, `Vertex AI` 기반 권한 통제·비용 귀속·운영 관측·`Batch API` 검증, 그리고 `4월 말 작품 생산 가능성 closure` 일정이 함께 밀린다.

## 2. 재무적 판단

### 2.1 이 문서가 재무적으로 묻는 질문

이 승인요청서는 `작품 1개가 바로 돈이 되느냐`를 묻는 문서가 아니다. 이번 안건은 `2026-04~12` 동안 `월 3작품`, 총 `27작품`을 운영 가능한 회사 체계로 올릴 것인지 판단하는 문서다. 따라서 재무 판단 단위도 `작품별 예상 대박치`가 아니라 `27작품 포트폴리오가 시장 기준선 대비 회수 가능한 구조인가`로 읽는 것이 맞다.

즉, 재무팀이 봐야 할 질문은 아래 두 가지다.

1. 운영 전환 1단계 기본 총원가가 얼마인가.
2. 그 총원가가 내부 시장 자료 기준에서 완전히 분리된 무리한 숫자인가.

### 2.2 통계 자료는 어디서 나왔는가

통계의 원자료는 `work_sales_monthly_60m.csv`다. 이 데이터는 `2021-02`부터 `2026-01`까지 `정확히 60개월`의 월별 순매출 추적 원자료다. 여기서 승인 판단용 모집단은 아래 규칙으로 만들었다.

1. 출판사가 `포텐`, `올나이트노벨`, `프로무림`인 행만 남겨 남성향 모집단으로 사용했다.
2. 작품 단위 중복 왜곡을 줄이기 위해 `작품 + 작가` 기준으로 묶었다.
3. `첫 관측월 = 첫 판매월`로 간주한 보수적 전체 모집단을 메인 기준선으로 사용했다.
4. `12개월 관측 완료 작품 1,699개`를 모집단으로 두고 `27작품 포트폴리오`를 `20,000회` 무작위 샘플링해 분포를 추정했다.

실무상 재무 방어에 필요한 관련 파일명은 아래 네 개다.

- `work_sales_monthly_60m.csv`
- `work_sales_monthly_by_work_60m_male_only.csv`
- `work_sales_work_profile_male_only.csv`
- `work_sales_roi_portfolio_baseline_male_only.csv`

이 문서는 `추정 매출`을 임의로 만든 것이 아니라, 내부 판매 이력에서 남성향 모집단을 분리해 `포트폴리오 분포`로 읽는 방식이다.

### 2.3 비용 구조는 어떻게 잡았는가

비용은 `고정비`, `운영형 변동비`, `예외 비용`, `실험성 비용`으로 나눠 읽는 것이 맞다.

| 구분 | 기준 | 2026-04~12 합계 | 해석 |
|------|------:|------:|------|
| Codex 구독 | 약 26만원/월 | 약 260만원 | 전처리, 리팩터, 유지 |
| Claude Code Pro Max | 약 26만원/월 | 약 260만원 | 감리, 교차검증 |
| Vertex AI API | 약 132~210만원/월 | 약 1,190~1,890만원 | 기본 생산 경로 |
| 개발비/서버비/기타 | 약 50만원/월 | 약 500만원 | 인프라, 예비, 운영 |
| Grok API | `+a` | `+a` | `19금 성인 HL` 요구 프로젝트 예외 |
| 합계 |  | 약 2,200~2,900만원 + a | 운영 전환 1단계 총원가 |

이 표에서 중요한 점은 세 가지다.

1. `Vertex AI API`는 기본 운영비다.
2. `Grok +a`는 상시 비용이 아니라 예외 분기 비용이다.
3. `관리형 파인튜닝 비용`은 이 승인 범위의 기본 운영비에 포함하지 않는다.

운영 가정은 기존 승인요청서와 동일하게 유지한다.

1. Google API 실측 기준 `1 arc 약 9,000원`
2. `Vertex Batch API` 병행 시 운영 가정 `1 arc 약 6,300원`
3. `작품당 70 arc`, `월 3작품` 기준으로 Vertex 비용을 산정

### 2.4 왜 27작품 포트폴리오 기준으로 읽는가

승인 범위 자체가 `월 3작품 x 9개월 = 총 27작품`이기 때문이다. 그러면 총원가와 직접 비교하는 값도 `27작품 포트폴리오의 출시 후 12개월 누적 순매출 분포`여야 한다.

![27작품 포트폴리오 손익 기준선](approval_roi_threshold_cost_vs_floor.png)

![27작품 전제 차트](approval_roi_bridge_27works.png)

핵심 분포는 아래처럼 읽는다.

| 지표 | 값 | 해석 |
|------|---:|------|
| 남성향 12개월 관측 완료 작품 수 | 1,699작품 | 내부 모집단 |
| 27작품 포트폴리오 P10 | 약 2,335만원 | 매우 보수적 구간 |
| 27작품 포트폴리오 P25 | 약 4,503만원 | 보수적 하한선 |
| 27작품 포트폴리오 P50 | 약 9,085만원 | 중위 기준선 |
| 27작품 포트폴리오 P75 | 약 1억 7,929만원 | 상단 구간 |
| 총원가 2,200만원 초과 확률 | 91.0% | 보수적 전체 모집단 기준 |
| 총원가 2,900만원 초과 확률 | 86.1% | 보수적 전체 모집단 기준 |

여기서 `P25 4,503만원 > 총원가 2,200~2,900만원`이라는 비교가 나온다. 이 비교는 `2026년 안에 현금이 바로 들어온다`는 뜻이 아니다. 의미는 하나다. 이번 승인 범위가 `시장 기준선과 완전히 동떨어진 무리한 운영비냐`를 물을 때, 내부 남성향 순매출 자료로 볼 경우 그 답이 `그 정도는 아니다`라는 뜻이다.

### 2.5 재무팀이 먼저 걸 수 있는 시비와 답변

#### Q1. 왜 개별 작품 손익이 아니라 포트폴리오 기준인가

이번 승인 범위가 작품 1개가 아니라 `월 3작품 x 9개월 = 27작품` 운영 전환이기 때문이다. 비용도 포트폴리오 단위로 발생하므로, 매출 기준선도 포트폴리오 단위로 맞추는 것이 맞다.

#### Q2. 통계가 과대추정된 것 아닌가

보수적 가정을 일부러 택했다.

1. 모집단은 남성향으로만 좁혔다.
2. `12개월 관측 완료 작품`만 썼다.
3. `첫 관측월 = 첫 판매월`로 간주한 보수적 전체 모집단을 메인 기준선으로 썼다.
4. 승인 판단도 `P50`이 아니라 `P25`를 기준선으로 잡았다.

#### Q3. 통계가 과소추정된 것 아닌가

그 가능성도 있다. 하지만 승인 문서는 낙관 추정을 쓰는 자리가 아니라 `최소한의 방어 가능한 기준선`을 쓰는 자리다. 따라서 이 문서는 의도적으로 보수적으로 잡았다.

#### Q4. 고정비와 변동비를 섞어 부풀린 것 아닌가

아니다. `구독형 고정비`, `Vertex 운영형 변동비`, `Grok 예외 비용`, `튜닝 실험비`를 분리해서 읽어야 한다. 특히 `Grok +a`와 `관리형 튜닝 실험비`는 기본 운영비와 섞어 보면 안 된다.

#### Q5. Vertex 튜닝 비용이 뒤에서 폭발하는 것 아닌가

이 지적은 맞는 지적이고, 그래서 분리해서 적는다. 별도 메모 `docs/2026-03-15/vertex-ai-gemini-tuning-cost-risk-note.md` 기준으로, 전체 pseudo 코퍼스를 그대로 쓰는 `Gemini 2.5 Pro supervised tuning`은 `3 epoch 약 685만 원` 추정치가 나온다. 이 수치는 현재 승인 범위의 기본 운영비와 섞으면 안 된다.

현재 활성 튜닝 파일럿은 아래처럼 별도 통제한다.

1. 대상: `특정 현판 작품` 단일 작품 style-control 셋
2. 1 epoch 원화 참고치: 약 `52,035원`
3. 3 epoch 원화 참고치: 약 `156,106원`
4. 해석: `운영 전환 1단계 기본비`가 아니라 `사전 승인형 실험비`

따라서 재무팀 관점 결론은 아래와 같다.

> 기본 승인 범위는 `운영형 API 비용`을 승인받는 안건이고, `Vertex 관리형 튜닝`은 별도 상한과 별도 파일럿 규칙으로 다뤄야 한다.

### 2.6 재무 판단 결론

재무적으로 이 안건은 `당장 얼마 벌까`보다 `27작품 포트폴리오를 운영 가능한 체계로 올릴 때, 기본 총원가가 내부 시장 기준선과 완전히 동떨어진 숫자냐`를 보는 승인 요청이다. 현재 기준으로는 아래처럼 요약할 수 있다.

1. 기본 총원가 `약 2,200~2,900만원 + a`
2. `+a`는 `Grok` 예외 프로젝트에만 붙는 비용
3. 남성향 `60개월`, `1,699작품`, `27작품 20,000회 샘플링` 기준 `P25 약 4,503만원`
4. 해석은 `즉시 현금회수 보장`이 아니라 `운영 전환 1단계 예산이 완전히 무리한 숫자는 아님`

## 3. 기술적 판단

### 3.1 글도비는 정확히 무엇인가

글도비는 `한 번 프롬프트 넣고 소설 한 화를 뽑는 도구`가 아니다. 이 시스템은 `IP 생산 인프라`에 가깝다. 운영 개념상 핵심은 아래 네 가지다.

1. 작품 기획 정보를 구조화한다.
2. arc 단위로 설계한다.
3. 화별 blueprint를 만든다.
4. 원고 생성과 검수를 분리한다.

현재 파이프라인은 아래처럼 정리된다.

```text
Treatment / Bible
  -> Stage 0: 전처리 / 구조화
  -> Stage 2: Arc 설계
  -> Stage 3: Blueprint 생성
  -> Stage 4: Manuscript 생성 및 심사
```

즉, 글도비의 본질은 `AI 작가`가 아니라 `장편 웹소설을 통제 가능한 절차로 생산하기 위한 시스템`이다.

### 3.2 지금 단계는 어디인가

현재 단계는 `Production`이 아니다. 아래처럼 구분해야 한다.

| 단계 | 의미 | 현재 판단 |
|------|------|------|
| POC | 아이디어 수준 구현 | 통과 |
| Technical Validation | 파이프라인 자체가 동작하는지 검증 | 통과 |
| MVP Validation | 실프로젝트 수준의 연속 생산으로 최소 가치 검증 | 현재 단계 |
| Pre-Production | 실운영 직전 비용, 안정성, 품질 최종 검증 | 미도달 |
| Production | 상업 운영 체계 | 미도달 |

현재 단계를 `MVP Validation 진행 중`으로 보는 근거는 아래다.

1. `00_test_00` 기준 `1 arc / 4화`에서 Stage 2 -> 3 -> 4 end-to-end 재현을 확인했다.
2. `2026-03-11 승인 근거 패키지` 기준 `3,800건대 테스트 통과 기록`과 전수조사 묶음이 확보되어 있었다.
3. `10 arc 연속 통과` 전제에서 다수 arc 연속 생산, 품질 게이트 동작, 운영 로그 축적이 확인되었다.

반대로 아직 안 된 것도 명확하다.

1. 실프로젝트 1건 상업 검증
2. `70 arc 이상` 장기 비용곡선 실측
3. `19금 성인 HL` 프로젝트의 `Grok +a` 실측
4. `Production` 단계의 인력, 책임, SLA 수준 운영

### 3.3 왜 `hierarchical pipeline + planning-execution loop`를 택했는가

장편 웹소설 시스템에서 문제는 `한 문단 잘 쓰기`가 아니라 `수백 화 동안 계획, 상태, 시점, 장면 전환, 회수 타이밍을 관리하는 것`이다. 이 문제를 풀려면 `먼저 계획하고`, `그 계획대로 쓰고`, `검수 후 다시 수정하는` 구조가 필요하다.

글도비는 이 요구 때문에 `hierarchical pipeline + planning-execution loop`를 택했다.

1. `Stage 0`에서 입력 기획을 구조화한다.
2. `Stage 2`에서 arc 목표와 진행을 설계한다.
3. `Stage 3`에서 화별 blueprint와 scene breakdown을 만든다.
4. `Stage 4`에서 원고를 생성하고 심사, advisory, validation을 거친다.

이 선택은 취향 문제가 아니라 장편 운영의 공학적 선택이다. `무작정 길게 이어쓰기`로는 아래 문제가 바로 온다.

1. arc 목표가 사라진다.
2. 회차 역할 분리가 흐려진다.
3. 복선과 회수 타이밍이 흔들린다.
4. 디버깅 포인트가 문장 내부에 묻힌다.

### 3.4 왜 `rolling memory writer`를 주 아키텍처로 두지 않았는가

이 문서에서 말하는 `rolling memory writer`는 공식 논문 taxonomy가 아니라 운영상 묶음 이름이다. 뜻은 `직전 본문 + 요약 메모리 + retrieval 조각`을 계속 굴리며 순차 생성하는 구조다.

이 접근은 `짧은 길이`나 `보조 기억` 수준에서는 유용하지만, `250화 이상` 장편의 주 아키텍처로 두기에는 약점이 크다.

1. 요약 손실이 누적된다.
2. retrieval miss가 잠복해도 늦게 드러난다.
3. 거시 계획이 약해진다.
4. 실패 시 원인 추적이 어렵다.
5. 좋은 문장을 쓴다고 해서 좋은 장기 구조가 자동으로 나오지 않는다.

그래서 글도비는 `hierarchy가 뼈대`, `memory/retrieval은 보조`라는 방향을 잡는다. 즉, memory는 필요하지만 뼈대 역할을 맡기지 않는다.

### 3.5 이 방향이 이상한 갈래가 아닌 이유

이건 혼자 이상한 방향으로 간 것이 아니다. 최근 장문 생성 연구도 대체로 아래 방향으로 수렴한다.

1. `outline / planning / chapter-scene decomposition`
2. `memory / summarization / retrieval`
3. `specialized agent` 또는 `revision loop`

글도비는 이 셋 중 첫 번째를 뼈대로 택하고, 두 번째를 보조로 쓰며, 세 번째를 운영적 심사 구조로 부분 수용하는 편이다. 즉, `장편 생성의 주류 문제설정`과 어긋난 구조가 아니라, 실무형으로 재조합한 구조다.

## 4. 승인 조건 및 실행 계획

### 4.1 이번 승인 범위

이번 승인 범위는 아래로 제한한다.

1. `2026-04~12` 운영 전환 1단계 예산 `약 2,200~2,900만원 + a` 상한
2. `Vertex AI` 운영 계정, 예산 한도, `Batch API` 활용 승인
3. `월 3작품` 기준 운영 검증 권한
4. `19금 성인 HL` 요구 프로젝트 발생 시 `Grok +a` 예외 분기 승인
5. 결과물 권리 구조와 운영 책임 체계 확정

### 4.2 승인 조건

조건은 넓게 열지 않고 아래처럼 묶어야 한다.

1. 예산 상한: 기본 운영비는 `2,200~2,900만원 + a` 범위를 넘기지 않는다.
2. 프로바이더 범위: 기본 생산 경로는 `Vertex AI`, 예외 프로젝트만 `Grok +a`.
3. 인간 감수 범위: 단기 운영에서는 인간 감수를 유지한다.
4. 튜닝/실험 경계: `관리형 튜닝`은 기본 운영비와 분리해 별도 승인한다.
5. 비용 관측: `Batch API`, usage, latency, error, 비용 귀속을 운영 지표로 남긴다.

### 4.3 승인 후 점검 항목

승인 후 바로 봐야 할 것은 아래다.

1. 실제 프로젝트 `1건` 운영 로그
2. `70 arc 이상` 장기 비용곡선
3. `Grok +a` 예외 프로젝트 실측
4. 실프로젝트 `1건` 상업 성과 및 ROI 실측
5. 품질 게이트 reject율과 재시도 비용 편차

### 4.4 월별 및 분기별 실행 계획

| 기간 | 목표 | 해석 |
|------|------|------|
| 2026.04 | 운영 전환 1단계 시작 | 계정, 권한, 비용 귀속, 기본 생산 경로 확정 |
| 2026.05~06 | 작품 생산 가능성 closure | 월 3작품 기준 운영 로그 확보 |
| 2026.07~08 | 퀄리티 업 1차 | 품질 게이트, 라우팅, retry 비용 최적화 |
| 2026.09~10 | 퀄리티 업 2차 | 장기 비용곡선, 유통/피드백 반영 |
| 2026.11~12 | 다음 단계 판단 | Pre-Production 진입 여부와 별도 튜닝 파일럿 판단 |

### 4.5 승인 거절 시 실제로 막히는 것

승인을 미루면 아래가 같이 지연된다.

1. 회사 운영 체계 안에서의 권한 통제
2. 비용 귀속과 모니터링 체계 구축
3. `Vertex AI` 기반 운영 최적화 검증
4. 실전 로그 누적 속도
5. `작품 생산 가능성 -> 퀄리티 업` 단계 전환 일정

즉, 승인 거절의 의미는 `리스크 회피`만이 아니다. `회사 자산화 지연`과 `검증 지연`을 같이 선택하는 것이다.

### 5.3 문서의 최종 해석

이 문서는 `AI 소설 도입 제안서`가 아니라, `MVP Validation 단계에 들어선 장편 IP 생산 시스템을 회사 운영 체계로 올릴 것인지` 묻는 첫 승인 요청서다. 첫 페이지는 `임원 판단용`, 이후 페이지는 `재무/개발 공격 방어용`으로 읽으면 된다.

### 5.4 3pass 감리 메모

이 문서는 아래 기준으로 재감리했다.

1. Pass 1 구조 감리: `1페이지 요약 -> 목차 -> 재무 -> 기술 -> 승인 조건 -> 부록` 구조가 결재 문서 목적과 맞는지 점검했다.
2. Pass 2 근거 감리: `1페이지는 기존 승인서 중심`, `2페이지 이후는 방어형 본문 중심`이라는 편집 원칙 아래 `60개월 매출 자료`, `27작품 포트폴리오 기준선`, `튜닝 비용 메모`, `Stage 0/2/3/4 구조`, `250화 구조 검토 문서`와 수치 및 파일명을 다시 대조했다.
3. Pass 3 실행 감리: PDF 렌더 기준 `1페이지 요약 전용`, `2페이지 목차`, `3페이지 재무 시작`이 실제로 유지되는지, 그리고 `운영비와 튜닝비 분리`, `Production 아님`, `인간 감수 유지`, `승인 후 점검 항목`이 실제 의사결정 문서로 충분한지 점검했다.

감리 후 최종 판단은 아래와 같다.

- 이 문서는 `전면 상업 운영 승인서`가 아니라 `운영 전환 1단계 승인서`로 읽혀야 한다.
- 숫자의 핵심은 `27작품 포트폴리오`, `기본 총원가 2,200~2,900만원 + a`, `P25 4,503만원`, `튜닝비 별도`다.
- 기술의 핵심은 `hierarchical pipeline + planning-execution loop`, `MVP Validation`, `rolling-memory 단독 아님`이다.
