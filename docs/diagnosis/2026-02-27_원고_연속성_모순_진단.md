## 2. 원인 분석

### 2-A. LLM(Chief Writer) 측 (주요 원인, 60%)

#### 원인 A: 복잡 수치 계산을 LLM에 전부 위임
- `chief_writer.yaml`에 레버리지 계산 공식 부재
- `state_updates.wealth`는 LLM 자유형식 선언 (Python 검증 없음)
- LLM이 "극적 효과"를 위해 수익률을 부풀리거나 계산식을 잘못 적용

**정확한 계산 (LLM이 틀린 부분)**:
```
진입가 60.15달러 → 매도가 64.20달러
기초자산 상승폭 = (64.20 - 60.15) / 60.15 × 100 = 6.73%
계좌 수익률 = 6.73% × 3배 레버리지 = 20.2%
실제 수익금 = 20억 × 20.2% ≈ 4.04억 → 총 24억
원고 표기: 수익률 40.6%, 수익금 8.15억 → 2배 과장
```

#### 원인 B: 소도구 물리 연속성 미추적
- `_generate_episode_digest()`는 사망/아이템/부상/무공 등 10개 카테고리만 추적
- "수트 재킷이 의자 등받이에 걸려있다"는 소도구 물리 상태 미추적
- LLM이 컨텍스트에서 직접 읽어야 하지만 3화→4화 사이에서 누락

### Step 2: investment_guard.py — validate_leverage_return() 추가 ✅
```python
def validate_leverage_return(entry_price, exit_price, leverage, stated_return_pct, tolerance=3.0):
    """계좌 수익률(%) = 기초자산 변동폭(%) × 레버리지 배수 공식 검증"""
    base_return_pct = (exit_price - entry_price) / entry_price * 100.0
    expected_return_pct = base_return_pct * leverage
    diff = abs(stated_return_pct - expected_return_pct)
    if diff > tolerance:
        return False, f"[V-LEVA] 불일치: 예상 {expected_return_pct:.1f}% vs 표기 {stated_return_pct:.1f}%"
    return True, "정합"
```
