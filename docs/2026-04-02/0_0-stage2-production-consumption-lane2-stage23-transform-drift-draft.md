## Findings

### F-1. The Stage2 → Stage3 bridge is `BlueprintConstraintCompiler.compile()` — it maps, but does not lock

The compiler reads `arc_data` and creates a structured `constraint_block` with 10+ fields:

```
must_focus, stop_line, continuity, inherited_state,
arc_constraint_summary, state_changes_summary, semantic_carryover,
immutable_fact_carryover, fact_lock_packet, capital_continuity_packet
```

This is a genuine structural transform — Stage2's flat/mixed authority gets re-organized into a dict of separated concerns. The compiler also adds new constructs (fact-lock, capital-lock) that Stage2 does not produce.

However, the compiler does **not** create any hard binding between the tactical_doc narrative content and the resulting blueprint. The tactical_doc is extracted as a prose substring via `extract_episode_tactical()` and passed to the LLM as `arc_focus` — a free-text prompt input.

Evidence: `blueprint_constraint_compiler.py:44-136`, `blueprint_ensemble.py:265-288`

### F-2. The actual constraint consumer (`_format_constraints`) applies a 4-band hierarchy that Stage2 does not have

`BlueprintEnsemble._format_constraints()` (L898-1091) organizes the compiled constraints into:

```
IMMUTABLE > HARD CONSTRAINT > EXPECTED CONTINUITY > ADVISORY
```

This is Stage3's most important structural addition. It provides:
- **IMMUTABLE**: fact_lock_packet anchors, capital_continuity_packet fields
- **HARD**: must_focus events, stop_line content, arc_constraint_summary
- **CONTINUITY**: location, time_context, ongoing_conflicts, inherited_state
- **ADVISORY**: state_changes_summary, semantic_carryover

Stage2 does not have this banding. Stage2 has `prohibition_summary` at prompt top and `constraint_block` as a flat string, but not a hierarchical conflict-resolution order.

This is genuine authority preservation that Stage3 adds.

### F-3. Despite banding, the primary content authority path is still LLM reinterpretation of prose

The constraint banding controls *which rules take priority*, but the actual creative content — scene_breakdown, integrated_scenario — is generated by the LLM from:

1. `arc_focus`: a tactical_doc substring (prose, not structured)
2. `constraints_str`: the banded constraints (structural, but advisory-to-hard)
3. `prev_info`: previous blueprint + manuscript text (large bulk payload)
4. `hud_context`: state tracker convenience

The prompt template `BLUEPRINT_GENERATION_PROMPT` (ensemble.yaml L271-450) declares:

```
Context Priority Contract:
1. Constraint Stack outranks arc-mission prose
2. Arc Mission outranks previous-truth archive
3. Previous Truth outranks HUD convenience state
```

But in practice, the LLM generates scene-level creative content that is **not structurally constrained** to match the tactical_doc prose. The EP5 case proves this: the tactical_doc describes a financial PB call; the blueprint generated a physical intrusion scene.

### F-4. Two Stage2 outputs are completely dropped by Stage3

| Stage2 Output | Consumed by Stage3? | Impact |
|---|---|---|
| `beat_sequence` | **No** — compiler and generator do not read it | Episode-level narrative beats are lost |
| `hybrid_composition` | **No** — not referenced anywhere in Stage3 | Intended narrative pattern (primary/secondary) is lost |

These are not trivial outputs. `beat_sequence` describes the intended progression of each episode. `hybrid_composition` describes the intended narrative tone mix. Both are Stage2's explicit structural guidance that Stage3 never sees.

Evidence: Grep for `beat_sequence` in `blueprint_constraint_compiler.py` and `blueprint_ensemble.py` returns zero hits outside of display/logging code. `hybrid_composition` is similarly absent.

### F-5. `state_changes` undergoes lossy compression from structured dict to advisory text

Stage2 produces `state_changes` as a rich structured dict with 15+ sub-fields (timeline, npc_deaths, skill_acquisitions, relationship_changes, major_items, resolved_plots, npc_injuries, npc_movements, entity_destructions, npc_personality_changes, npc_npc_relationships, npc_introductions, time_markers, permanent_injuries, companion_changes, commitments, protagonist_emotion, npc_dialogue_profiles, numerical_facts, financial_events, episode_details).

The compiler's `_summarize_state_changes()` compresses this to a summary. The constraint formatter then places this in the **ADVISORY** band — the lowest priority tier.

This means state changes are advisory, not binding. A blueprint that contradicts a state change (e.g., using a dead NPC) would only trigger an advisory warning, not a hard REJECT. The `_apply_dead_npc_advisory()` method in `unified_blueprint_validator.py` confirms this is indeed advisory-only.

### F-6. The validator has arc-fidelity checks but they are post-generation and Python-advisory

`_collect_tactical_semantic_fidelity_issues()` and `_collect_fidelity_prevalidation_issues()` in `unified_blueprint_validator.py` check whether the blueprint content matches the arc source. But these are:

1. Post-generation (checking after the LLM has already produced the blueprint)
2. Python-only advisory (no REJECT authority — advisory only, forwarded to Director)
3. Pattern-based (keyword matching, not semantic comparison)

The final verdict authority belongs to the Director, which receives the advisory warnings and makes an LLM-based judgment. This means the arc-fidelity gate is **LLM-decided**, not structurally enforced.

## Top 5 Contract-Drift Seams

### Seam 1 (CRITICAL): tactical_doc → LLM free reinterpretation

The arc's authoritative narrative specification enters Stage3 as a free-text prompt substring. The LLM can add, remove, or modify story events without structural constraint. This is the root cause of EP5's intrusion invention.

### Seam 2 (MAJOR): beat_sequence and hybrid_composition dropped at boundary

Two of Stage2's explicit structural outputs describing episode-level progression and narrative tone are never consumed by Stage3. This means Stage3 generates scene-level content without knowing Stage2's intended beat structure.

### Seam 3 (MODERATE): state_changes lossy compression to advisory

Full structured state changes (15+ fields) are compressed and demoted to advisory priority. Important state facts like NPC deaths, relationship changes, and permanent injuries become non-binding.

### Seam 4 (MODERATE): episode_details structural demotion

Per-episode event lists are merged into the arc_focus prose block rather than being treated as structured constraints. Their authority is diluted by the surrounding tactical prose.

### Seam 5 (MODERATE): compile_to_prompt() is dead code

`BlueprintConstraintCompiler.compile_to_prompt()` (L138-275) provides a well-structured prompt formatter with explicit FACT-LOCK, CAPITAL-LOCK, MUST_FOCUS, STOP_LINE sections. But it has **zero live callers** — the actual generation path uses `BlueprintEnsemble._format_constraints()` instead. This means the compiler has two formatter implementations, only one of which is used, creating maintenance drift risk.

## Non-Issues

### N-1. Stage3 constraint banding is genuine and useful

The 4-band hierarchy (IMMUTABLE > HARD > CONTINUITY > ADVISORY) is a real structural improvement over Stage2's flat constraint packaging. This is not theater — it provides a clear conflict-resolution order that Stage2 lacks.

### N-2. fact_lock_packet and capital_continuity_packet are Stage3 innovations

These constructs are created by the compiler from prior manuscript/blueprint evidence and placed in the IMMUTABLE band. They enforce continuity for settled facts and capital state in a way Stage2 does not attempt. This is genuine downstream authority hardening.

### N-3. The prompt template's Context Priority Contract is well-designed

The explicit priority declaration (Constraint Stack > Arc Mission > Previous Truth > HUD) is architecturally correct. The problem is not the contract design but the lack of structural enforcement beyond prompt-level instruction.

### N-4. The validator has substantial prevalidation coverage

`_python_pre_validate()` runs 12+ check categories including structure, fidelity, arc compliance, continuity, fact-lock drift, capital drift, temporal drift, scene specificity, and Stage4 readiness. The issue is authority level (advisory-only), not coverage breadth.

---

## Verdict: mixed

Stage3 is neither a pure authority-preserving compiler nor a pure reinterpretation layer. It operates as a **mixed** system:

- **Compiler-like aspects**: constraint compilation, 4-band hierarchy, fact-lock/capital-lock packet construction, structured scene design
- **Reinterpretation-heavy aspects**: primary content generation via LLM interpretation of tactical prose, dropped Stage2 structural outputs (beat_sequence, hybrid_composition), state_changes demotion

The strongest evidence for "reinterpretation-heavy" is the EP5 case: Stage3's LLM generated narrative content (불량배 intrusion) that Stage2's tactical authority did not authorize, and the validation stack did not block it structurally.

The strongest evidence for "compiler-like" is the constraint banding, fact-lock, and capital-lock innovations — these genuinely preserve and harden Stage2 authority in ways Stage2 itself does not implement.

Net assessment: **Stage3 adds real structural value but remains a significant reinterpretation risk because its content generation path is not structurally bound to Stage2's narrative intent.**
