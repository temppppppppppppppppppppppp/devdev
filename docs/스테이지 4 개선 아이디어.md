## 0. 대원칙 — 디렉터 주권주의

```
┌──────────────────────────────────────────────────────────────┐
│                    Director (LLM)                            │
│                  = 유일한 PASS/REJECT 판정권자                │
│                                                              │
│  "판단은 LLM들이 하고 최상위 결정은 Director가 해야 함"       │
│  "판단에 필요한 재료를 Python이 보조해 주는 구조"             │
└──────────────────────────────────────────────────────────────┘

역할 분담:
- Python = 재료 제공자 (감지, 수집, 정리, 보고)
- LLM들 = 판단자 (모순 여부 평가, 심각도 판단)
- Director = 최종 결정권자 (PASS/REJECT 판정)

금지 사항:
- Python이 직접 REJECT 판정하는 것 ← 디렉터 주권주의 위반
- Python이 Director/LLM의 판정을 override하는 것
- Python이 후보를 제거하여 Director의 선택지를 줄이는 것
```

### S2-1 상세: Python CRITICAL → 직접 REJECT

```python
# unified_arc_validator.py:156-157
critical_count = sum(1 for i in all_issues if i.get("severity") == "CRITICAL")
if critical_count > 0:
    verdict = "REJECT"  # ← Python이 직접 판정!
```

**문제**: `_python_validate()`의 8개 체크 결과가 CRITICAL이면, LLM 문맥 분석과 무관하게 REJECT.
**개선안**: Python CRITICAL을 "경고 보고서"로 Director에 전달, Director가 판정.

### S2-3 상세: LLM REJECT를 Python이 PASS override (이중 침해)

```python
# continuity_arc.py:406-418
if result.get('decision') == 'REJECT' and not has_critical_cross_arc:
    if intra_only and start_state_corrected:
        result['decision'] = 'PASS'  # ← LLM의 REJECT를 Python이 PASS로!
```

**문제**: LLM이 "REJECT"로 판정했는데, Python의 조건(`intra_only`, `start_state_corrected`)으로 PASS 변환.
**개선안**: Python 조건을 "참고 정보"로 제공, LLM/Director가 최종 판단.

### S2-5 상세: Director REJECT → Python PASS 강제

```python
# stage2_orchestrator.py:1413-1424
if audit.get('decision') == 'REJECT' and draft_validator_passed and consensus_passed:
    if is_quota_failure:
        audit['decision'] = 'PASS'  # ← Director의 REJECT를 Python이 무시!
```

**문제**: Director가 REJECT했으나, Python이 "API 할당량 오류일 것"이라 판단하여 PASS 강제.
**개선안**: quota_failure 감지 시 Director에 재면담 요청, Python이 직접 판정 변경 금지.

## 7. Director 프롬프트 강화 (전 Stage)

### 7.1 공통 추가 섹션: 연속성 위반 REJECT 유도

```
### 🚨 연속성 위반 보고 — REJECT 판단 기준

아래 Python 사전 검증에서 CRITICAL 위반이 보고된 경우:
- 사망한 NPC의 재등장, 미습득 아이템 사용, 파괴된 장소 방문
- 시공간 모순 (순간이동, 타임라인 충돌)
- 동일 사건/아이템의 중복 발생

→ 해당 후보는 반드시 REJECT하세요.
→ REJECT 이유에 구체적 모순 내용을 포함하세요.

단, 다음은 모순이 아닙니다:
- 역사적 사실/현실 팩트와 다른 것 (투자물 주가, 실제 역사 등)
- 세계관 내 허용된 설정 (판타지 마법, 무협 경공)
- 캐릭터 성장에 따른 성격 변화 (근거가 있으면 OK)
```

### 7.2 Stage별 추가 개선

| Stage | 개선 | 내용 |
|-------|------|------|
| **Stage 2** | mandatory_context 신설 | StateTracker 정보를 Arc 판정 시 Director에 전달 |
| **Stage 2** | 과거 연속성 검사 추가 | 직전 Arc 종료 상태와 현재 Arc 시작 상태 정합성 |
| **Stage 3** | `BLUEPRINT_SELECTION_PROMPT` 신규 외부화 | 연속성 가중치 30%+ 명시 |
| **Stage 3** | mandatory_context 신설 | Python 검증 결과를 Director 프롬프트에 주입 |
| **Stage 4** | Python 경고 가중치 10%→35% | 감점이 아닌 판정 요소로 격상 |

### 7.3 REJECT 시 구조화 피드백

```json
{

    "continuity_violations": [

            "severity": "CRITICAL|MAJOR|MINOR",
            "fix_suggestion": "구체적 수정 방향"
        }
    ],
    "action_items": [
        "1순위: 씬#3의 철무련주를 부련주로 교체",
        "2순위: 타임라인을 '삼일 후'로 변경"
    ]
}
```

### 7.4 "역사적 사실 vs 서사 모순" 구분

```
A. 서사 모순 (REJECT 사유) — 이전 원고에서 확립된 사실과 충돌:
   - "제20화에서 A가 사망했는데 제25화에서 살아있다"
   - "제23화에서 검을 얻었는데 제25화에서 없다고 함"
   → 반드시 REJECT

B. 역사적 사실/팩트 불일치 (모순 아님):
   - "WTI 가격이 실제와 다름" (투자물 세계관)
   → 모순으로 보지 않음

C. 캐릭터 성장 (모순 아님) — 근거가 있는 변화:
   - "냉혹한 캐릭터가 사건 후 성격이 변함" (근거 있음)
   → PASS 가능
```

## 12. 결정된 정책 사항

1. **Python 최소 기준 유지**: 글자수/씬 수 극단적 미달(0자, 0씬)은 Director가 볼 가치 없음 → Python 필터링 유지 (주권 침해 아님)
2. **quota_failure 처리**: API 오류 시 Director 판정 override 금지 → 재면담 루프 추가 또는 다음 배치 재생성
3. **ContinuityInspector = "연속성 전문가"**: "판정자" → "전문가(장관)" 역할. Director 과로사 방지를 위해 도메인 전문 분석 담당. REJECT "권고"는 가능, "강제"는 불가
4. **냉동인간(Writer) 폐지**: ✅ **완료** — 5회 면담 모두 REJECT 시 실패 메시지 + `should_return=True` 반환. 패치 모드 전 라운드 적용
5. **False Positive 관리 — "내각제" 아키텍처**: Director가 혼자 다 하는 건 무리 → 전문가 LLM 체계 도입

## 13. "내각제" 아키텍처 — 전문가 체계

### 13.1 3계층 구조

```
┌───────────────────────────────────────────────────────────────┐
│ Python (공무원) = 데이터 수집, 팩트 확인                       │
│   BlockingValidator, StateTracker, ManuscriptValidator         │
│   "철무련주는 23화에서 사망" 같은 팩트만 수집                  │
│   ❌ 판단 금지, ❌ 권고 금지                                   │
├───────────────────────────────────────────────────────────────┤
│ 전문가 LLM (장관) = 도메인 분석, 권고안 작성                   │
│   ContinuityInspector → "연속성 장관"                         │
│   GenreGuard + LLM → "장르 장관"                              │
│   Python 팩트를 해석하여 Director에 권고                      │
│   ✅ REJECT 권고 가능, ❌ 최종 결정 불가                      │
├───────────────────────────────────────────────────────────────┤
│ Director (대통령) = 전문가 권고 검토 + 최종 PASS/REJECT       │
│   전문가 합의 시 → 가볍게 확인 후 결정 (부담 최소화)         │
│   전문가 의견 나뉠 시 → 직접 깊이 분석 후 결정               │
│   ✅ 유일한 최종 판정권                                       │
└───────────────────────────────────────────────────────────────┘
```

### 13.2 전문가 합의 체계 — False Positive 해결

```
케이스 1: 전문가 전원 "REJECT 권고"
  → Director는 높은 확률로 REJECT (재료 명확)
  → False Positive 낮음

케이스 2: 전문가 의견 나뉨
  연속성 전문가: "REJECT 권고 (타임라인 모순)"
  장르 전문가: "PASS 권고 (장르 규칙 준수)"
  → Director가 최종 판단 (이때만 깊이 분석)

케이스 3: 전문가 전원 "PASS 권고"
  → Director는 가벼운 확인만 하고 PASS
  → Director 부담 최소화

케이스 4: Python은 CRITICAL인데 전문가 LLM은 "괜찮음"
  연속성 전문가: "Python이 사망 NPC라 했지만 동명이인 확인"
  → Director는 전문가 분석 존중 → PASS
  → False Positive 해결
```

### 13.3 전문가 전환 대상

| 전문가 | 현재 구현 | 전환 방향 |
|--------|---------|---------|
| **ContinuityInspector** | LLM 기반 (이미 있음) | "판정자" → "권고자"로 반환값 변경 |
| **GenreGuard** | Python + `run_deep_validation()` | Python 팩트 + LLM 해석 분리 |
| **ManuscriptValidator** | Python only | Python 팩트 수집 유지 (전문가 불필요) |
| **BlockingValidator** | Python only | Python 팩트 수집 → ContinuityInspector가 해석 |

### 13.4 냉동인간 폐지 — 3회 REJECT = 시스템 종료

```
현재: 3회 REJECT → 냉동인간(Writer) 소환 → quick_judge (관대) → 강제 진행
개선: 3회 REJECT → 시스템 종료 + 실패 보고서 출력
     "3회 연속 REJECT. 연속성 모순이 해결되지 않아 중단합니다."
     사용자가 수동 검토 후 재시작
```

## 15. "걍 모순 있냐고 물어보면 되는 거 아냐?" — TF-A/B/C/D 조사 결과

> 유저 질문 원문:
> "모순이 있냐고 제미니에게 물어보면 답을 주잖아. api에서도 걍 모순이 있냐고 물어보면 되는 거 아냐?"
> "스테이지 2,3,4를 진행할 때도 제작 이전에 이전 정보와 모순이 없게끔 한다. 프롬프트 추가 어떰."
> "제작 이후에도 모순이 있냐고 물어보든가."

### 15.1 결론: 유저가 맞다

현재 시스템이 모순을 못 잡는 이유는 **복잡한 인프라 부족이 아니라, LLM에게 "모순 있냐"고 안 물어보기 때문.**

### 15.2 현재 시스템이 못 잡는 3가지 근본 원인

#### 원인 1: Director에게 "모순 찾아라"고 안 물어봄

`ENSEMBLE_SELECTION_PROMPT` (director_prompts.py L10~91)의 평가 기준:

```
1. 직전 화 연속성 + 내부 일관성 (35%):
   "자연스럽게 이어지는가?" ← 주관적 질문
   "모순이 1건이라도 있으면 0점" ← 있긴 한데...
```

문제:
- "자연스럽게 이어지는가?"는 **분위기/맥락** 질문이지 **사실 대조** 질문이 아님
- "모순이 있으면 0점"이라고만 했지, **무엇과 비교해서** 모순인지 기준이 없음
- **"이전 원고에서 확립된 사실 목록"이 프롬프트에 없으므로 비교 대상이 없음**

#### 원인 2: Director가 이전 원고를 500자만 받음

```python
# select_and_judge_ensemble() 호출 시:
previous_ending = prev_text[-500:]  # ← 500자만!

# 반면 audit_manuscript() 호출 시:
prev_full_text = _expand_prev_full_text()  # ← 3화 전문 로드
```

**핵심 문제**: 후보 선택(select_and_judge_ensemble)과 사후 검증(audit_manuscript)이 서로 다른 컨텍스트를 받음.
후보 선택 단계에서 이미 모순 있는 원고를 PASS하면, 사후 검증은 무의미.

#### 원인 3: 모순 검사 코드가 이미 있는데 비활성화

```python
# director_continuity.py:328 — 이미 완성된 메서드
check_manuscript_history_conflicts(
    ep_num, current_manuscript, manuscript_history
)

# director_prompts.py:97-135 — 이미 완성된 프롬프트
MANUSCRIPT_HISTORY_CONFLICT_PROMPT = """
[Role] 원고 연속성 전문가
[Task] 현재 원고가 이전 원고들과 충돌하는지 검사하라.
1. 사망 충돌  2. 아이템 충돌  3. 장소 충돌
4. 타임라인 충돌  5. 관계 충돌  6. 상태 충돌
"""
```

**→ 이 메서드가 stage4_orchestrator 파이프라인에서 호출되지 않음.**
코드는 완성, 연결만 안 됨.

### 15.3 해결책: Pre-Generation + Post-Generation 이중 방어

#### A. Pre-Generation — "모순 없게 만들어라" (생성 전 프롬프트 강화)

| Stage | 현재 상태 | 추가 필요 사항 |
|-------|---------|-------------|
| **Stage 2 (Arc)** | ✅ Preflight에서 이전 Arc 정보 상세 주입 | ⚠️ "이전과 모순되면 안 된다" 명시적 금지 지시 추가 |
| **Stage 3 (Blueprint)** | ✅ 이전 에피소드 요약 + HUD 주입 | ⚠️ 같은 명시적 금지 지시 추가 |
| **Stage 4 (Manuscript)** | ✅ prev_ending + HUD + lookback 10화 요약 주입 | ⚠️ **핵심 사실 목록**(이름/금액/상태) 명시 주입 + 금지 지시 |

**구체적 개선**:
```
현재 ChiefWriter 프롬프트:
  "[V66] 확장 Lookback: 직전 10화 요약"
  → 요약이라서 "한미증권" 같은 구체적 이름이 누락될 수 있음

개선안:
  "[핵심 사실 목록 — 변경 시 이유 명시 필수]"
  - 증권사: 한미증권 (3화에서 계좌 개설)
  - WTI 가격: 70.80달러/배럴 (5화 종가)
  - 가용 현금: 73억원 (6화 시점)
  → 이 사실과 다르게 쓸 경우 반드시 작중 이유를 설명해야 함
```

#### B. Post-Generation — "모순 있냐고 물어보기" (생성 후 검증 강화)

**즉시 가능한 개선 3가지**:

| # | 작업 | 난이도 | 효과 |
|---|------|--------|------|
| **B-1** | `check_manuscript_history_conflicts()` 활성화 — stage4_orchestrator에서 호출 연결 | 코드 이미 존재 | 모순 탐지 ~30%→~85% |
| **B-2** | Director `ENSEMBLE_SELECTION_PROMPT`에 `prev_full_text` 전달 (500자→3화 전문) | 프롬프트 필드 추가 | 모순 감지 정밀도 +20% |
| **B-3** | Director 프롬프트에 "명시적 모순 검사" 체크리스트 추가 | 프롬프트 텍스트 추가 | 구체적 피드백 품질 향상 |

**B-1 상세 (가장 ROI 높음)**:
```python
# stage4_orchestrator.py — 현재 818줄에 연속성 체크가 있지만 1회차만 실행
# 개선: 매 면담마다 실행 + REJECT 시 구체적 피드백

history_check = director.check_manuscript_history_conflicts(
    ep_num=next_ep,
    current_manuscript=best_manuscript,
    manuscript_history=recent_manuscripts  # 이전 N화
)

if history_check["decision"] == "CONFLICT":
    conflicts = history_check["conflicts"]
    # 구체적 피드백 예시:
    # "5화에서 '한미증권'이었는데 현재 원고에서 '대민증권'으로 바뀜"
    # "6화에서 '73억 전액 투자'라 했는데 현재 원고에서 '15억 이체'로 축소"
    director_feedback = format_conflict_feedback(conflicts)
    → ChiefWriter 재생성 시 이 피드백 전달
```

### 15.4 피드백 루프 현황

**현재 피드백 경로 (이미 작동 중)**:
```
Director REJECT → action_items 추출
    → ChiefWriter.regenerate_with_feedback(director_feedback=...)
    → 프롬프트에 "### 🚨 [Director 피드백 - 반드시 반영]" 섹션 주입
```

**문제점**: 피드백 구체성 부족
```
현재 피드백: "분량을 5,000자 이상으로 확장하세요"  ← 분량만 지적
개선 피드백: "5화에서 한미증권이었는데 9화에서 대민증권으로 바뀜.
            한미증권으로 통일하거나, 증권사 변경 이유를 작중에서 설명하세요."
```

**개선 후 예상 효과**:

| 지표 | 현재 | 개선 후 |
|------|------|--------|
| 모순 탐지율 | ~30% | ~85% |
| 피드백 구체성 | "분량 확장" 수준 | "어느 화의 무엇이 모순" 수준 |
| 2차 시도 모순 수정률 | ~20% | ~70% |
| 추가 토큰 비용 | - | +5~10% (~$0.05/ep) |

### 15.5 왜 현재 Python 검증은 이걸 못 하나?

**핵심**: Python은 "사전 정의된 규칙"만 체크 가능

```
Python이 잡을 수 있는 것:
  ✅ "철무련주"라는 NPC가 사망 목록에 있는데 원고에 등장 → 이름 매칭
  ✅ "용린검"이 상실 목록에 있는데 원고에서 사용 → 이름 매칭

Python이 잡을 수 없는 것:
  ❌ "한미증권" → "대민증권" 변경 → 증권사가 추적 대상이 아님
  ❌ "73억" → "15억" → 금액이 추적 대상이 아님
  ❌ "380 × $2 ≠ 42.5억" → 수학 검증 코드 없음
  ❌ "WTI 70 → 61, 하루 만에 13% 급락" → 현실성 판단 불가
```

**결론**: Python 인프라를 아무리 강화해도 **"사전에 모르는 모순"**은 잡을 수 없음.
LLM은 자연어 추론으로 **"사전 정의 없이도"** 모순을 감지할 수 있음.
따라서 **"모순 있냐고 LLM에게 물어보는 것"**이 가장 효과적인 해결책.

### 15.6 개선 실행 우선순위

```
Phase 1 (즉시, 가장 ROI 높음):
  ① check_manuscript_history_conflicts() 활성화
  ② ENSEMBLE_SELECTION_PROMPT에 prev_full_text 전달
  → 코드 이미 존재, 연결만 하면 됨

Phase 2 (다음):
  ③ Director 프롬프트에 "명시적 모순 검사 체크리스트" 추가
  ④ ChiefWriter Pre-Generation에 "핵심 사실 목록" 주입
  → 프롬프트 텍스트 작업

Phase 3 (선택):
  ⑤ 장르별 특수 검증 (투자물: 수학 검증, 무협: 경지 일관성)
  ⑥ 에피소드 단위 사실 스냅샷 자동 생성
  → 새 인프라 필요
```

### IDEA 7: 다단계 모순 검증 (Multi-Pass Verification)

```
핵심: 단일 LLM 호출 대신 여러 단계로 모순 검증
→ 각 단계가 서로 다른 관점에서 검사

Pass 1 — Flash 모델 (빠르고 저렴):
  "이전 원고와 현재 원고 사이에 명백한 사실 모순이 있는가?"
  → 빠른 스캔, 의심 항목 목록 생성

Pass 2 — Pro 모델 (정밀):
  "Pass 1에서 플래그된 N건에 대해 실제로 모순인지 정밀 분석하라"
  → 오탐 필터링, 확정 모순만 남김

Pass 3 — Director (최종 판정):
  "확정된 모순 목록 + 자유 형식 리뷰 → PASS/REJECT"

장점:
  - Flash 모델은 저렴 → 200K 컨텍스트 스캔 비용 절감
  - Pro 모델은 의심 항목만 정밀 분석 → 토큰 효율
  - Director는 확정된 정보만 받음 → 판단 품질 향상

비용 추정:
  Flash 스캔: ~$0.03/ep
  Pro 정밀분석: ~$0.05/ep (의심 항목 수에 비례)
  Director: 기존과 동일
  → 총 +$0.08/ep (현재 대비 미미한 증가)

난이도: ★★☆  효과: ★★★★☆
→ 현재 아키텍처에 쉽게 삽입 가능. Flash→Pro 체인은 이미 폴백 체인에 존재.
```

### IDEA 8: 장르 전문 수학 검증 (Domain Math Validator)

```
핵심: 투자물의 수익 계산, 무협의 경지 체계 등 장르별 수학/논리 검증

투자물 예시:
  프롬프트: "선물 수익 = 계약수 × 틱가치 × 변동폭. 아래 원고의 계산이 맞는지 검증하라."
  입력: "380계약, WTI $2 상승, 수익 42.5억원"
  → LLM: "380 × 1000배럴 × $2 = $760,000 ≈ 9.88억원. 42.5억은 오류."

무협 예시:
  프롬프트: "현재 경지: 후천초급. 아래 원고에서 사용한 무공이 이 경지에서 가능한지 검증하라."
  입력: "용천삼격을 연달아 사용하여..."
  → LLM: "용천삼격은 화경급 무공. 후천초급에서 불가능."

투자 계산기 (Python 보조):
  - 선물: 계약수 × 배수 × 단가변동 × 환율
  - 주식: 보유수 × (매도가 - 매수가) - 수수료
  - 부동산: 매입가 × 레버리지 × 수익률
  → Python이 계산, LLM이 원고 수치와 대조

난이도: ★★★  효과: ★★★☆☆ (장르별)
→ 투자물에서 효과 극대. 무협/판타지는 체계가 작품마다 달라서 범용화 어려움.
```

```
→ 가장 쉬운 개선 중 하나. 직전 화 연결만 강화 (장기 기억은 해결 안 됨)
```

### IDEA 12: 읽기 전용 팩트 체커 에이전트 (Read-Only Fact Checker Agent)

```
핵심: 생성과 분리된 별도 LLM 에이전트가 "팩트만 체크"

현재 문제:
  Director가 "품질 평가 + 모순 검사 + PASS/REJECT 판정"을 한 번에 수행
  → 모순 검사에 할당되는 주의력이 분산됨

개선:
  Fact Checker Agent (별도 LLM 호출):
    입력: 현재 원고 + 과거 사실 원장
    출력: 모순 목록 (있으면) or "모순 없음"
    역할: 오직 팩트 대조만. 품질/분량/문체 판단 안 함.

  Director:
    입력: 현재 원고 + Fact Checker 보고서
    출력: 최종 PASS/REJECT
    역할: 품질 + Fact Checker 보고서를 종합하여 판정

장점:
  - 팩트 체크에 LLM 전체 주의력 집중 → 감지율 향상
  - Director 부담 경감 → 품질 판단 집중
  - Fact Checker는 Flash 모델로도 충분 → 비용 절감

난이도: ★★☆  효과: ★★★★☆
→ IDEA 7(다단계 검증)의 구체화 버전. "내각제"의 실제 구현.
```

### IDEA 13: 작중 시간 타임라인 DB (In-World Timeline Database)

```
핵심: 작중 시간을 명시적으로 추적하여 시간 모순 방지

구조:
  timeline = [
      {"ep": 1, "in_world_date": "1987-03-01", "events": ["상속 발생"]},
      {"ep": 3, "in_world_date": "1987-03-05", "events": ["한미증권 계좌 개설"]},
      {"ep": 5, "in_world_date": "1987-03-07", "events": ["WTI 68→70.80 폭등"]},
      {"ep": 7, "in_world_date": "1987-03-08", "events": ["WTI 61.25 급락"]}
  ]

검증:
  - "하루 만에 13% 급락" → timeline에서 자동 감지
  - "어제 만났다" vs timeline 상 "3일 전" → 불일치 감지
  - 이동 시간 검증: "서울→부산, 같은 날 오후" → 가능(KTX) vs 불가능(도보)

추출:
  - 매 화 확정 후 LLM이 작중 날짜/시간 추출
  - state_changes에 `time_markers` 필드 이미 있음 (V66.1) → 활용 확대

난이도: ★★★  효과: ★★★☆☆
→ V66.1에서 기초 인프라(time_markers) 구축 완료. 추출 정확도가 관건.
```

### IDEA 14: 주기적 전수 팩트 감사 (Periodic Full Fact Audit)

```
핵심: 10화 또는 Arc 종료마다 "지금까지 전체 사실을 감사"

현재:
  모순 검사가 "이번 화 vs 직전 30화"만 비교
  → 31화 전의 모순은 영원히 못 잡음

개선:
  10화마다 Full Audit:
    입력: 팩트 원장(IDEA 6) 전체
    질문: "이 원장 안에서 서로 모순되는 사실이 있는가?"
    → "ep3에서 한미증권이었는데 ep45에서 대민증권으로 바뀜" 감지

  Arc 종료마다 Deep Audit:
    입력: 해당 Arc 전체 원고 + 팩트 원장
    질문: "이 Arc에서 새로 확립된 사실이 기존 사실과 충돌하는가?"
    → Arc 단위 일관성 보증

비용:
  10화마다 1회 × Flash 모델 = ~$0.05/10ep = $0.005/ep
  → 무시할 수 있는 수준

난이도: ★★☆  효과: ★★★★☆
→ IDEA 6(팩트 원장)이 선행 필요. 있으면 구현 간단.
```
