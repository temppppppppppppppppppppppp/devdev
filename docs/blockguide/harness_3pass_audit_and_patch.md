## PASS 1: 구조 정합성 — "하네스 시스템은 순차적 시스템인가?"

### 1.1 설계 의도 (맞는 부분)

하네스 시스템은 **명확한 순차 파이프라인**이다:

```
Planning (원칙 A~K, 18단계 설계)
  → Phase 0 (대단원 아크 + 적대자 + NPC + 복선 + 자본곡선)
    → Production (3블록 안전배치 → 검증 → 확장)
      → BI (동기화 산출물)
```

SSOT §4의 "1턴 1단위 규칙", §6의 "auto-run + 정지 게이트", §7의 "저지능 LLM용 10개 규칙"은 **LLM이 한 번에 다 하지 못하게** 설계됨.

### 1.2 실제 작동 (깨지는 부분)

**그런데 실제 TR 2건이 동일 패턴으로 실패했다.** 이것은 "LLM이 한 번에 다 하려고 했거나", "순차 시스템이 실제로 강제되지 않았거나", "순차 시스템이 강제되었지만 각 단계의 품질 게이트가 약했다"는 뜻이다.

| 증거 | 의미 |
|------|------|
| chaebol: opponent 4명, weakness 7종, solution 말미 전량 동일 | Phase 0에서 opponent 4명만 설계 → Production이 그대로 복사 |
| us_ai_exile: opponent 10명이지만 아크 내 1명, weakness 사실상 1종 | Phase 0에서 "아크 = opponent 1명" 구조 → Production이 10아크 × 1명 복사 |
| 양쪽 모두: solution 말미 69~70블록 동일 | Production 프롬프트가 solution 다양성을 **생성 시점에 강제하지 않음** |

### 1.3 PASS 1 판정

| 항목 | 판정 |
|------|------|
| 순차 구조 설계 | **PASS** — 문서 구조는 맞음 |
| 순차 강제력 | **FAIL** — 강제 메커니즘이 문서 규칙일 뿐, 실행 시 검증 루프가 없음 |
| Phase 0 품질 게이트 | **FAIL** — opponent/weakness 설계 깊이를 검증하는 정량 게이트 없음 |

## PASS 2: 근본 원인 분석 — "왜 같은 패턴으로 실패하는가?"

### 2.1 근본 원인 5대 축

#### RC-1. Phase 0의 opponent 설계가 **수량만 요구하고 배분을 강제하지 않음**

Planning 하네스 §14.1A 순번 8~9:
```
8. 핵심 적대자 1차 묶음 — 내부 적대축을 만든다
9. 중기/후기 적대자 확장 — 업계 적대자와 최종 권력전을 고정
```

Production 하네스 Phase 0 §2:
```
1. 적대자 전환 계획(opponent_transition_plan) — 최소 3세력, 전환 블록 포함
```

**문제**: "최소 3세력" + "전환 블록 포함"이지만:
- 아크별 최소 몇 명인지 없음
- 단일 opponent 점유율 상한 없음
- opponent × sector × weakness 교차 매트릭스 없음
- Phase 0 완성 후 정량 검증 게이트 없음

→ LLM이 "3세력 설계했으니 완료"로 판단하고, 70블록에 3~4명만 반복 배치.

#### RC-2. weakness_exploited 설계 자체가 Phase 0에 없음

Planning 하네스 11개 원칙(A~K)에는 "적대자 합리성"(원칙 C)과 "적대자 이득 구조"가 있지만, **weakness_exploited를 아크별로 사전 설계하라는 지시가 없다**.

Production 하네스 Rule 7: `"weakness_exploited 동일 표현 3회 금지"` — 이것은 **생성 후 검증 규칙**이지 **설계 지시**가 아님.

→ LLM이 Phase 0에서 weakness를 설계하지 않고, Production에서 즉석 생성. 결과: 아크 내 동일 weakness 복사.

#### RC-3. Production 프롬프트(§14)가 **이전 배치의 solution 패턴을 보여주지 않음**

Production 하네스 §3.1 생성 프롬프트 컨텍스트 6개:
```
1. Phase 0 아크 설계
2. 이전 블록 최대 10개
3. 자본 곡선
4. NPC 상태
5. 적대자 상태
6. 복선/회수 상태
```

**빠진 것**: "직전 블록들의 solution 말미 패턴", "지금까지 사용된 weakness 목록", "지금까지 사용된 opponent 빈도"

→ LLM이 이전에 뭘 썼는지 모르니, 같은 템플릿을 반복.

#### RC-4. validate_v1/v2가 opponent/weakness/solution 템플릿을 잡지 못함

| 검증 함수 | 잡는 것 | 못 잡는 것 |
|-----------|---------|------------|
| validate_v1 (패턴 A~H) | 빈 필드, 영어 오염, 대사 비율, 포맷 | opponent 다양성, weakness 반복, solution 템플릿 |
| validate_v2 (패턴 I~P) | 자본 연속성, deal_type 반복, 복선 밀도 | 위와 동일 |
| **validate_v3 (패턴 Q~U)** | **opponent, weakness, solution, 밀도** | — |

validate_v3는 **TF-BH1에서 신설**됨. 기존 v1/v2로는 이 실패 패턴을 탐지 불가.

**하지만 validate_v3가 있어도**, 배치 생성 → 검증 → 재작업 루프에서 **검증 결과가 다음 배치 프롬프트에 피드백되지 않으면** 같은 패턴이 반복됨.

#### RC-5. "3블록 안전 모드"가 실제로 발동하지 않음

Production 하네스 §1: `"Opus: 10블록, Gemini Pro: 5, Flash: 3"`, `"확신 낮으면 3블록 안전 모드로 강등"`

**문제**: "확신이 낮은지" 판단하는 기준이 없음. LLM은 자기 확신이 항상 높으므로 10블록 모드로 달림.

→ 10블록 단위로 찍으면, 아크 1개(10블록)가 한 번에 나오고, 그 안에서 opponent/weakness가 고정됨.

### 2.2 근본 원인 요약표

| # | 근본 원인 | 위치 | 영향 | 패치 난이도 |
|---|-----------|------|------|-------------|
| RC-1 | Phase 0 opponent 배분 매트릭스 부재 | Planning §14.1A, Production §2 | opponent 4~10명이지만 아크 독점 | 중 |
| RC-2 | weakness 사전 설계 지시 부재 | Planning 전체, Production §2 | weakness 사실상 1종 | 중 |
| RC-3 | 생성 프롬프트에 패턴 피드백 없음 | Production §3.1, §14 | solution 템플릿 반복 | 상 |
| RC-4 | v1/v2가 핵심 결함 미탐지 | Production §5.1~5.2 | 생산 중 조기 탐지 실패 | 하 (v3 이미 존재) |
| RC-5 | 안전 모드 발동 기준 부재 | Production §1 | 10블록 일괄 생산 → 아크 내 고정 | 하 |

### 2.3 "LLM이 한 번에 다 하려고 하는가?" — 답변

**Yes, 그러나 하네스 탓이 더 크다.**

하네스가 "1턴 1단위"를 선언하지만, 실제로:
1. Phase 0에서 opponent를 **블록 레벨까지 배분하라는 지시가 없어서**, "3세력 설계" = "3명 이름 나열"로 끝남
2. Production에서 10블록 배치가 기본이라, 아크 1개가 한 번에 나오고 그 안에서 variety가 0
3. 검증(v1/v2)이 이 문제를 못 잡아서, 다음 배치로 그냥 넘어감
4. 7아크 × 10블록이 끝나면, 70블록 전체에 걸친 패턴 반복이 이미 고정

**순차 시스템이지만, 각 단계의 품질 게이트가 핵심 결함을 통과시키는 구조.**

## PASS 3: 오더 프롬프트 적절성 — "프롬프트가 다양성을 강제하는가?"

### 3.1 Production 프롬프트 분석 (§14.1 Opus/Sonnet 전체판)

프롬프트 구조 23줄 중:
- Phase 0 컨텍스트 주입: ✓
- 이전 블록 참조: ✓
- 31개 금지 규칙 요약: ✓
- **opponent 다양성 지시**: ✗ (Rule 29는 문서에 있지만 프롬프트 본문에 요약 포함 여부 불확실)
- **weakness 차별화 지시**: ✗
- **solution 말미 다양성 지시**: ✗
- **이전 배치 패턴 경고 피드백**: ✗

### 3.2 Planning 프롬프트 분석 (§14.1A 18단계)

순번 8~9(적대자 설계):
```
8. 핵심 적대자 1차 묶음 — 내부 적대축을 만든다
9. 중기/후기 적대자 확장 — 업계 적대자와 최종 권력전을 고정
```

**문제**:
- "만든다", "고정"이지 **"아크별 배분하라"가 아님**
- 적대자 수량 하한 없음 (Production Phase 0에서야 "최소 3세력")
- weakness 설계는 이 18단계에 **아예 없음**
- solution 패턴 가이드라인도 없음

### 3.3 사전 선언 프로토콜 (Production §3.3)

기존 5항목:
```
1. 이전 배치와 capital 연속성
2. 이번 배치의 NPC 변동
3. 이번 배치의 deal_type
4. 이번 배치의 복선/회수
5. 이번 배치의 emotional_beat
```

TF-BH1 추가 1항목:
```
6. 약점 차별화 증명
```

**문제**: opponent 배분/교체 선언이 없음. "이번 배치에서 어떤 opponent를 쓰고, 이전 배치와 어떻게 다른지"를 선언하지 않음.

### 3.4 차이 행렬 (Production §3.4)

기존 20항목 + TF-BH1 추가 5항목(21~25):
```
21. opponent 열에서 고유 이름이 대단원 내 2명 미만?
22. solution 마지막 20자가 같은 블록 5개 이상?
23. weakness_exploited가 10블록 내 3종 미만?
24. content 4필드 합계 200자 미만?
25. sector 같은 값 10블록+ 연속?
```

**문제**: 이 차이 행렬은 **배치 종료 후 자기 검증**이다. 즉, 이미 생성된 다음에 체크. 생성 시점에 다양성을 강제하지 않음.

### 3.5 PASS 3 판정

| 항목 | 판정 |
|------|------|
| 오더 프롬프트의 구조 | **PASS** — 체계적 |
| 오더 프롬프트의 다양성 강제력 | **FAIL** — 생성 시점에 opponent/weakness/solution 다양성을 주입하지 않음 |
| Phase 0 프롬프트의 배분 지시 | **FAIL** — "3세력 만들라"만 있고, "아크별 배분하라" 없음 |
| 피드백 루프 | **FAIL** — 검증 결과가 다음 배치 프롬프트에 주입되지 않음 |

## 패치안: 5건

### P-1. Phase 0 "opponent × arc 배분 매트릭스" 의무화 (RC-1 해소)

**대상**: Planning 하네스 §14.1A 순번 8~9 사이 + Production 하네스 §2

**패치 내용**:

Planning §14.1A에 순번 8.5 신설:
```
8.5 적대자 아크 배분표 — 각 대단원(10블록)에 최소 2명의 고유 opponent를 배정한다.
    70블록 전체 고유 opponent ≥8명.
    단일 opponent가 전체의 30%를 넘지 않도록 배분한다.
    이 표가 없으면 Phase 0 미완성이다.
```

Production §2 "최소 필수 시트"에 추가:
```
5. 적대자 블록 배분표(opponent_block_allocation) — 대단원별 primary/secondary opponent, 점유 블록 범위
```

Phase 0 출고 게이트에 정량 체크 추가:
```
- 고유 opponent ≥8명
- 단일 opponent 점유율 ≤30%
- 아크별 고유 opponent ≥2명
```

### P-2. Phase 0 "weakness × arc 사전 설계" 의무화 (RC-2 해소)

**대상**: Planning 하네스 §14.1A + Production 하네스 §2

**패치 내용**:

Planning §14.1A에 순번 8.7 신설:
```
8.7 약점 다양화 설계 — 각 대단원(10블록)에 최소 3종의 고유 weakness를 설계한다.
    weakness는 opponent 이름 치환이 아니라 "적대자가 간과하는 구조적 빈틈"이 달라야 한다.
    70블록 전체 고유 weakness ≥10종.
    이 설계가 없으면 Phase 0 미완성이다.
```

sector_roadmap (R32) 확장 시트에 `unique_weaknesses` 필드를 **필수**로 승격:
```json
{
  "sector": "장례의전",
  "unique_weaknesses": [
    "운영비 인식 부재 — 비용표에 묻힌 실제 원가",
    "외주 단가 불투명 — 단가 기준이 현장이 아니라 본사",
    "의전 인력 이직률 무관심 — 교체 비용을 안 세는 구조"
  ]
}
```

### P-3. 생성 프롬프트에 "패턴 피드백 블록" 주입 (RC-3 해소)

**대상**: Production 하네스 §3.1 생성 프롬프트 컨텍스트, §14 프롬프트 템플릿

**패치 내용**:

생성 프롬프트 컨텍스트 7번째 항목 추가:
```
7. 패턴 경고 피드백 (이전 배치까지 누적)
   - 지금까지 사용된 opponent 빈도: {opponent_frequency_table}
   - 지금까지 사용된 weakness 목록: {weakness_list_so_far}
   - solution 말미 20자 반복 경고: {solution_tail_warnings}
   - "위 목록에 이미 있는 패턴을 이번 배치에서 반복하지 마라"
```

이 피드백은 **validate_v3 중간 실행 결과**에서 자동 추출:
```python
def build_pattern_feedback(blocks_so_far: list[dict]) -> str:
    """이전 배치까지 누적 블록에서 패턴 경고를 생성."""
    opps = Counter(b.get('genre_ext',{}).get('opponent',{}).get('name','') for b in blocks_so_far)
    weaknesses = set(b.get('genre_ext',{}).get('opponent',{}).get('weakness_exploited','') for b in blocks_so_far)
    tails = Counter(b.get('content',{}).get('solution','')[-20:] for b in blocks_so_far)

    lines = ["[패턴 피드백]"]
    lines.append(f"opponent 빈도: {dict(opps.most_common(5))}")
    lines.append(f"사용된 weakness {len(weaknesses)}종")
    for tail, cnt in tails.most_common(3):
        if cnt >= 3:
            lines.append(f"⚠ solution 말미 '{tail}' {cnt}회 반복 — 이번 배치에서 다른 결말 필수")
    return "\n".join(lines)
```

### P-4. 사전 선언 프로토콜에 "opponent 교체 선언" 추가 (RC-3 보완)

**대상**: Production 하네스 §3.3

**패치 내용**:

기존 6항목 뒤에 7번 추가:
```
7. **opponent 교체 증명**: 이번 배치의 opponent가 직전 배치와 최소 1명 다른 이유를 1문장으로 서술하라.
   - 같은 opponent를 연속 5블록 이상 사용할 수 없다.
   - 예: "직전 배치는 윤석진(CFO) 중심. 이번 배치는 린넨 공급업체 대표가 합류하며 갈등 축 분화."
```

### P-5. 배치 크기 "첫 아크 3블록 강제" + "아크 전환 시 3블록 재강등" (RC-5 해소)

**대상**: Production 하네스 §1, SSOT §4

**패치 내용**:

Production §1 배치 크기 규칙 교체:
```
기존: "Opus: 10블록, 확신 낮으면 3블록 안전 모드"
변경:
- 첫 아크(블록 1~10): 반드시 3→4→3 안전 배치로 시작.
```

**근거**: 10블록 일괄 = 아크 1개 통째로 생성 = 아크 내 variety 0. 3블록 강제로 중간 검증 기회를 확보.

## 왜 실패했는가: 1문장 요약

**Phase 0이 "몇 명 만들라"만 말하고 "어디에 배치하라"를 안 말하니, LLM이 3~10명을 설계해놓고 70블록에 복사 붙여넣기 했다. Production 프롬프트가 "이전에 뭘 썼는지"를 안 보여주니, 매 배치가 독립적으로 같은 템플릿을 반복했다. 검증(v1/v2)이 이걸 못 잡으니, 70블록이 완성될 때까지 아무도 문제를 모른 채 끝났다.**
