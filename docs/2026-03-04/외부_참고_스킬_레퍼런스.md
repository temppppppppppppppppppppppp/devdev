## 3. Gemini API 활용 스킬

글도비가 전면 의존하는 Google Gemini API의 최적 사용법.

### 3-1. Context Caching (비용 절감)

글도비의 `base_agent.py`에서 이미 `_get_or_create_context_cache`를 구현 중. 추가 최적화 포인트:

| 기법                 | 설명                                                                                                     | 적용 대상                                   |
| -------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| **Implicit Caching** | Gemini 2.5+ 모델에서 자동 활성화. 프롬프트 앞부분에 안정적 콘텐츠→끝에 변동 콘텐츠 배치 시 캐시 히트율 ↑ | `chief_writer`, `director` 시스템 프롬프트  |
| **Explicit Caching** | 수동 설정, 보장된 비용 절감. 최소 32,768 토큰 (Gemini 2.5는 더 낮음)                                     | Bible/Treatment/Arc 전술서 등 대형 컨텍스트 |
| **프롬프트 구조화**  | 접두사 매칭 기반이므로 — ①시스템 지시 ②참조 문서 ③사용자 질문 순서 유지                                  | 모든 에이전트 프롬프트                      |

```
최적 배치:
[시스템 인스트럭션] ← 고정, 캐시 가능
[Bible/세계관 문서] ← 프로젝트 내 고정, 캐시 가능
[Arc 전술서] ← Arc 내 고정, 캐시 가능
[이전 원고 컨텍스트] ← 에피소드별 변동
[현재 작업 지시] ← 매번 변동
```

### 3-2. Structured Output (JSON 스키마)

글도비가 `response_mime_type="application/json"` + `response_json_schema`를 사용 중. 추가 팁:

- **Pydantic 모델 → JSON Schema 자동 변환**: Gemini API가 Pydantic 직접 지원. `response_schemas.py`의 기존 dict 스키마를 Pydantic 모델로 전환하면 타입 안전성 ↑
- **description 필드 활용**: 스키마의 각 필드에 `description`을 넣으면 LLM이 더 정확하게 응답
- **enum 사용**: `fix_scope`, `verdict` 같은 제한된 값은 `enum`으로 정의하면 출력 정확도 ↑

### 3-3. Prompt Engineering (Gemini 3 특화)

```
Gemini 3 모델 기본 성향:
- 간결하고 직접적인 응답 (자세한 설명 원하면 명시적 요청 필요)
- 시스템 인스트럭션에 핵심 제약/역할 배치 권장
- Few-shot 예시가 장문 지시보다 효과적
- PTCF 프레임워크: Persona→Task→Context→Format
```

## 4. Hybrid Search (sqlite-vec + FTS5 + RRF)

글도비의 `vec_memory.py`가 이미 구현. 외부 best practices 정리.

### 현재 글도비 구현

```
Dense: gemini-embedding-001 (3072차원) → sqlite-vec KNN k=20
Sparse: FTS5 전문 검색 k=10
Hybrid: Reciprocal Rank Fusion (k=60)
```

### 참고할 개선 포인트

| 개선 항목         | 설명                                                                    | 참고 출처                                 |
| ----------------- | ----------------------------------------------------------------------- | ----------------------------------------- |
| **Pre-filtering** | FTS5로 후보 축소 → 벡터 검색 범위 제한 → 성능 ↑                         | alexgarcia.xyz (sqlite-vec 제작자 블로그) |
| **가중치 튜닝**   | FTS5/vec 결과에 서로 다른 가중치 부여 가능 (예: 0.7 dense + 0.3 sparse) | Hybrid Search 논문                        |
| **sqlite-lembed** | Ollama 기반 로컬 임베딩 — API 비용 절감 가능                            | sqlite 생태계 확장                        |
| **BM25 스코어링** | FTS5의 `rank` 함수로 BM25 점수 활용 — 현재 사용 여부 확인 필요          | SQLite FTS5 공식 문서                     |

### RRF 공식 (참고)

```
RRF_score(d) = Σ 1 / (k + rank_i(d))    (k=60이 표준)
```

## 6. Pydantic v2 + LLM 응답 파싱 패턴

글도비가 `pydantic>=2.0`을 이미 사용 중. 최적 활용 패턴:

### 6-1. 구조화된 출력 검증

```python
# 권장 패턴: Pydantic 모델로 LLM 응답 정의
from pydantic import BaseModel, Field
from enum import Enum

class FixScope(str, Enum):
    INPLACE = "inplace"
    PARTIAL = "partial"
    FULL = "full"

class DirectorVerdict(BaseModel):
    verdict: str = Field(description="PASS, REJECT, or PASS_WITH_FIX")
    score: int = Field(ge=0, le=100, description="품질 점수 0-100")
    fix_scope: FixScope | None = Field(None, description="수정 범위")
    feedback: str = Field(description="수정 피드백")
```

### 6-2. 재시도 패턴 (LLM 파싱 실패 시)

| 패턴                                    | 설명                                     | 글도비 현재 구현                                             |
| --------------------------------------- | ---------------------------------------- | ------------------------------------------------------------ |
| **Simple Retry**                        | 동일 요청 재시도                         | ✅ `base_agent.py` 네트워크 재시도 22회 (선형 백오프 10~30초) |
| **Corrective Prompting**                | 에러 메시지를 LLM에 피드백하여 자체 수정 | ⚠️ 부분적 — PASS_WITH_FIX 피드백 전달                         |
| **Exponential Backoff + Jitter**        | 지수적 대기 + 랜덤 편차                  | ⚠️ Rate Limit은 선형 백오프(30×n초), Jitter 미구현            |
| **Fallback Chain**                      | 실패 시 다른 모델로 전환                 | ✅ 4단계 모델 폴백                                            |
| **Circuit Breaker**                     | 연속 실패 시 일시 차단                   | ✅ 2중 구현: ①continuation 5회 제한 ②쿼터 모델 1h TTL 차단    |
| **Partial Validation** (Pydantic 2.10+) | 스트리밍 중 부분 검증                    | ❌ 미구현 — 향후 검토 가능                                    |

```
   + A-4 실패 패턴 감지           ← 같은 모순 2연속 → Arc 구조 진단
```

## 29. 자체 프레임워크 정규화·표준화·강화 로드맵

> 외부 프레임워크 전환 대신 **자체 프레임워크를 내부적으로 완성**하는 전략.
> 현재 자산: Agent 21종 · Stage 클래스 15종 · **Protocol 13종** (Agent 5 + Service 5 + DB 1 + Validator 2)

### 29-1. 정규화 (Normalization) — ★★★ 최우선

> **목표**: 47개 컴포넌트(에이전트 8 + Skills 39) 파일의 인터페이스 통일, 중복 제거, 일관된 호출 패턴.

| 현재 문제                | 구체 사례                                                                              | 해결 방안                              |
| ------------------------ | -------------------------------------------------------------------------------------- | -------------------------------------- |
| **호출 패턴 불일치**     | `analyst.py`는 `ask()`, `chief_writer.py`는 `generate()`, `director.py`는 `evaluate()` | `BaseAgent.run()` 단일 진입점으로 통일 |
| **반환 타입 혼재**       | `str`, `dict`, `tuple`, `NamedTuple` 혼재                                              | `AgentResult` Pydantic 모델로 통일     |
| **에러 처리 분산**       | 각 에이전트마다 try/except 패턴 상이                                                   | `BaseAgent._safe_call()` 데코레이터    |
| **프롬프트 로딩 불균일** | 일부 하드코딩, 일부 `PromptLoader`                                                     | 전면 `PromptLoader` 마이그레이션       |
| **Context 구조 차이**    | `Stage2Context`, `Stage3Context`, `Stage4Context` 필드 불일치                          | 공통 `BaseContext` + Stage별 확장      |

**정규화 액션 플랜**:
```
Phase A: 인터페이스 통일 (1~2주)
├─ BaseAgent.run(input: AgentInput) → AgentResult 정의
├─ 47 컴포넌트 시그니처 정규화 (에이전트 8 + Skills 39)
└─ Protocol 5종에 run() 반영

Phase B: 반환 타입 통일 (1주)
├─ AgentResult(success: bool, data: Any, errors: list, metadata: dict)
├─ 기존 반환값 → AgentResult 래핑
└─ 점진적 마이그레이션 (하위호환 유지)

Phase C: Context 계층 정리 (1주)
├─ BaseContext (공통 필드: project, episode_no, db, config)
├─ Stage2Context(BaseContext) 확장
├─ Stage3Context(BaseContext) 확장
└─ Stage4Context(BaseContext) 확장
```

| **Self-Play Fine-tuning**                | LLM이 자기 생성 vs 인간 텍스트를 구분 학습 → 반복 개선. DPO 능가     | `adversarial_self_play.py`              | 원고 품질 **자동 향상** — Chief Writer 출력 → Critic 비판 → 재생성 루프    |
| **DPO (Direct Preference Optimization)** | 인간 선호 쌍( preferred / dispreferred) 직접 학습 → 보상 모델 불필요 | `director_selections` DB 테이블         | PASS vs REJECT 원고 쌍 → **Director 판정 데이터로 DPO 학습** 가능          |
| **Constitutional AI**                    | 원칙("헌법") 기반 자기 비판 → 자기 수정, 인간 피드백 불필요          | `chief_writer_quality.py` self-critique | 현재 5가지 체크 → **CLAUDE.md 대원칙을 "헌법"으로** 주입하면 CAI 패턴 완성 |
| **RISE (Recursive IntroSpection)**       | 과거 실패 궤적 → 반성문 → 작업 기억 업데이트 → 개선                  | `failure_learning.py`                   | Stage3/4 실패 패턴 DB → **다음 생성 시 자동 회피**                         |
| **SEAL (Self-Adapting LM)**              | 자기 편집 + RL로 가중치 자체 업데이트                                | 🔬 장기 연구                             | Gemma 3 로컬 Fine-tuning 시 적용 검토                                      |

### 36-3. DPO 학습 데이터 자동 수집

```python
# director_selections 테이블에서 DPO 학습 쌍 자동 추출
# PASS 원고 = preferred, REJECT 원고 = dispreferred

SELECT 
    s.selected_draft AS preferred,      -- Director가 선택한 원고
    s.rejected_drafts AS dispreferred,  -- Director가 탈락시킨 원고들
    s.score, s.feedback
FROM director_selections s
WHERE s.score >= 70  -- 충분히 신뢰 가능한 판정만

# → Gemma 3 LoRA DPO Fine-tuning에 충분
```

## 41. LLM 보안 — 프롬프트 인젝션 방어

> 글도비는 외부 사용자 입력을 받지 않으므로 인젝션 리스크 낮음. 그러나 **생성된 원고가 프롬프트를 오염**시키는 "자기 인젝션" 위험은 존재.

### 41-1. 글도비 특유의 보안 위험

| 위험               | 발생 경로                                                            | 현재 방어     | 개선안                                       |
| ------------------ | -------------------------------------------------------------------- | ------------- | -------------------------------------------- |
| **자기 인젝션**    | 생성된 원고 텍스트가 다음 에피소드 컨텍스트로 재주입 → LLM 지시 오해 | ❌ 없음        | 원고 텍스트 ↔ 시스템 지시 격리 (구분자 강화) |
| **프롬프트 누출**  | LLM이 시스템 프롬프트를 원고 내에 그대로 출력                        | YAML 외부화   | 출력 후처리 필터링 추가                      |
| **JSON 파싱 주입** | LLM이 반환한 JSON에 악의적 키/값                                     | Pydantic 일부 | 전 출력 Pydantic 강제                        |

### 41-2. 계층적 방어 전략 (외부 참고)

**추천 파이프라인**:
```python
def parse_manuscript_to_vn(text: str) -> list[VNCommand]:
    """글도비 원고 → WebGAL 스크립트 변환"""
    commands = []
    for line in text.split('\n'):
        # 1단계: 규칙 기반 — 대사 패턴 매칭
        if match := re.match(r'[「"](.*?)[」"]', line):
            speaker = detect_speaker(line)  # NPC 레지스트리 참조
            commands.append(Say(speaker, match.group(1)))
        
        # 2단계: 장면 전환 감지 (Blueprint 기반)
        elif is_scene_break(line):
            commands.append(ChangeBg(get_scene_bg(line)))
        
        # 3단계: 지문 → 나레이션
        else:
            commands.append(Narration(line))
    
    # 4단계: 감정 비트 → 표정/BGM 주입
    inject_emotions(commands, emotional_beats)
    return commands
```

**한국어 특수 과제**:
- 조사 결합 (「~라고 했다」 vs 직접 화법) → 정규식 패턴 라이브러리 필요
- 존칭 체계 (해요체/합쇼체/해체) → 캐릭터 관계에 따른 표정 매핑
- 웹소설 관례 (♧, ◆, --- 등 장면 전환 기호) → 커스텀 토큰 사전
