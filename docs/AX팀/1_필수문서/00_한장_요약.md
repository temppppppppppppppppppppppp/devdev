# 글도비 AX 검토 한 장 요약

## 검토 요청 개요

글도비는 LLM으로 장기 연재형 웹소설 생산 공정을 자동화하려는 프로젝트입니다.

저희가 파악하는 범위에서는 LLM을 통한 장편 글쓰기, 특히 장기 연재형 웹소설 생산에는 아직 널리 합의된 표준 프로세스가 없습니다. 글도비는 상업 웹소설을 반복 가능한 장르 패턴, 대리만족, 캐릭터 관계, 회차별 보상 구조를 가진 패턴 구조로 보고, 이를 LLM 파이프라인으로 안정적으로 생산할 수 있는지 검증하고 있습니다.

이번에 AX팀에 요청드리는 것은 문장 표현 교정보다는 LLM 파이프라인 구조, 비용, 응답 지연, 토큰/캐시 최적화 검토, 그리고 운영/기획 관점의 의사결정 기준 수립 지원입니다.

핵심 요청은 두 가지입니다.

1. S4, 즉 실제 원고 생성/검토/정착 단계에서 연속성 문제를 어떻게 더 낮은 비용으로 조기에 탐지할지에 대한 최적화 검토
2. 현재 상태를 기준으로 앞으로의 개발 로드맵, 적정 예산, 실전 테스트 규모, 계속 투자/축소/전환 기준을 어떻게 잡을지에 대한 판단 기준 제안

## 용어 기준

- S0/S2/S3/S4: 글도비 시스템의 생산 단계 이름입니다.
- 작가 에이전트(ChiefWriter): 원고 후보를 생성하는 LLM 역할입니다.
- 검토 에이전트(Director): 원고 후보를 평가하고 수정 방향을 판단하는 LLM 역할입니다.
- 통과(PASS): 해당 단계 기준을 통과했다는 뜻입니다. Stage4 통과가 곧 플랫폼 제출 최종본이라는 뜻은 아닙니다.
- 정착: 통과한 결과를 DB, 파일, 로그, 다음 회차 맥락에 일관되게 저장하는 과정입니다.
- 정본: 다음 단계가 기준으로 삼아야 하는 공식 원고나 사실 정보입니다.

## 현재 어디까지 왔나

- S0/S2/S3/S4 기준의 장기 콘텐츠 생산 파이프라인이 있습니다.
- AX팀 검토에서는 현재 생산축을 `S2 -> S3 -> S4`로 보면 됩니다. S2는 block의 2~6화 페이싱과 방향을 정하고, S3는 회차별 스켈레톤을 설계하며, S4는 실제 원고를 생성, 검토, 재시도, 정착합니다.
- 감독형 실행 기준으로 15화 초안 연쇄를 생성했습니다.
- 최종 승인 원고 접근자, 설계도 계보, 정착 증거, 품질 신호, 맥락 캐시 관측값이 있습니다.
- 권위 기준은 S3 회차 설계도, S4 최종 승인 원고, bible/DB 정착 정보로 나뉩니다. 맥락 캐시와 세션 메모리는 정본이 아니라 비용과 지연을 줄이기 위한 보조 계층입니다.
- 현재 LLM 호출은 GCP/Vertex AI Gemini 경로로 직접 연결되어 있으며, 세션 메모리 envelope와 맥락 캐시 관측값을 보조 계층으로 기록합니다.
- 다만 현재 Stage4 통과(PASS)는 "상업 제출 후보본"이라기보다 "쓸 수 있는 초안"에 가깝습니다.

## 운영/기획 의사결정 지원 필요성

개발 실무자가 아닌 운영/기획 담당자 관점에서는, 현재 시스템을 기술적으로 어디까지 왔다고 봐야 하는지에 대한 판단 기준이 필요합니다.

개발 기간이 길어진 구조적 이유는 단순 원고 생성기가 아니라, S4 원고 단계의 연속성 검증, 정착, 장기기억 계보, 재시도 비용 통제를 함께 다루는 생산 공정을 구축했기 때문입니다.

현재 내부 판단은 "1차 생산성 이슈는 어느 정도 닫혔고, 이후는 실전 테스트를 통해 디버깅, 안정화, 비용 통제 기준을 잡아가는 단계"입니다. 이 판단이 맞는지, 지금 상태를 PoC, MVP, alpha, beta, 운영 준비 중 어디에 놓아야 하는지 AX팀 관점의 판단 기준이 필요합니다.

또한 어느 정도 예산과 기간이 정상적인 개발/안정화 범위인지, 몇 회차/몇 작품의 실전 테스트를 통과해야 다음 단계로 넘어갈 수 있는지, 계속 투자할지 축소/전환할지 판단하는 지표가 필요합니다.

현재 로드맵 가설은 글도비가 안정화 후반 단계에 가깝고, 추가 안정화/최적화 이후 상업성 레이어와 장기기억을 검증하면 1차 개발 종료 조건을 논의할 수 있다는 것입니다. 이 로드맵 판단이 타당한지, 어떤 순서와 기준으로 종료 조건을 잡아야 하는지도 검토 요청드립니다.

## 앞으로의 방향

현재는 `S0 -> S2 -> S3 -> S4` 구조입니다.

장기적으로는 S2가 새로 아크를 창작하는 역할을 줄이고, 재료/TR block을 S3가 읽을 수 있는 회차 패킷으로 정규화하는 역할로 바꾸려 합니다.

목표 방향은 아래와 같습니다.

```text
현재: S0 -> S2 -> S3 -> S4
전환: S0/TR block -> S2 정규화기 -> S3 -> S4
장기: S2 정규화기를 S3 사전 점검으로 흡수
```

또한 Stage4 통과 이후에는 독자용 최종 후보본으로 승격시키는 별도 폴리싱 관문이 필요하다고 보고 있습니다.

## 현재 가장 큰 문제

1. S4 실제 원고 단계에서 연속성 오류와 선택 후 충돌이 늦게 발견됩니다.
2. Stage4 원고 생성, 검토 에이전트 평가, 재시도 루프가 비용과 응답 지연을 키웁니다.
3. 최종 승인 원고, 회차 설계도, bible/DB, 캐시, 세션 메모리 사이의 권한 경계가 복잡합니다.
4. 캐시와 세션 메모리가 비용/지연/품질을 실제로 개선하는지 추가 검증이 필요합니다.
5. 현재 벤치마크는 15화 감독형 초안 연쇄 생성 성공이며, 완전 자동 장기 실행 검증은 별도입니다.
6. 운영/기획 관점에서 개발 로드맵, 예산, 실전 테스트 규모, 계속 투자/축소/전환 기준이 필요합니다.

## AX팀 검토 요청 사항

- S4 실제 원고 단계에서 연속성 오류와 선택 후 충돌이 어디서 생기고, 어느 검증을 더 앞단으로 옮길 수 있는지 진단
- Stage4에서 비용/응답 지연이 누적되는 API 호출 구간, 재시도 경로, 역할별 모델 라우팅, 출력 토큰 예산 조정안 검토
- GCP/Vertex AI 직결 호출에서 맥락 캐시와 세션 메모리의 비용상 이득, 최신성 검증, 무효화 기준 검토
- 문체 예시와 구조 패턴 도너(참고 패턴)를 어디까지 프롬프트에 넣고, 어디부터 검색/캐시/후처리로 분리할지 검토
- 원고 전문이나 원문 프롬프트 없이도 진단 가능한 최소 비식별 관측 패킷 설계
- 장기 실행 검증과 비용 벤치마크를 어떤 형태로 설계해야 하는지에 대한 권고
- 현재 상태를 PoC/MVP/alpha/beta/운영 준비 중 어디로 볼지, 적정 예산과 개발 기간을 어떻게 잡을지, 실전 테스트 통과 기준을 어떻게 둘지에 대한 판단 기준
- 추가 안정화/최적화, 상업성 레이어, 장기기억 검증, 1차 개발 종료 선언까지의 로드맵 판단 기준
