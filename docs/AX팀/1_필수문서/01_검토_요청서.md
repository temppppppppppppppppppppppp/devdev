# 글도비 LLM 파이프라인 검토 요청

안녕하세요.

요청 주신 글도비 LLM 파이프라인 검토 자료를 전달드립니다.

이번 자료는 아래 다섯 가지 검토 목적에 맞춰 정리했습니다.

1. LLM 파이프라인 구조 검토
2. 비용 및 응답 지연 절감 가능 지점 검토
3. 토큰 사용량 및 맥락 캐시 최적화 검토
4. GCP/Vertex AI 직결 호출, 세션 메모리, 맥락 캐시 사용 방식 검토
5. 비개발자 관점의 MVP 범위, 적정 예산, 개발 기간, 실전 테스트 기준, 계속 투자 여부 판단을 위한 의사결정 보조
6. 안정화 종료 시점, 상업성 레이어/장기기억 검증 순서, 1차 개발 종료 조건을 포함한 로드맵 의사결정 보조

검토 전제는 다음과 같습니다. 저희가 파악하는 범위에서는 LLM을 통한 장편 글쓰기, 특히 장기 연재형 웹소설 생산에 대해 널리 합의된 표준 프로세스가 아직 없습니다. 글도비는 상업 웹소설을 반복 가능한 장르 패턴, 대리만족, 캐릭터 관계, 회차별 보상 구조를 가진 패턴 구조로 보고, 이를 LLM 파이프라인으로 안정적으로 생산할 수 있는지 검증하는 프로젝트입니다.

추가로, 개발 실무자가 아닌 운영/기획 담당자 관점에서는 기술 병목 진단뿐 아니라 의사결정 기준 수립도 필요합니다. 현재 자체 판단은 "1차 생산성 이슈는 어느 정도 닫혔고, 이후는 실전 테스트 기반 디버깅/안정화 단계"입니다. 이 판단이 맞는지, 현재 상태를 PoC/MVP/alpha/beta/운영 준비 중 어디로 봐야 하는지, 어느 정도 예산과 기간을 정상 범위로 봐야 하는지 검토 부탁드립니다.

개인적인 판단으로는 현재 글도비는 안정화를 거의 끝내 가는 상태입니다. 추가 안정화/최적화 이후 상업성 레이어와 장기기억 검증을 통과하면 1차 개발 종료 단계에 들어갈 수 있다고 예상합니다. 이 로드맵 판단이 타당한지, AX팀 관점에서 종료 조건과 다음 단계 순서를 어떻게 잡아야 하는지도 함께 검토 부탁드립니다.

## 주요 검토 요청 사항

현재 가장 중점적으로 검토받고 싶은 부분은 Stage4 원고 생성 이후의 비용과 응답 지연, 그리고 다음 투자/개발 단계를 정하기 위한 판단 기준입니다.

특히 아래 항목에 대한 의견을 부탁드립니다.

- 작가 에이전트와 검토 에이전트 호출이 반복될 때 비용이 누적되는 구조
- 비싼 원고 생성 호출 전에 더 앞단으로 옮길 수 있는 검증 항목
- 역할별 모델 라우팅과 출력 토큰 예산 분리 가능성
- 맥락 캐시 사용 시 필요한 최신성 검증 기준
- 최종 승인 원고, 회차 설계도, 장기기억 계층 사이의 권한 경계
- 원고 전문 없이 비용/지연 분석에 필요한 최소 관측 데이터
- 현재 상태를 PoC, MVP, alpha, beta, 운영 준비 중 어디로 봐야 하는지
- 적정 예산, 개발 기간, 안정화 기간, 실전 테스트 규모, 계속 투자/축소/전환 기준
- 비개발자가 매주 확인할 수 있는 비용/품질/속도 대시보드 항목
- 추가 안정화/최적화, 상업성 레이어 검증, 장기기억 검증, 1차 개발 종료 선언을 어떤 순서와 기준으로 배치해야 하는지

이번 공유 자료에는 시스템 구조, 데이터 흐름, 모델/토큰/비용 관측값, 구성도, 현재 상태/장애물/지원 요청, 원본 자료 공유 가이드를 포함했습니다.

- GCP service account JSON

- 배포/운영 credential
