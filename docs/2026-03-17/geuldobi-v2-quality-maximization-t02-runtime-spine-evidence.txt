4. facts
- Fact: `main_a.py` bootstraps import path before local module imports (`main_a.py:12`, `main_a.py:44`), normalizes Windows UTF-8 stdio before runtime notices (`main_a.py:47`, `main_a.py:90`), installs Windows selector-event-loop fallback (`main_a.py:69`, `main_a.py:91`), and enables `faulthandler` to `crash_dump.log` before `SovereignApp` boot proceeds (`main_a.py:94`). `tests/test_main_a_packaged_bootstrap_contract.py` and `tests/test_encoding_boundary_contract.py` explicitly lock these boundaries.
- Fact: boot-time failure persistence is workspace-scoped, not project-scoped. `_resolve_boot_error_log_path()` uses `GEULDOBI_WORKSPACE` or `os.getcwd()` (`main_a.py:20`), `_persist_boot_failure_traceback()` writes `logs/error.log` before project-local sinks exist (`main_a.py:27`), and the `__main__` guard calls it on fatal boot failure (`main_a.py:4803`).
- Fact: `SovereignApp.boot()` order is stable and linear: genre selection -> project selection -> project-local `.env` reload -> `StudioSystem.boot_v20_project()` bind -> runtime sink retarget -> genre alignment -> HUD/Guard initialization -> `VecMemory` init -> lazy agent attach -> main menu loop (`main_a.py:1172`, `main_a.py:1194`, `main_a.py:1217`, `main_a.py:1299`, `main_a.py:1328`).
- Fact: path/root precedence is centralized in `modules/core/runtime_paths.py`: `GEULDOBI_ENGINE_ROOT` overrides engine root, `GEULDOBI_WORKSPACE` overrides workspace root, and `GEULDOBI_PROJECTS_ROOT` overrides project root (`modules/core/runtime_paths.py:9`, `modules/core/runtime_paths.py:16`, `modules/core/runtime_paths.py:23`, `modules/core/runtime_paths.py:30`). `main_a.py`, `modules/api/process_runner.py`, and `modules/api/bridge_server.py` all consume this shared contract.
- Fact: `StudioSystem.boot_v20_project()` is the primary project bootstrap substrate for the main runtime. It binds `ProjectContext`, common services, optional wuxia-only services, and leaves `guard` unbound until genre-specific runtime init (`modules/core/system.py:9`, `modules/core/system.py:22`). `check_v20_readiness()` reads Stage 0/1/2 completion directly from DB anchors (`modules/core/system.py:69`).
- Fact: `_run_main_process()` is the top-level steady-state dispatcher for the main CLI runtime and exposes keys `0/1/2/3/4/5/6/7/44/77/88/99` (`main_a.py:2461`). This is the same menu protocol replayed by the desktop/API runner.
- Fact: the main runtime uses thin Stage wrappers and extracted orchestrators. `_stage_2_arcs()` injects `Stage2Context` and delegates to `Stage2Orchestrator.stage_2_arcs_async_logic()` (`main_a.py:3185`, `modules/core/stage2_orchestrator.py:24`, `modules/core/stage2_orchestrator.py:224`). `_stage_3_batch_blueprinting()` injects `Stage3Context` and delegates to `Stage3Orchestrator.stage_3_batch_blueprinting()` (`main_a.py:3442`, `modules/core/stage3_orchestrator.py:457`, `modules/core/stage3_orchestrator.py:526`). `_stage_4_v2_chief_writer()` lazily initializes `StateTracker`, `WorldStateManager`, and `FactLedger`, injects `Stage4Context`, then delegates to `Stage4Orchestrator.stage_4_v2_chief_writer()` (`main_a.py:4043`, `modules/core/stage4_orchestrator.py:198`, `modules/core/stage4_orchestrator.py:1661`).
- Fact: the reference-only lane docs confirm lane-1, lane-2, and lane-3 semantics already landed inside Stage 4 submodules (`stage4_context_builder.py`, `stage4_interview_round.py`, `director_ensemble.py`, `chief_writer.py`). T02 therefore treats them as downstream runtime delegates, not fresh runtime-spine inventions.
- Fact: `modules/api/bridge_server.py` is the public control-plane spine for desktop/app transport. Lifespan wires `ProcessRunner`, `RiskApprovalGate`, and `PromptBroker` (`modules/api/bridge_server.py:1688`). `/run` validates request state, enforces risk approval for destructive keys, then starts the subprocess (`modules/api/bridge_server.py:1721`). `/stop` is idempotent (`modules/api/bridge_server.py:1864`). `/status` merges runner state, diagnostics, pending prompts, and recent provenance (`modules/api/bridge_server.py:1882`).

- Fact: the bridge layer persists control-plane provenance to `logs/control-plane-provenance.jsonl` and risk approvals to `logs/risk-approval-log.jsonl` (`modules/api/bridge_server.py:186`, `modules/api/risk_approval.py`). `tests/test_bridge_server_http_contract.py` and `tests/test_control_plane_approval_provenance_ssot.py` verify that `/status` can surface recent provenance summaries.
- Fact: `lite_mode` and `test_mode` implement a separate runtime spine that bypasses `main_a.py`, `bridge_server.py`, `ProcessRunner`, `ProjectContext`, and DB-backed `StudioSystem`. `main_lite.py` selects a project folder and calls `BridgeRunner(project).run()` (`lite_mode/main_lite.py:33`, `lite_mode/main_lite.py:67`, same structure in `test_mode/main_lite.py`). `run_stage.py` directly invokes `BridgeRunner.run_stage_2/3/4()` (`lite_mode/run_stage.py:33`, `lite_mode/run_stage.py:52`, `lite_mode/bridge/runner.py:1341`, `lite_mode/bridge/runner.py:1450`, `lite_mode/bridge/runner.py:1562`, mirrored in `test_mode`).

7. contradictions or uncertainty
- Fact: the public control plane exposes every public `/run` key as Mode B (`modules/api/control_plane_contract.py:19`), and bridge status/provenance tests also model Mode B-heavy behavior.
- Inference: `ProcessRunner` Mode A is now a compatibility or internal path rather than the normal public desktop/backend transport.
- Open Question: is any live caller still relying on Mode A-only behavior such as confirm padding plus auto-exit? `T08` should confirm from test/inventory coverage.
- Fact: early boot failures persist to workspace/root sinks before project selection, while later runtime sinks are project-retargeted.
- Inference: operator evidence for one failed run can split across workspace-level and project-level log roots.
- Open Question: do any operator-visible surfaces expose workspace-level `logs/error.log` or `crash_dump.log` without filesystem inspection? `T07` should confirm.
- Fact: `lite_mode` and `test_mode` duplicate a file-based Selenium runtime spine with near-identical entrypoints and bridge runners.
- Inference: runtime behavior can drift between the main `main_a.py`/FastAPI spine and the Lite/Test spine even when both are treated as usable entrypoints.
- Open Question: should `lite_mode` and `test_mode` be treated as supported runtime lanes, diagnostics harnesses, or legacy compatibility paths? `T01` and `T08` should classify.
- Fact: `ProcessRunner._build_stdin_sequence()` hard-codes `main_a` prompt order, while `prompt_classifier.py` uses regex over prompt text and option formatting.
- Inference: prompt wording drift in `main_a.py` can break remote execution without any underlying stage-logic regression.
- Open Question: beyond Stage 0 and status/provenance tests, is there an end-to-end contract test that binds live `main_a.py` prompt surfaces to `prompt_classifier.py` step taxonomy? `T08` should verify.
