# 시스템 고도화 축 딥다이브 — 마스터 오더

Date: 2026-03-17
Status: active
Authority: 이 문서가 3개 터미널 조사의 유일한 오더 소스

---

## 1. 배경

글도비 파이프라인의 기존 개선 작업(roadmap-v2, 3-lane 실행 큐)은 주로 "잘 쓰고(1), 잘 체크하고(2), 잘 수정시키고(3)" 축에 집중했다.

이번 조사는 **아직 체계적으로 다뤄지지 않은 9개 축**을 딥다이브한다.
코드 수정 없이, 정적 분석과 구조적 논증으로 각 축의 현황·갭·영향도·방향을 도출한다.

### 9개 축 목록

| # | 축 | 핵심 질문 |
|---|---|---|
| 7 | 잘 배우고 (Learning) | 성공/실패에서 뭘 가져가는가? |
| 8 | 잘 멈추고 (Stopping) | 언제 충분한지 아는가? |
| 9 | 잘 측정하고 (Measuring) | "좋다"를 어떻게 정의하는가? |
| 10 | 잘 읽고 (Comprehension) | 준 정보를 실제로 쓰는가? |
| 11 | 잘 조율하고 (Orchestration) | 에이전트들이 팀으로 작동하는가? |
| 12 | 잘 흐르고 (Resilience) | 실패 시 대안 경로가 있는가? |
| 13 | 잘 설명하고 (Explainability) | 왜 이런 결과인지 추적 가능한가? |
| 14 | 잘 다르고 (Diversity) | 반복을 피하고 변주를 만드는가? |
| 15 | 잘 맞추고 (Alignment) | 내부 기준이 외부 가치와 일치하는가? |

## 2. 터미널 할당

```
터미널 1 — 묶음 A: 시스템 성숙도
  축 7 (잘 배우고), 축 8 (잘 멈추고), 축 9 (잘 측정하고)
  공통 관점: "시스템이 자기 자신을 얼마나 이해하는가?"

터미널 2 — 묶음 B: 아키텍처 효율
  축 10 (잘 읽고), 축 11 (잘 조율하고), 축 12 (잘 흐르고)
  공통 관점: "정보와 제어가 얼마나 효율적으로 흐르는가?"

터미널 3 — 묶음 C: 출력 가치
  축 13 (잘 설명하고), 축 14 (잘 다르고), 축 15 (잘 맞추고)
  공통 관점: "산출물이 외부 가치 기준에서 얼마나 좋은가?"
```

각 터미널 내에서 3개 축은 **순차 진행** (앞 축 발견이 뒤 축에 반영되도록).
터미널 간은 **완전 병렬** (의존 없음).

## 3. 조사 프로토콜 (축당 4단계)

모든 축에 동일하게 적용.

### Step 1 — 현황 인벤토리

> "이 능력과 관련해 현재 뭐가 있는가?"

- 코드베이스에서 해당 능력의 **흔적**을 수집
- 파일명, 클래스명, 함수명, config 키, 프롬프트 섹션 수준으로 식별
- "있다"의 기준: 해당 능력을 **의도적으로 구현한** 코드/설정
- 부수적으로 해당 능력에 기여하는 것도 별도 표기 ("의도적" vs "부수적")
- 산출물: 인벤토리 테이블

### Step 2 — 갭 식별

> "있어야 하는데 없는 것은?"

- Step 1 인벤토리 대비 **이상적 시스템이라면 있을 것**을 도출
- "없다"의 증거 = "이 코드가 없다"가 아니라 "이 **경로/메커니즘/피드백 루프**가 없다"
- 갭 유형 분류:
  - **완전 부재**: 해당 능력 자체가 설계에 없음
  - **부분 구현**: 일부만 있거나, 특정 스테이지에만 있음
  - **형식적 존재**: 코드는 있으나 실효성 의문
- 산출물: 갭 목록 (유형 태그 포함)

### Step 3 — 영향도 추정

> "이 갭이 최종 산출물 품질에 얼마나 영향을 주는가?"

- 영향 경로 2가지로 분리:
  - **직접 영향**: 원고 품질, 모순, 연속성, 재미에 영향
  - **간접 영향**: 개발 속도, 디버깅 비용, 운영 부담에 영향
- 각 갭에 정성 등급:
  - `critical`: 이 갭 때문에 시스템 천장이 눌림
  - `significant`: 품질 편차/불안정의 주요 원인
  - `nice-to-have`: 있으면 좋지만 없어도 현재 수준 유지 가능
- 산출물: 영향도 매트릭스

### Step 4 — 방향 스케치

> "어떤 방향으로 메울 수 있는가?"

- **구현 제안이 아니라 접근법 후보** 수준
- 각 방향에 대해:
  - 접근법 1줄 요약
  - 난이도: 소/중/대
  - 새 LLM 호출 필요 여부
  - 기존 인프라 활용 가능 여부
  - 리스크/부작용
- "당장 할 수 있는 것"과 "설계가 필요한 것"을 명확히 분리
- 산출물: 방향 후보 테이블

## 4. 축별 조사 가이드

### 축 7: 잘 배우고 (Learning)

**핵심 질문**: 시스템이 생산 경험에서 무엇을 축적하고, 축적된 것이 다음 생산에 어떻게 반영되는가?

**탐색 대상**:
- `failure_learning.py` — FailureLearner, 17개 카테고리, generate_constraint_prompt()
- `pass_rate_monitor.py` — AttemptRecord, reject_reason 영속
- `dynamic_prompt_weighting.py` — 실패 키워드 → 가중치 매핑
- Stage 2의 failure_constraints 주입 경로
- Stage 4의 failure_constraints 부재 (roadmap-v2 테마 G 참조)
- episode_production.jsonl — 생산 로그 축적 구조
- 앙상블 낙선 후보 처리 (arc/blueprint/manuscript)

**핵심 갭 후보**:
- 성공에서 배우는 메커니즘 존재 여부
- 장르별/Arc위치별/조건별 학습 분화 여부
- 낙선 후보의 "왜 탈락했는지"가 학습에 반영되는지
- 학습 데이터의 decay/갱신 정책
- 학습이 실제로 행동을 바꾸는 증거 경로

---

### 축 8: 잘 멈추고 (Stopping)

**핵심 질문**: 시스템이 "이 정도면 충분하다" 또는 "이건 더 해도 안 된다"를 어떻게 판단하는가?

**탐색 대상**:
- retry budget 구조 (3-lane 작업 후 현재 상태)
- scoring threshold 72점 이진 판정
- PASS_WITH_FIX → local repair 계약 (lane-3 작업물)
- Director verdict 3-state (PASS/PASS_WITH_FIX/REJECT)
- 에스컬레이션 경로 (Stage 4 실패 → Stage 3/2 재설계 트리거)
- max_rounds, max_retries 등 하드코딩된 멈춤 조건
- "marginal pass" (72~75점) 감지/처리 메커니즘
- 상류 재설계 트리거 조건

**핵심 갭 후보**:
- "천장 감지" — 같은 조건으로 반복해도 개선 안 될 때 인지하는지
- "수렴 판단" — 3회차가 1회차보다 나아지고 있는지 추적하는지
- "충분히 좋다" vs "더 나아질 수 있다" 구분
- 상류(Arc/Blueprint) 재설계가 자동으로 트리거되는 조건
- 비용 대비 품질 향상의 한계효용 인식

---

### 축 9: 잘 측정하고 (Measuring)

**핵심 질문**: "좋은 원고"의 정의가 명확하고, 측정 체계가 그 정의를 충실히 반영하는가?

**탐색 대상**:
- scoring_validator.py — 6차원 점수 체계
- validation_orchestrator.py — PreLLM/Continuity/Blocking/Scoring/Advisory 5계층
- commercial_appeal 차원 정의와 측정 방법
- reader_satisfaction_guide 내용과 위치
- 장르별 임계값 차이 (68~72)
- Director의 PASS 판정 근거 구조
- negative_example_injector — 40개 부정 예시
- positive 예시 부재

**핵심 갭 후보**:
- "재미있는가"를 측정하는 차원이 있는지
- "독자가 다음 화를 클릭하는가" 관점의 메트릭
- 장르별 "좋다"의 의미 차이가 측정에 반영되는지
- 점수 차원 간 상관관계/충돌 (예: commercial_appeal vs character_consistency)
- 모순 없음 ≠ 재미있음 — 이 갭이 측정 체계에 어떻게 나타나는지
- 절대 점수 vs 상대 품질(이전 화 대비, 장르 평균 대비) 관점

---

### 축 10: 잘 읽고 (Comprehension)

**핵심 질문**: LLM에 전달된 컨텍스트가 실제로 활용되고 있는가? 정보 전달 ≠ 정보 활용.

**탐색 대상**:
- CW 프롬프트 어셈블리 경로 (chief_writer_prompts.py → stage4_context_builder.py → stage4_interview_round.py)
- 프롬프트 내 정보원 개수와 순서 (41개 정보원)
- Gemini 모델의 알려진 attention 특성 (primacy/recency/middle attrition)
- 정보 중복: 같은 사실이 여러 섹션에 다른 형태로 등장하는지
- 정보 모순: 프롬프트 내 섹션 간 충돌 가능성
- HUD/NPC/World State 정보가 실제 원고에 반영되는 비율 (간접 추정)
- Director 프롬프트의 정보 구조

**핵심 갭 후보**:
- "이 정보를 줬는데 CW가 무시했다" vs "이 정보를 안 줬다"를 사후 구분하는 메커니즘
- 프롬프트 내 우선순위 신호 (이 정보가 저 정보보다 중요하다는 표시)
- 정보 활용률 측정/피드백 루프
- 프롬프트 크기 증가에 따른 활용률 감소 곡선 인식

---

### 축 11: 잘 조율하고 (Orchestration)

**핵심 질문**: 21개 에이전트와 9개 advisory가 팀으로서 정합적으로 작동하는가?

**탐색 대상**:
- 에이전트 21개 목록 및 역할 분담 (modules/domain/agents/)
- advisory 9개 목록 및 각각의 검사 범위 (stage4_interview_round.py advisory 체인)
- Director와 advisory 간 정보 흐름
- 앙상블 내 후보 간 다양성 유도 메커니즘
- 에이전트 간 직접 통신 경로 (있다면)
- Critic, Analyst, Architect 등의 역할 경계와 중첩
- advisory 결과 충돌 시 해소 메커니즘

**핵심 갭 후보**:
- 에이전트 간 "프로토콜" 존재 여부 (단순 프롬프트 전달 외)
- advisory 9개가 모순된 조언 시 Director의 해소 능력
- 전체 에이전트 토폴로지에서의 정보 병목/단절 지점
- "같은 검사를 다른 에이전트가 중복 수행" 패턴
- 에이전트 추가/제거의 시스템 전체 영향 예측 가능성

### 축 12: 잘 흐르고 (Resilience)

**핵심 질문**: 파이프라인이 실패 시 유연하게 대응하는가, 아니면 경직된 컨베이어벨트인가?

**탐색 대상**:
- Stage 2→3→4 고정 순서의 예외 경로
- 앙상블 낙선 후보 재활용 메커니즘 (있다면)
- REJECT 후 행동: 같은 조건 재시도 vs 조건 변경
- 부분 성공 활용: 좋은 부분은 살리고 나쁜 부분만 재생성
- 에러 복구: API 실패, 타임아웃, OOM 시 복구 경로
- Stage 간 역행 (Stage 4 실패 → Stage 3 재실행) 경로
- lite_mode, test_mode 등 대체 경로

**핵심 갭 후보**:
- "2등 후보 승격" 경로 존재 여부
- 부분 재생성 (씬 단위, 구간 단위) 가능 여부
- 상류 재설계의 자동 트리거 vs 수동 트리거
- 병렬 경로 탐색 (A안 수리 + B안 재생성 동시 시도)
- graceful degradation — 자원 부족 시 품질을 점진적으로 낮추는 전략

---

### 축 13: 잘 설명하고 (Explainability)

**핵심 질문**: 산출물의 의사결정 과정을 사후에 추적하고 이해할 수 있는가?

**탐색 대상**:
- 로깅 구조: episode_production.jsonl, verdict traces, retry traces
- Director verdict의 근거 기록 범위
- CW의 창작 의도 기록 여부 (thinking 토큰, 중간 추론)
- 앙상블 선택 근거 기록 범위 (comparison_notes 240자 절삭)
- gate override 사유 기록
- advisory 개별 판단 근거 보존 범위
- Stage 간 핸드오프에서 "왜 이것을 선택했는지" 전달 여부

**핵심 갭 후보**:
- "이 원고에서 사망 NPC가 왜 살아났는지" 역추적 가능성
- CW가 "왜 이렇게 썼는지" — 블랙박스 수준
- 앙상블 비교의 근거가 240자로 절삭되는 문제
- 오류 발생 시 원인 특정까지의 경로 길이
- 운영자가 "이번 에피소드 품질이 왜 낮았는지"를 시스템에 물어볼 수 있는지

---

### 축 14: 잘 다르고 (Diversity)

**핵심 질문**: 시스템이 의도적으로 다양성을 만들어내는가, 아니면 안전한 평균으로 수렴하는가?

**탐색 대상**:
- 앙상블 3후보 생성 시 다양성 유도 메커니즘 (temperature, 프롬프트 변형, 전략 지정)
- Arc 생성의 전략 다양성 (FourPhaseArcGenerator 등)
- negative_example_injector 40개 — "이렇게 쓰지 마" 방식의 한계
- AI slop 감지/제거 메커니즘 현황
- 장르 내 화별 톤/구조 변주 메커니즘
- 같은 장르 연속 생산 시 패턴 수렴 관찰 가능성
- Director의 다양성 관련 평가 차원 (pattern_diversity)

**핵심 갭 후보**:
- "의도적 변주" — 시스템이 "이번엔 다르게 써봐"를 요청하는 메커니즘
- positive few-shot 0개 — "이렇게 쓰면 좋다"의 부재
- 앙상블 후보 간 실제 차별화 정도
- 장기 연재에서 패턴 반복 감지 → 능동적 탈출 메커니즘
- 상투적 표현 DB vs 대체 표현 제안의 비대칭

---

### 축 15: 잘 맞추고 (Alignment)

**핵심 질문**: 시스템의 내부 품질 기준이 실제 독자/시장 가치와 얼마나 일치하는가?

**탐색 대상**:
- commercial_appeal 차원의 정의와 측정 방법
- reader_satisfaction_guide 내용 분석
- scoring_validator의 6차원이 실제 독자 만족과의 상관관계
- 장르별 "성공한 원고"의 기준 차이
- 외부 피드백 수집/반영 경로 (있다면)
- 플랫폼별 요구사항 (분량, 클리프행어, 연재 주기 등) 반영 여부
- "시스템이 좋다고 한 원고" vs "사람이 좋다고 한 원고" 비교 가능성

**핵심 갭 후보**:
- 외부 신호(독자 반응, 편집자 피드백, 시장 데이터) 입력 경로 완전 부재 여부
- 모순 없음 ≠ 재미있음 — 이 간극이 시스템 어디에서 인식되는지
- "플랫폼 적합성"(분량, 포맷, 연재 구조)이 품질 기준에 포함되는지
- commercial_appeal이 실제로 무엇을 측정하는지 (추상적 레이블 vs 구체적 기준)
- 시스템 자체 평가와 인간 평가의 교정(calibration) 메커니즘

## 6. 3-Pass 감리 규칙

AGENTS.md Document Save Rule 준수.

- **Pass 1**: 사실 정확성 — 인벤토리가 실제 코드와 일치하는지, 갭 주장의 근거가 있는지
- **Pass 2**: 논리 정합성 — 갭→영향도→방향의 논리 연결이 건전한지, 비약이 없는지
- **Pass 3**: 완성도 — 누락된 관점, 불균형한 깊이, 모호한 표현 수정
- 각 Pass 후 확신도 기록
- **확신도 95% 미만이면 추가 감리 반복 후에만 저장**
- 형식적 3pass 금지 — 각 pass에서 실제로 수정/보완한 내용을 기록
