7. contradictions or uncertainty
- Inference: Stage 3's direct reread of `plot_roadmap[arc_idx]` is compensating for an incomplete Stage 2 handoff surface. Production Stage 2 code compresses block semantics for retrieval and does not clearly persist raw upstream treatment fields onto saved arcs, while Stage 3 explicitly restores them from the bible.
- Inference: Stage 2's `plan.total_budget_chars` is not a true final-context ceiling. The retrieval-plan body is capped inside `_execute_stage2_retrieval_plan`, but Stage 2 prepends work-slot and fact-ledger summaries afterward, so the final `vector_context` can exceed the plan budget without a drop ledger.
- Inference: Pack C logging for upstream intent survival is incomplete in Stage 2/3. Current observability records counts and coarse warnings, but the inspected code does not emit per-field `present -> survived -> dropped_at` provenance for treatment/block/work-focus signals.
- Inference: The Stage 3 -> Stage 2 reverse-feedback contract is fragile because it depends on a shared app-level list instead of an explicit Stage 3 context slot or durable queue/sink.
- Open Question: Does Stage 4 consume any upstream provenance beyond the saved blueprint and `_stage3_meta`, or are Stage 3 observability flags invisible to the CW prompt path? (`T04` lane)
- Open Question: Are `quality_dashboard.record_retrieval_observation(...)` records durable enough to reconstruct failed Stage 2/3 handoff cases without separate log scraping? (`T06`/`T07` lanes)
- Open Question: Is there any downstream hard cap on `semantic_context` inside `three_phase_bp.generate`, given that `Stage3Orchestrator` logs char count but does not apply a final combined cap before the call? (`T09` lane)
