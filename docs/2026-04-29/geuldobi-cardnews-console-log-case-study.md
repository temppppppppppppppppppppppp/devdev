## 카드 1. 표지

### 큰 제목

콘솔 로그로 읽는 AI 웹소설 제작 공정

### 보조 문장

글도비는 원고 생성기가 아니라, 장편 작품을 끝까지 관리하기 위한 제작 파이프라인입니다.

### 로그 증거

```text
python main_a.py
V40 SOVEREIGN COCKPIT
Multi-Genre Production Factory
```

### 사람 말 번역

이 화면은 "AI에게 글을 써달라고 하는 창"이 아니라, 작품 제작 공정에 들어가는 조종석입니다.

### 설계 이유

장편 웹소설은 한 번의 생성보다, 설정과 판단과 기록을 계속 유지하는 일이 더 어렵습니다.

### 시각 메모

큰 타이틀은 중앙. 아래에 콘솔 로그 박스를 작게 배치. 배경은 밝게, 콘솔 박스는 어두운 먹색.

## 카드 2. 대전제

### 큰 제목

LLM은 구조화된 언어를 더 안정적으로 다룹니다

### 로그 증거

```text
anchors.bible
anchors.arcs
anchors.style_guide
stage_attempts
director_selections
```

### 사람 말 번역

LLM에게 모든 것을 자유 산문으로 맡기면 장편의 설정과 상태가 흐려집니다. 그래서 글도비는 작품을 JSON, anchor, table, verdict 같은 구조로 나눠 다룹니다.

### 설계 이유

DB와 JSON은 개발자 취향이 아니라, LLM이 장편 제작을 안정적으로 다루게 하는 제작 언어입니다.

### 시각 메모

왼쪽에는 자유 산문 덩어리, 오른쪽에는 정리된 key/value 박스. 오른쪽이 더 선명해 보이게.

## 카드 3. 빈 채팅창이 아니라 제작 공정으로 시작한다

### 큰 제목

글도비는 빈 채팅창에서 시작하지 않습니다

### 로그 증거

```text
V40 GENRE SELECTOR
장르별 전문 공정 선택
투자 (Investment Fiction)
```

### 사람 말 번역

사용자는 먼저 장르를 고릅니다. 이 순간부터 시스템은 해당 장르에 맞는 제작 규칙과 판단 기준을 준비합니다.

### 설계 이유

장르는 분위기가 아니라 실패 조건입니다. 투자물은 자본, 거래, 회수 전략이 무너지면 작품이 무너집니다.

### 시각 메모

장르 선택 메뉴를 카드의 증거 이미지처럼 배치. "장르 = 판단 기준" 문구를 강조.

## 카드 4. 장르를 저장한다

### 큰 제목

선택한 장르는 프로젝트의 기억이 됩니다

### 로그 증거

```text
투자 전문 공정이 선택되었습니다.
HUD 시스템: INVESTMENT
프로젝트 장르 정보 저장: 투자
```

### 사람 말 번역

장르 선택은 일회성 UI 입력이 아닙니다. 프로젝트 DB에 저장되어 이후 Stage 0, Stage 2, Stage 3의 기준이 됩니다.

### 설계 이유

장편 제작에서는 매 단계가 같은 장르 기준을 공유해야 합니다. 그래야 뒤의 판단이 앞의 선택을 배신하지 않습니다.

### 시각 메모

작은 DB 아이콘 또는 장부 모양. "선택 -> 저장 -> 다음 단계 기준" 흐름 화살표.

## 카드 5. 원고보다 먼저 기억과 판단 장치를 켠다

### 큰 제목

글을 쓰기 전에 제작실을 먼저 켭니다

### 로그 증거

```text
Vector DB integrity check complete
Director Guard 연결 완료
Writer Guard/Genre 연결 완료
Quality Dashboard 활성화
```

### 사람 말 번역

원고 생성 전에 기억 장치, 판단자, 검증기, 품질 대시보드가 먼저 준비됩니다.

### 설계 이유

LLM이 쓴 결과를 나중에 감으로 평가하는 것이 아니라, 처음부터 추적과 심사를 전제로 제작합니다.

### 시각 메모

중앙에 "제작실 ON" 느낌. 주변에 Memory, Director, Guard, Dashboard 네 개의 작은 모듈.

## 카드 6. Stage 0은 기준선 장착이다

### 큰 제목

Stage 0은 원고 작성이 아니라 기준선 장착입니다

### 로그 증거

```text
Bible Selection
Roadmap Selection
로드맵 선택 완료
설계도(50개)와 원고 역사가 무결하게 통합되었습니다.
```

### 사람 말 번역

Bible은 세계관과 설정의 기준선이고, Roadmap은 장기 전개 설계입니다. Stage 0은 이 기준 자료를 런타임에 연결합니다.

### 설계 이유

장편은 앞에서 정한 설정이 뒤에서도 계속 효력을 가져야 합니다. 그래서 먼저 기준선을 고정합니다.

### 시각 메모

책 모양 Bible, 지도 모양 Roadmap, 중앙의 DB anchor로 연결되는 다이어그램.

## 카드 7. 주인공 설정은 서술 계약이다

### 큰 제목

주인공 설정은 취향 입력이 아니라 서술 계약입니다

### 로그 증거

```text
주인공의 세계관 출신을 선택하세요
주인공의 유형을 선택하세요
서술 시점을 선택하세요
외부 시점 삽입 정책을 선택하세요
주인공 설정이 Bible에 저장됨
```

### 사람 말 번역

회귀 여부, 회귀 시점, POV, 외부 시점 허용 정도는 이후 모든 에피소드의 정보 공개 방식을 결정합니다.

### 설계 이유

시점 규칙이 흔들리면 독자는 같은 작품을 읽고 있다고 느끼기 어렵습니다.

### 시각 메모

주인공 실루엣 주변에 POV, regression, secrecy, external POV 태그.

## 카드 8. 문체는 기준선이 된다

### 큰 제목

참조 문체를 감이 아니라 기준선으로 만듭니다

### 로그 증거

```text
문체 분석 시작: 1화, 4,247,609자
통계 분석
리듬 분석
LLM 심층 분석
Anti-AI 패턴 생성
StyleGuide DB 저장 완료
```

### 사람 말 번역

참조 원고를 그대로 흉내 내는 것이 아닙니다. 문장 리듬, 모범 문단, 피해야 할 AI식 표현을 분해해 스타일 가이드로 저장합니다.

### 설계 이유

웹소설 문체는 예쁜 문장보다 읽기 리듬이 중요합니다. 그래서 문체도 기록 가능한 제작 기준으로 바꿉니다.

### 시각 메모

텍스트 샘플이 리듬, 샘플, 금지 패턴 세 박스로 분해되는 구성.

## 카드 9. 작품마다 망가지면 안 되는 선이 다르다

### 큰 제목

작품별 금지선은 별도 Guard로 다룹니다

### 로그 증거

```text
작품가드 설정
라이브러리에서 가져오기
기본 템플릿으로 초기화
현재 프로젝트 작품가드 미리보기
```

### 사람 말 번역

이 실행에서는 작품가드 가져오기가 완료되지는 않았습니다. 하지만 시스템에는 작품별 금지선과 감각을 별도 계약으로 다루는 경로가 있습니다.

### 설계 이유

작품마다 망가지면 안 되는 선이 다릅니다. 투자물에서는 손익 구조와 자본 흐름의 설득력이 특히 중요합니다.

### 시각 메모

체크리스트 카드. "이 작품에서 절대 깨지면 안 되는 것"이라는 작은 제목.

### 설계 이유

큰 전개와 실제 회차 사이에는 중간 설계 단위가 필요합니다.

### 시각 메모

Roadmap -> Arc 1, Arc 2, Arc 3, Arc 4로 쪼개지는 흐름.

## 카드 11. 기획 문장은 바로 원고가 아니다

### 큰 제목

기획 블록을 제작 가능한 정보로 보강합니다

### 로그 증거

```text
Batch 1~4 range enrich start
Block 1 task done
Block 2 task done
Block 3 task done
Block 4 task done
Enrich Phase completed
```

### 사람 말 번역

원본 기획 블록은 그대로 원고 지시서가 되기 어렵습니다. 시스템은 각 블록을 목표, 제약, 인과, 상태 변화가 더 분명한 정보로 보강합니다.

### 설계 이유

기획과 생산 사이의 간극을 줄여야 이후 생성물이 덜 흔들립니다.

### 시각 메모

흐릿한 메모가 선명한 제작 지시서로 바뀌는 before/after.

## 카드 12. Arc 사이 인과를 용접한다

### 큰 제목

앞뒤가 끊기지 않게 연결부를 먼저 맞춥니다

### 로그 증거

```text
Arc 1-2 고유 명사 앵커링 완료
Arc 1-2 인과율 용접 완료
Arc 2-3 인과율 용접 완료

```

### 사람 말 번역

각 Arc는 따로 노는 조각이 아닙니다. 시스템은 Arc 사이의 고유명사, 사건, 상태 연결을 먼저 맞춥니다.

### 설계 이유

장편에서 흔한 실패는 앞에서 만든 사건이 뒤에서 사라지는 것입니다.

### 시각 메모

네 개의 Arc 블록 사이를 얇은 연결선으로 묶고, 연결부에 anchor 표시.

## 카드 13. 생성 전에 위험 조건을 모은다

### 큰 제목

생성은 Preflight 이후에 시작됩니다

### 로그 증거

```text
Preflight 병렬 분석 시작
arc_drive 완료
preflight 완료
constraint 완료
FourPhase-Director 대면
Pre-Director 검증 체인 시작
```

### 사람 말 번역

시스템은 먼저 요구 조건과 위험 조건을 모읍니다. 그 뒤 FourPhase 생성과 Pre-Director 검증을 거쳐 Director 심사로 보냅니다.

### 설계 이유

한 번에 생성하면 실패 원인을 알기 어렵습니다. 단계가 나뉘어야 어디서 흔들렸는지 추적할 수 있습니다.

### 시각 메모

Preflight -> FourPhase -> Pre-Director -> Director 흐름을 가로 타임라인으로.

## 카드 14. Director는 생성물을 그냥 믿지 않는다

### 큰 제목

합격은 판단과 재심사를 거쳐 기록됩니다

### 로그 증거

```text
Director PASS (score=100)
Director PASS (score=95)
Director PASS_WITH_FIX (score=90)
Director 재심사 #1 호출 중
재심사 #1: PASS (score=100)
```

### 사람 말 번역

Arc 1~3은 PASS를 받았고, Arc 4는 PASS_WITH_FIX 이후 patch와 재심사를 거쳐 최종 PASS가 되었습니다.

### 설계 이유

Python은 증거를 모으고, Director가 서사적 판단을 내립니다. 그리고 그 판단은 DB에 남습니다.

### 시각 메모

PASS 도장 3개와 PASS_WITH_FIX -> PATCH -> PASS 흐름. 너무 시험지처럼 딱딱하지 않게.

## 카드 15. 상태를 다음 Arc로 넘긴다

### 큰 제목

장편은 기억을 잃는 순간 무너집니다

### 로그 증거

```text
ConstraintDB 업데이트 완료
StateExtractor context ready
Stage2 Carryover Authority
assets=20억원
assets=23억원
portfolio_position
```

### 사람 말 번역

Arc가 통과된 뒤에는 위치, 자산, 소지품, 포트폴리오 같은 상태가 다음 Arc로 넘어갑니다.

### 설계 이유

투자물에서 자산과 포지션은 장식이 아니라 플롯의 핵심 상태입니다. 이전 결과를 잊으면 다음 이야기가 무너집니다.

### 시각 메모

Arc 1의 상태 카드가 Arc 2, Arc 3, Arc 4로 이어지는 모습. 자산 숫자를 작은 배지로 표시.

## 카드 16. Arc는 회차 설계도로 넘어간다

### 큰 제목

Arc가 끝나면 바로 원고가 아니라 Blueprint로 갑니다

### 로그 증거

```text
Stage 2: Arc Tactical Design [완료]
Stage 3: Episode Blueprinting
Arc 설계: 4개 완료
예상 총 에피소드: 17
Three Phase Blueprint Generator 시작
```

### 사람 말 번역

Arc 설계가 끝나면 시스템은 그것을 회차 단위 Blueprint로 풀기 시작합니다. 이 사례는 Stage 3 생성 시작 지점까지 보여줍니다.

### 설계 이유

큰 전술을 실제 회차 생산으로 옮기려면, 원고 전에 회차 설계도가 한 번 더 필요합니다.

### 시각 메모

Arc 4개가 17개 Episode Blueprint로 펼쳐지는 팬아웃 다이어그램.

## 카드 17. 마무리

### 큰 제목

글도비는 AI 글쓰기보다 AI 제작 공정에 가깝습니다

### 로그 증거

```text
anchors
stage_attempts
director_selections
llm_calls
cost_log
ui_events
```

### 사람 말 번역

콘솔 로그는 화면이고, DB는 기억입니다. 글도비는 생성, 판단, 기록, 상태 동기화를 분리해 장편 제작을 관리합니다.

### 설계 이유

좋은 문장을 한 번 뽑는 것보다, 긴 작품이 끝까지 같은 세계와 같은 판단 기준을 유지하게 만드는 것이 더 어렵기 때문입니다.

### 시각 메모

마지막 카드는 차분하게. "생성 / 판단 / 기록 / 상태" 네 단어를 원형 구조로 배치.

## 사용 메모

- 카드 1~5는 "왜 이런 시스템인가"를 설명하는 도입부다.

- 카드 10~16은 실제 Stage 2 -> Stage 3 공정 해설이다.
- 카드 17은 마무리 요약이다.
- 공유용으로 너무 길면 카드 9를 빼고 16장으로 줄일 수 있다.
