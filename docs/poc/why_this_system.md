# 글도비: AI 웹소설 자동 생산 시스템의 필요성과 현황

**문서 유형**: 내부 기술 검토 보고서 (POC 단계)
**작성일**: 2026-02-25
**기준 커밋**: `13a531b` (2026-02-24)
**검토 대상**: 본 시스템 도입의 구조적 타당성

---

## 초록

본 보고서는 상용 LLM 서비스 직접 사용 대비, 전용 자동화 생산 시스템 구축의 구조적 타당성을 검토한다. 비교는 처리량, 연속성 유지, 품질 일관성, 확장 비용 구조 4개 축을 기준으로 한다. 본 시스템은 현재 2,583개 테스트 케이스를 통과한 POC 상태이며, Stage 0→2→3→4의 4단계 파이프라인으로 구성된다. 본 보고서는 시스템의 실제 구현 코드를 근거로 주장을 기술하고, 예상 반론에 대한 재반론을 포함하며, 프로덕션 전환을 위한 미해결 과제를 명시한다. 본 보고서가 입증하지 못하는 것—실제 독자 반응 및 매출 기여—도 명시적으로 한계로 기재한다.

## 1. 서론

### 1.1 비교 구도의 설정

LLM을 활용한 웹소설 원고 생산 방식은 다음 세 가지로 분류할 수 있다.

- **Option A**: 상용 LLM 구독 서비스(Gemini Ultra 등)를 웹 인터페이스로 직접 사용
- **Option A'**: 상용 LLM API를 직접 호출하는 단순 자동화 스크립트 구성
- **Option B**: 웹소설 생산에 특화된 전용 파이프라인 시스템 구축 (본 시스템)

**왜 A는 비교 대상에서 탈락하는가.**

웹 인터페이스(Option A)는 Selenium 등 브라우저 자동화 도구를 통해 Python 스크립트로 부분 자동화가 가능하다. 프롬프트 입력과 응답 추출을 스크립트로 처리하는 수준의 구현은 기술적으로 어렵지 않다.

그러나 두 가지 구조적 제약이 존재한다.

첫째, **1계정 1세션 제약**이다. 웹 인터페이스는 동시에 하나의 대화 세션만 운용 가능하다. 복수 작품의 병렬 생산이나 단일 작품의 병렬 처리가 불가능하며, 처리량을 늘리려면 계정 수를 늘려야 하고 비용이 계정 수에 비례해 증가한다.

둘째, **봇 차단 정책 리스크**다. 상용 LLM 서비스의 이용약관은 일반적으로 자동화 도구를 통한 비정상적 접근을 금지한다. 브라우저 자동화를 통한 대규모 반복 접근은 서비스 측의 봇 감지 정책에 의해 계정 정지 또는 접근 차단으로 이어질 수 있다. 이 리스크는 생산 규모가 커질수록 높아지며, 사전 예고 없이 운용이 중단될 수 있다.

이 두 제약은 단발성 소량 생산에서는 감수 가능하다. 그러나 복수 작품의 지속 생산이 목표라면 처리량 상한과 운용 안정성 양쪽에서 구조적 한계가 된다. 결론적으로 "반복 자동 생산"을 전제하면 비교는 A'과 B 사이로 좁혀진다.

**A'의 정의.**

A'는 API를 직접 호출하고, 상태를 파일이나 단순 DB에 저장하며, 기본적인 재시도 로직을 갖춘 스크립트 수준의 구현이다. 구축 비용이 낮고, 유지보수가 단순하다. Option B의 타당성은 이 A'와의 차이에서 성립해야 한다.

### 1.2 비교 기준

| 기준 | 의미 |
|------|------|
| 처리량(Throughput) | 단위 시간당 생산 가능한 원고량 |
| 연속성(Continuity) | 수십~수백 화에 걸친 서사 일관성 자동 유지 |
| 품질 일관성(Quality Consistency) | 동일 기준의 반복 적용 가능성 |
| 확장 비용 구조(Scalability) | 작품 수 증가 시 추가 비용의 성격 (선형 vs 고정) |

### 1.3 이 문서가 입증하지 못하는 것

아래 항목은 본 문서의 범위 밖이다. 과장을 피하기 위해 먼저 명시한다.

- 본 시스템이 생산한 원고가 구독·스크립트 방식 대비 **독자 반응 또는 매출** 측면에서 우위에 있다는 것
- 본 시스템의 API 비용이 구독 비용보다 낮다는 것 (에피소드당 LLM 호출 횟수가 많아 단순 비교 불가)
- LLM이 LLM의 출력을 평가하는 Director 구조가 인간 편집자의 판단과 동등하거나 우위라는 것

이 세 가지는 본 시스템의 구조적 설계가 아니라 실운용 데이터가 필요한 주장이며, 현재 POC 단계에서는 근거가 없다.

## 2. Option A'의 구조적 한계

A'(단순 API 스크립트)로 달성할 수 있는 것과 그렇지 않은 것을 구분한다.

### 2.1 A'로 해결 가능한 것

- **병렬 API 호출**: `asyncio` 또는 `ThreadPoolExecutor` 적용으로 구현 가능
- **기본 상태 저장**: JSON 파일 또는 SQLite에 NPC 목록·회차 요약 저장 가능
- **단순 재시도 로직**: 실패 시 동일 프롬프트 재전송 가능
- **비용 추적**: API 응답의 `usage_metadata` 파싱으로 구현 가능

즉, A'는 처리량 문제와 단순 상태 관리 문제를 기술적으로 해결할 수 있다.

### 2.2 A'가 구조적으로 달성하기 어려운 것

**공정 간 의존성 관리**: A'는 단일 LLM 호출 또는 선형 호출 체인을 기본 구조로 한다. Arc 설계 → Blueprint 설계 → 원고 생산이라는 계층적 공정에서, 상위 공정의 출력이 하위 공정의 제약으로 변환되는 파이프라인을 구현하려면 각 단계의 출력 포맷 명세, 유효성 검증, 제약 컴파일 로직이 필요하다. 이는 스크립트 수준에서 즉흥적으로 구현할 수 있으나, 규모가 늘어날수록 일관성 유지가 어렵다.

**장기 연속성 유지의 신뢰성**: 100화 이상의 연재에서 NPC 사망 여부, 보유 아이템 상태, 세계관 팩트가 정합성을 유지하려면, 단순 상태 파일 저장을 넘어 에피소드별 상태 스냅샷, 팩트 이력, 충돌 감지 로직이 필요하다. 이 셋을 A'에 추가하는 것은 기술적으로 가능하다. 그러나 그 시점에서 A'는 이미 단순 스크립트가 아니다.

**품질 기준의 명세화**: 합격/불합격의 기준을 코드로 명시하지 않으면, 기준은 LLM 호출 시 프롬프트 안에 자연어로만 존재한다. 이 경우 동일 에피소드를 재생성하더라도 기준 적용이 확률적으로 달라진다. 기준을 코드로 명세하고 독립 에이전트가 평가하는 구조를 추가하면, 이 역시 A'가 아니게 된다.

**A'와 B의 경계에 대하여.**

A'와 B의 경계는 불연속적인 점이 아니라 연속적인 스펙트럼이다. A'에 기능을 추가할수록 B에 수렴한다. 이 문서에서 A'와 B를 구분하는 기준은 다음과 같이 정의한다.

> **A'**: 파이프라인 단계 간 인터페이스가 코드로 명세되지 않고, 품질 기준이 프롬프트 내 자연어로만 존재하며, 다회차 상태 추적이 에피소드 수에 비례한 수동 관리를 전제로 하는 구현.
>
> **B**: 파이프라인 단계 간 입출력 포맷이 명세되고, 품질 기준이 설정값 또는 코드로 고정되며, 다회차 상태가 시스템에 의해 자동 추적되는 구현.

이 정의 하에서 A'에 ① 단계 간 포맷 명세, ② 품질 기준 코드화, ③ 자동 상태 추적을 모두 추가하면 그것은 B다. 본 시스템은 이 세 요건을 갖춘 구현이다. A'가 셋 중 하나라도 갖추지 않으면 A'다.

따라서 선택의 실질적 질문은 "A'냐 B냐"가 아니라 **"세 요건 중 어디까지 필요한가"** 이며, 필요 요건의 수에 비례해 B의 정당성이 성립한다.

**요약**: A'가 해결하는 문제는 처리량이다. 본 시스템이 추가로 해결하는 문제는 **공정 구조화**, **장기 연속성의 자동화된 신뢰성**, **품질 기준의 코드화** 세 가지다. 이 중 필요한 것이 없다면 A'로 충분하고, 필요한 것이 있다면 그 항목이 B를 구축하는 근거가 된다.

## 3. 본 시스템의 구조

### 3.1 파이프라인

```
Stage 0 (세계관 설계)
  ├── 컨셉 → Bible + Treatment 생성
  ├── 역설계: 기존 원고 → Bible·StyleGuide 자동 추출
  └── StyleExtractor → StyleGuide DB 저장

Stage 2 (Arc 전술 설계)
  ├── Analyst → Arc DNA 생성
  ├── 앙상블: 3개 전략 병렬 생성 (ThreadPoolExecutor)
  └── Director → 합격/불합격/수정 지시 (자기일관성 투표 3회)

Stage 3 (Episode Blueprint 설계)
  ├── 제약 컴파일: Arc 섹션 → 에피소드 제약 추출
  ├── 앙상블: 3개 후보 병렬 생성
  └── Director → 후보 비교 선택

Stage 4 (원고 생산)
  ├── Smart Context Retrieval → 관련 컨텍스트 자동 선별
  ├── Chief Writer → 초안 작성 (StyleGuide 자동 주입)
  ├── Director → 품질 심사 (기준: 60점, 재시도 최대 4회)
  └── 통과 → DB 저장 + WorldState·FactLedger 갱신
```

### 3.2 연속성 유지 인프라

**WorldStateManager** (`modules/core/world_state.py`):
에피소드별 세계 상태를 Python 코드로 자동 갱신한다. 추적 항목: 생존/사망 NPC, 관계, 보유 아이템, 파괴된 장소, 활성 플롯. LLM 호출 없음.

**FactLedger** (`modules/core/fact_ledger.py`):
인물, 아이템, 장소, 조직의 팩트를 에피소드별로 이력 보존한다. `MAX_HISTORY_PER_ENTITY = 100`으로 200화 이상 장기 연재 대응. LLM 호출 없음.

**TruthGate** (`modules/core/truth_gate.py`):
원고 생성 후 5개 규칙을 자동 검사한다: 사망 NPC 부활, 미보유 아이템 사용, 파괴된 장소 방문, 스킬 중복 습득, 카르마 범위 이탈. 결과는 Advisory(차단이 아닌 경고) 형태다.

이 세 모듈은 A'에서 구현하려면 별도로 설계해야 하는 요소다. 구현이 불가능한 것이 아니라, 구현 비용이 존재한다는 것이 요점이다.

### 3.3 품질 기준의 코드화

Director 에이전트(`modules/domain/agents/director.py`)가 원고 품질 평가를 담당한다.

- **기준**: 기본 통과 점수 60점 (설정값으로 조정 가능)
- **자기일관성**: 동일 원고에 대해 3회 독립 평가 후 다수결 적용
- **구조**: GradingSystem, EnsembleSelector, ContinuityValidator, QualityAuditor 4개 서브모듈로 분리
- **원칙 위반 검사(V0128)**: 사망 NPC 행동 등 구조적 위반은 점수와 무관하게 별도 처리

평가 기준이 코드로 명시되어 있으므로, 작품 수·회차 수에 무관하게 동일하게 적용된다. 이것이 인간 편집자의 판단보다 우수하다는 주장은 하지 않는다. 다만 **일관성**에 한해서는 코드화된 기준이 사람보다 편차가 낮다.

### 3.4 문체 관리

StyleExtractor(`modules/core/stage0/style_extractor.py`, 777줄)가 5단계 파이프라인으로 문체를 분석한다.

1. Python 통계 분석: 문장 길이 분포, 시점, S/M/L 리듬 패턴
2. 샘플 큐레이션: 대표 문장 20~30개, 대화 10~15개, 모범 문단 5~8개 자동 추출
3. 리듬 분석: 액션씬/일상씬 밀도 측정
4. LLM 심층 분석: tone, description_style, emotion_rendering, anti_ai_패턴 생성
5. Anti-AI 패턴 코드화: 금지 표현 목록 → 원고 생성 시 자동 주입

생성된 StyleGuide는 DB에 캐싱되며, Stage 4에서 `style_guide.to_prompt()`를 통해 Chief Writer 프롬프트에 자동 포함된다. 기술적 구현은 완료 상태이며, 미결 사항은 **어떤 작품의 문체를 레퍼런스로 선정할 것인가**라는 운영 정책이다.

### 3.5 Smart Context Retrieval

ContextAdvisor(`modules/core/context_advisor.py`, 677줄)가 LLM 호출 시 관련 컨텍스트를 자동 선별한다.

- Stage별(2/3/4/Director) 검색 슬롯 자동 생성
- 검색 방식: Dense(벡터), Sparse(FTS5 키워드), Hybrid(RRF 결합) 중 설정값 기반 선택
- LLM 보강 조건: NPC 5개 이상, Arc 경계 전환, Reject 재시도, Director 저신뢰도
- 최대 컨텍스트 예산(chars) 준수로 API 비용 제어

편집자가 수동으로 관련 내용을 선별해 프롬프트에 첨부하는 작업의 자동화다.

### 3.6 오류 누적 억제 메커니즘

본 시스템에는 앙상블, 자기일관성 투표, Self-Reflection, Tree of Thoughts, Adversarial Self-Play, Chain-of-Verification 등 다수의 추론 보강 기법이 구현되어 있다(`modules/core/self_reflection.py`, `modules/core/chain_of_verification.py`, `modules/core/adversarial_self_play.py` 등). 이 기법들의 역할을 올바르게 프레이밍하는 것이 중요하다.

**이 기법들이 하지 않는 것**: 출력 품질의 절대적 향상을 보장하지 않는다. LLM이 LLM의 출력을 재평가하는 구조의 한계는 섹션 4 반론 2에서 이미 인정한 바 있다.

**이 기법들이 실제로 하는 것**: 단일 LLM 호출의 실패 확률 *p*를 낮추는 것이다.

이것이 왜 중요한가를 수식 없이 서술하면 다음과 같다. 단일 호출의 오류율이 *p*일 때, *n*개 에피소드를 연속 생산하는 과정에서 단 한 번도 오류 없이 완주할 확률은 `(1−p)^n`이다. *p* = 0.1이고 *n* = 50이면 완주 확률은 약 0.5%다. *p*를 0.05로 절반 줄이면 완주 확률은 약 7.7%로 오른다. 즉 **에피소드 수가 늘어날수록 단일 호출 오류율의 감소가 복리 효과를 낸다.**

앙상블(3개 후보 생성 → 최적 선택), Director 자기일관성 투표(3회 독립 평가 → 다수결), Self-Reflection(생성 후 자기비평 → 수정 지시)은 각각 단일 호출보다 낮은 유효 오류율을 목표로 한다. 이 오류율 감소가 장기 연재 자동화에서 갖는 가치는, 규모가 클수록 커지고 규모가 작을수록 줄어든다.

따라서 이 기법들의 타당성 여부는 목표 생산 규모에 종속된다. 10화 단발이라면 단일 호출로 충분하다. 100화 무인 연속 생산이라면 *p* 감소가 구조적으로 필요해진다.

**한계**: 실제로 각 기법이 *p*를 얼마나 줄이는지는 현재 측정된 바 없다. 구조적 논리는 성립하나, 효과의 크기는 실운용 데이터가 없으면 알 수 없다.

## 4. 예상 반론과 재반론

이 절은 합리적인 검토자가 제기할 수 있는 반론을 상정하고, 현재 근거로 답할 수 있는 범위를 명시한다.

---

**반론 1. "API를 직접 쓰면 동일한 자동화가 가능하다. Option B의 복잡성이 정당화되는가?"**

재반론: 처리량과 기본 상태 저장에 한해서는 옳다. 그러나 공정 계층화(Arc → Blueprint → 원고의 제약 전파), 장기 연속성 추적(WorldState, FactLedger), 품질 기준의 코드화(Director 에이전트)를 A' 수준에서 구현하면, 그 결과물은 구조적으로 본 시스템과 동일해진다. 차이는 이미 구현되어 있는가 아닌가다. 별도 구축 비용이 없다면 A'를 선택하는 것이 합리적이다. 구축 비용이 존재한다면, 기구현된 시스템을 채택하는 것이 합리적이다.

---

**반론 2. "Director가 LLM이고, 평가 대상도 LLM의 출력이다. 이는 순환 평가 아닌가? 60점 기준이 의미 있는 척도인가?"**

재반론: 이 반론은 타당하다. Director의 평가가 인간의 품질 판단과 상관관계가 있는지는 현재 검증된 바 없다. 60점 기준은 임계값 설정일 뿐이며, 그 자체가 품질의 절대 척도를 의미하지 않는다. 현재 Director 구조가 해결하는 것은 **절대 품질**이 아니라 **일관성**이다 — 동일 기준을 100개 에피소드에 동일하게 적용하는 것. 이 일관성이 실제 독자 반응과 연동되는지는 실운용 데이터가 필요하다. 이 문서는 그것을 입증하지 않는다.

---

**반론 3. "API 비용은 구독보다 높을 수 있다. 단일 에피소드에 6회 이상 LLM 호출이 병렬 실행된다면, 실제 운용 비용 구조는 어떻게 되는가?"**

재반론: 단순 비용 비교는 현재 이 문서의 범위 밖이다. 다만 구조적으로 명확한 것은, API 비용은 작품 수·회차 수에 비례하는 **변동 비용**이고 구독 비용은 **고정 비용**이라는 점이다. 생산량이 충분히 많으면 단가는 API 방식이 낮아질 수 있고, 생산량이 낮으면 구독이 유리하다. 이 손익분기점은 실제 운용 계획에 따라 결정되어야 하며, 본 보고서는 이를 산정할 데이터를 보유하지 않는다.

---

**반론 4. "2,583개 테스트 통과가 원고 품질을 보장하는가?"**

재반론: 보장하지 않는다. 테스트는 코드 레벨의 동작 검증이다: 모듈이 입력을 받아 올바른 형식의 출력을 반환하는지, 예외 처리가 의도대로 동작하는지, 상태 전이가 정확한지를 검증한다. 원고의 서사적 완성도, 독자 몰입도, AI 특유 패턴의 부재는 테스트로 검증되지 않는다. 이것은 본 시스템의 한계이며, 섹션 6에서 별도로 다룬다.

---

**반론 5. "10종 장르를 지원한다고 하나, 실제 검증은 투자물·무협 2종뿐이다. 나머지 8종의 Guard 로직이 실제로 유효한지 어떻게 알 수 있는가?"**

재반론: 알 수 없다. 나머지 8종은 코드 구현은 완료되었으나 실 생산 검증이 없다. Guard 로직이 해당 장르 전문가의 기준에서 유효한지는 해당 장르 원고를 실제로 생산하여 측정해야 한다. 현재는 그 데이터가 없다. 이 사실은 섹션 6.3에서 명시적으로 인정한다.

---

**반론 6. "StyleExtractor가 Anti-AI 패턴을 생성하지만, 그것이 실제로 독자가 AI 생성 텍스트를 인식하는 방식과 대응하는가? 이 기능의 효과는 측정된 바 있는가?"**

재반론: 측정된 바 없다. StyleExtractor는 LLM이 Anti-AI 패턴을 생성하고, 그 패턴을 다른 LLM에게 금지 지시로 주입하는 구조다. 이것이 실제 텍스트 수준에서 AI 특성을 줄이는지, 그리고 독자 반응에 영향을 주는지는 별도 평가가 필요하다. 현재 이 기능의 가치는 가설 수준이다.

---

**반론 7. "앙상블, ToT, Self-Reflection 등의 기법이 실제로 오류율을 줄인다는 근거가 있는가? API 호출을 3배로 늘리는 것이 오류율 감소로 정당화되는가?"**

재반론: 실증 근거가 없다는 점은 인정한다. 본 시스템에서 이 기법들의 실제 오류율 감소 효과는 측정된 바 없다. 구조적 논리 — 단일 호출보다 복수 샘플링이 분산을 줄인다는 것 — 는 성립하나, 그 효과의 크기는 알 수 없다.

다만 이 반론이 성립하려면 다음 전제가 필요하다: "단일 호출의 오류율이 장기 연재에서 무시 가능한 수준이다." 이 전제가 맞다면 기법들은 불필요한 비용이다. 이 전제가 틀리다면 기법들의 방향성은 옳다. 어느 쪽이 맞는지는 역시 실운용 데이터가 필요하다.

결론적으로 반론 7과 본 시스템의 주장 모두 현재로서는 데이터 없는 구조적 논리에 기반한다. 우열을 가릴 수 없으며, 이 문서는 그것을 인정한다.

---

## 7. 미해결 과제

### 7.1 기술 부채

`main_a.py`(3,300줄, SovereignApp 클래스 내 private 메서드 83개)와 `db_manager.py`(2,241줄, 단일 클래스에 이종 책임 84개 메서드)가 God Object 구조를 유지한다. 기능 추가 및 버그 수정 시 사이드이펙트 범위가 넓어 유지보수 비용이 증가하는 구조다.

`core/` 레이어 오케스트레이터 5건이 `domain/agents/`를 직접 import하는 레이어 역전도 존재한다. lazy import로 처리되어 런타임 영향은 제한적이나, 계층 경계가 명시적으로 위반된 상태다.

### 7.2 품질 지표 부재

현재 검증 파이프라인은 일관성(연속성 오류, NPC 상태 충돌, Blueprint 위반)을 검사한다. 이는 필요조건이지 충분조건이 아니다.

독자 반응에 직접 연동되는 지표—회차 이탈률, AI 생성 텍스트 특유의 패턴(단조로운 문장 구조, 전환 표현 반복, 진부한 감정 묘사)—에 대한 정량 지표가 부재하다. 이를 해소하려면 자사 원고의 플랫폼 매출 데이터와 원고 특성 간 상관 분석이 선행되어야 한다. 현재는 해당 데이터 수집 구조 자체가 미설계 상태다.

문체 클로닝의 운영 정책도 미결이다. 고성과 작품의 문체가 레퍼런스로 최적이라는 가정이 검증되지 않았으며, 레퍼런스 선정 기준이 없다.

### 7.3 장르 커버리지의 실증 부재

10종 장르의 Guard·HUD 시스템이 구현되어 있으나, 투자물·무협 이외 8종은 실 생산 검증 사례가 없다. Guard 로직이 해당 장르 전문가 기준에서 유효한지 확인되지 않았다.

### 7.4 전후 공정 부재

기존 블록 생산 모듈(`블록 연구소`)은 현재 deprecated 상태다. 컨셉 입력은 기획자가 수동으로 진행해야 한다. 원고 생산 이후의 공정(독자 시선 시뮬레이션, 플랫폼 최적화, 교열)도 없다. 현재 출력은 카카오/네이버 기본 포맷 변환까지다.

### 7.5 벤더 락인

본 시스템은 Google Gemini API에 단일 의존한다. `base_agent.py`의 fallback chain도 Gemini 모델 간 이동(`gemini-2.5-pro` → `gemini-2.5-flash`)에 한정되어 있다. API 가격 인상, 모델 deprecated, 서비스 정책 변경, 할당량 축소 등의 외부 변수에 대한 대응 수단이 없다. 대체 LLM 제공자(OpenAI, Anthropic 등)로 전환하려면 `base_agent.py`의 전면 수정이 필요하다. 이는 기술 리스크가 아니라 사업 연속성 리스크다.

### 7.6 에피소드당 실제 비용 미산정

`db_manager.py`에 `save_cost_record()` 및 `get_cost_summary()`가 구현되어 있어 비용 기록 구조는 존재한다. 그러나 실제 운용을 통해 에피소드 1개 생산 시 평균 API 비용이 얼마인지 산정된 수치가 없다. 섹션 4 반론 3에서 비용 손익분기점을 "범위 밖"으로 처리했지만, 이것은 프로덕션 도입 결정 전 반드시 해소되어야 할 항목이다. 기록 구조가 있으므로 실 운용 후 수치 산정은 가능하다.

### 7.7 피드백 환류 구조 부재

`FailureLearner`(`modules/core/failure_learning.py`)는 실패 패턴을 DB에 저장하고 `get_learned_constraints()`로 조회하는 구조를 갖추고 있다. 그러나 저장된 실패 패턴이 다음 생성 시 프롬프트를 자동으로 수정하는 폐쇄 루프는 구현되어 있지 않다.

더 근본적으로, 독자 반응(조회수, 이탈률, 구매 전환) → 원고 특성 분석 → 시스템 파라미터 개선이라는 외부 피드백 환류가 구조적으로 없다. 현재 시스템은 생산 이후의 결과를 내부에 반영하지 못한다.

### 7.8 저작권 및 IP 리스크 미해결

두 가지 독립적인 저작권 문제가 미해결 상태다.

첫째, **AI 생성 원고의 저작권 귀속**이다. 현행 한국 저작권법은 창작의 주체로 자연인을 전제하며, AI가 생성한 결과물에 대한 저작권 귀속 기준이 명확하지 않다. 상업 배포 시 권리 주장 가능 범위에 대한 법적 검토가 선행되어야 한다.

둘째, **문체 클로닝 시 레퍼런스 원고의 저작권**이다. StyleExtractor는 기존 원고를 분석하여 문체 패턴을 추출한다. 레퍼런스로 사용하는 원고가 타인의 저작물일 경우, 추출된 문체 패턴 및 Anti-AI 패턴이 해당 저작물의 창작적 표현을 포함하는지 여부가 불명확하다. 법적 선례가 확립되어 있지 않은 영역이다.

### 7.9 내용적 환각 무방비

TruthGate의 5개 검사는 **구조적 오류** — 사망 NPC 부활, 미보유 아이템 사용 등 — 를 감지한다. 그러나 LLM이 생성하는 **내용적 환각**, 즉 실제로 틀린 사실 정보의 서술은 감지하지 못한다.

투자물 장르에서 실재하지 않는 금융 상품, 잘못된 세율, 불가능한 수익률이 원고에 포함될 수 있다. 의학 장르에서는 잘못된 시술 방법이나 약물 용량이 서술될 수 있다. 이러한 오류는 서사적 일관성 검증으로는 감지되지 않으며, 독자가 해당 정보를 사실로 수용할 경우 별도의 문제가 된다. 현재 이 유형의 오류에 대한 전용 검증 구조가 없다.

### 7.10 출력 재현성 부재

`base_agent.py`의 LLM 호출은 `temperature=0.5`, `top_p=0.95`로 설정되어 있으며, seed 고정 기능이 없다. 동일 입력에 대해 동일 출력이 보장되지 않는다.

이는 섹션 3.3의 "품질 기준의 일관성"과 구분되어야 한다. 기준 적용의 일관성 — 동일 기준을 100개 에피소드에 동일하게 적용한다 — 은 유지된다. 그러나 동일 입력에 대해 동일 원고가 출력된다는 의미의 재현성은 없다. 이것은 결함이라기보다 LLM 생성의 구조적 특성이지만, 품질 검증 결과의 재현 불가능성은 디버깅과 회귀 테스트를 어렵게 만드는 요인이다.

## 8. 결론

### 8.1 Option B가 A'에 비해 구조적으로 우위인 조건

본 시스템이 A' 대비 정당화되는 조건은 다음과 같다.

1. **동일 기준으로 복수 작품을 지속 생산하는 구조**가 필요한 경우 — 공정 계층화와 품질 기준 코드화가 필요해진다.
2. **100화 이상 장기 연재**를 자동 관리해야 하는 경우 — WorldState·FactLedger 수준의 연속성 추적이 필요해진다.
3. **편집자 개입 없이 반복 생산**이 목표인 경우 — 재시도·자동 검증 파이프라인이 필요해진다.

이 세 조건이 모두 불필요하다면 A'로 충분하다.

### 8.2 현재 단계의 위치

본 시스템은 위 조건들에 대응하는 핵심 파이프라인을 구현한 POC다. 실증된 것과 실증되지 않은 것을 구분하면:

- **구조적으로 구현된 것**: 공정 분리, 연속성 추적, 품질 기준 코드화, 문체 관리
- **검증된 것**: 코드 동작(2,583 테스트), 투자물·무협 파이프라인 실행
- **미검증인 것**: 독자 반응 품질, 비용 손익분기, 나머지 8종 장르

프로덕션 전환을 위해서는 섹션 7의 10개 과제가 해소되어야 한다. 우선순위 기준으로 분류하면 다음과 같다.

- **실운용 전 해소 필요**: 7.1(기술 부채), 7.8(저작권·IP), 7.9(내용적 환각)
- **실운용 병행 해소**: 7.6(비용 산정), 7.7(피드백 환류) — 데이터가 없으면 해소 불가
- **중장기 과제**: 7.2(품질 지표), 7.3(장르 검증), 7.4(전후 공정), 7.5(벤더 락인)
- **구조적 수용**: 7.10(재현성) — LLM 특성상 완전 해소 불가. 영향 범위를 명확히 하는 것이 현실적 대응이다.

### 8.3 미해결 과제에도 불구하고 진행해야 하는 이유

섹션 7의 10개 과제는 실재하는 문제다. 그러나 이것이 "진행하지 말아야 한다"는 결론으로 이어지지는 않는다. 이유는 다음 네 가지다.

**첫째, 미해결 과제의 상당수가 B에 고유한 것이 아니다.**

7.5(벤더 락인), 7.8(저작권·IP), 7.9(내용적 환각)은 A'를 사용하더라도 동일하게 존재한다. LLM API를 사용하는 순간 벤더 락인은 발생하고, AI 생성 원고의 저작권 문제는 생산 방식과 무관하게 적용되며, 내용적 환각은 어떤 LLM 호출에서도 발생한다. 이 세 가지는 "B를 선택하지 말아야 할 이유"가 아니라 "LLM 기반 생산 방식 전체의 리스크"다. B를 포기해도 사라지지 않는다.

**둘째, 일부 과제는 시작하지 않으면 영구적으로 해소할 수 없다.**

7.6(비용 산정)과 7.7(피드백 환류)은 실운용 없이는 해소 불가다. 에피소드당 실제 비용은 생산해봐야 알 수 있고, 피드백 환류는 독자 반응 데이터가 쌓여야 설계할 수 있다. 이 두 과제를 해소하기 위한 유일한 방법은 제한적 범위라도 실운용을 시작하는 것이다. 시작하지 않으면 불확실성이 줄어들지 않는다.

**셋째, 전환 비용은 지금이 가장 낮다.**

A'로 운용하다가 작품 수가 누적된 뒤 B로 전환하면, 기존 작품 데이터 마이그레이션, 레거시 프로세스 재설계, 작품별 연속성 재구성이 추가 비용으로 발생한다. 현재는 POC가 완성되어 있고, 실운용 작품 수가 적으며, 기술 부채가 최소화된 시점이다. 전환 비용이 이후 어느 시점보다 낮다.

**넷째, 불확실성은 판단 유예의 근거가 아니라 범위 제한의 근거다.**

현재 미검증 항목들 — 독자 반응 품질, 비용 손익분기, 장르별 효과 — 에 대한 합리적 대응은 "전면 중단"이 아니라 "검증 가능한 범위에서의 제한적 실운용"이다. 1~2개 작품, 단일 장르, 단기 연재로 범위를 제한하면 미검증 항목들을 실데이터로 검증할 수 있다. 이것이 POC의 정의이기도 하다.

## 9. 마지막 질문: 안 간다는 선택지가 있는가

지금까지의 논의는 A, A', B를 동등한 선택지로 취급했다. 그러나 이 프레임 자체를 재검토할 필요가 있다.

LLM 시장의 변화 속도를 보면, Gemini 1.0에서 2.5까지 약 2년이 걸렸다. 같은 기간 동안 모델의 맥락 창은 수만 토큰에서 수백만 토큰으로 확장되었고, 추론 능력은 단순 텍스트 생성에서 멀티스텝 계획과 코드 실행으로 넓어졌다. 이 속도가 둔화된다는 근거는 현재 없다.

이 흐름은 콘텐츠 생산 영역에서 다음을 의미한다. 오늘 A'로 충분하다고 판단한 사람은, 6개월 뒤 경쟁자가 B 수준의 자동화로 생산량을 2배로 늘릴 때 대응 수단이 없다. 그 시점에 B를 구축하려면 A'로 누적된 작품 데이터의 마이그레이션 비용과 프로세스 재설계 비용이 추가된다. 즉, **늦게 전환할수록 전환 비용이 높아지는 구조다.**

B' — 현재 B의 미해결 과제들이 해소되고, 피드백 환류와 품질 지표가 갖춰진 상태 — 는 아직 존재하지 않는다. 그러나 LLM 시장의 변화 속도를 전제하면, B'로의 이동은 선택의 문제가 아니라 시점의 문제일 가능성이 높다.

이 문서를 검토하는 독자에게 묻는다.

> **지금 가지 않겠다는 결정은, 나중에도 가지 않겠다는 결정인가. 아니면 나중에 더 높은 비용으로 가겠다는 결정인가.**

본 시스템의 현재 상태가 불완전하다는 것은 이 문서 전체에서 인정했다. 그러나 이 질문은 완전성의 문제가 아니다. LLM 기반 콘텐츠 생산 자동화가 산업 내에서 보편화되는 시점이 온다면 — 그것이 1년 후인지 3년 후인지의 차이일 뿐 — 그 시점에 축적된 운용 경험과 데이터를 가진 쪽과 그렇지 않은 쪽의 격차는 따라잡기 어렵다.
