## PASS 1 — 생산기지 감리 (운영자가 실제로 돌릴 수 있는가)

### F-01. 운영자 SOP 부재 — 문서가 설계도이지 작업 매뉴얼이 아님 ❌

**현상:**
기획안은 폴더 구조(§1) + 파이프라인 흐름도(§2) + 설계 결정(§3) + 코드 스니펫(§5) 으로 구성됨.

**빠진 것:**
"작품 1개를 처음부터 출고까지 생산하려면 지금 무엇을 실행하는가?"에 대한 **스텝별 실행 가이드**가 없음.

| 질문 | 기획안 답변 |
|------|------------|
| 1. 어떤 파일을 어떤 순서로 열어야 하나? | §2에 흐름도만 있고, 실행 명령 없음 |
| 2. LLM에게 어떤 프롬프트를 주나? | 없음 — "하네스 읽기" 후 어떻게? |
| 3. Python 스크립트를 어떻게 실행하나? | 없음 — `python scripts/build_*.py`? args? |
| 4. 배치 실패 시 어떻게 하나? | "같은 배치 재작업"이라고만 — 어떤 파일을 고쳐서 어디에? |
| 5. 완료 판정을 누가 어떻게 하나? | "출고 게이트 체크리스트" 언급만, 항목 없음 |

**왜 이게 중요한가:**
- 기획안 = 건축 설계도. 생산기지 = 작업 표준서(SOP).
- 설계도만 있고 SOP가 없으면 → 매번 "이거 어떻게 하지?" → 하네스 문서 4개를 처음부터 읽어야 함
- 기획안의 핵심 목표 "뭘 먼저 해야 하지? 반복 제거" (§0)가 달성 안 됨

**심각도:** **P0 — 생산기지의 존재 이유 불충족**

### F-02. 투입 자원 명세 부재 — 공장에 원재료 목록이 없음 ❌

**현상:**
§2 "입력: 작품 컨셉 + 장르 선택"이 전부.

**빠진 것:**

| 투입 자원 | 어디에? | 형식? | 최소 요건? |
|-----------|--------|-------|-----------|
| 작품 컨셉 | ? | 텍스트? JSON? | 몇 줄? 뭘 포함? |
| 소재 뱅크 쿼리 결과 | material_bank.db | SQL 결과? JSON? | 최소 몇 건? 어떤 테이블? |
| 역사 이벤트 목록 | ? | ? | 대체역사면 필수? 투자물이면 몇 건? |
| NPC 원형 | ? | ? | 최소 몇 명? opponent 포함? |
| 장르 가드 설정 | genre_guards/*.py | Python 클래스 | 이미 존재해야? 없으면? |
| API 키 (Gemini) | ? | 환경변수? | 어떤 모델? 비용? |

**왜 이게 중요한가:**
- 공장에 원재료 입고 목록이 없으면 → 생산 중간에 "이것도 필요했어?" 발생
- 특히 소재 뱅크 조회(§B)가 "키워드/섹터/연도 검색"이라고만 되어 있고, **어떤 쿼리를 어떤 순서로 실행해야 Phase 0에 충분한 소재가 모이는지** 없음

**심각도:** **P0 — 투입 명세 없는 생산 라인**

### F-03. 처리 시간·병목 분석 부재 — 공장 가동률을 모름 ⚠️

**현상:**
기획안에 시간 관련 언급이 하나도 없음.

**실측 기반 추정 (기존 배치 이력에서):**

| 공정 | 추정 시간 | 병목 |
|------|----------|------|
| §A 하네스 읽기 | ~30분 (4개 문서 2,500줄+) | 사람 읽기 속도 |
| §B 소재 조회 | ~1시간 | 쿼리 설계 + 결과 선별 |
| §C Phase 0 | ~2시간 | LLM 1회 + 사람 검토 |
| §D TR 생산 70블록 | **~24배치 × 30분 = 12시간+** | **LLM 생성 + 검증 루프** |
| §E TR 병합 | ~15분 | Python 자동 |
| §F BI 생산 | ~2시간 | LLM + 동기화 검증 |
| §G 교차 감사 | ~2시간 | 5-pass + 3-pass |
| §H 출고 | ~15분 | 체크리스트 확인 |
| **합계** | **~20시간** | **§D가 전체의 60%** |

**왜 이게 중요한가:**
- §D가 병목 → 배치 크기·LLM 모델·validate 루프 최적화가 핵심
- 이 분석 없이 폴더만 정리하면 → 생산 속도 개선 0
- "1턴 1배치" 규칙의 비용을 운영자가 인지해야 함

**심각도:** **P1 — 운영 계획 불가**

### F-04. 품질 메트릭 단일 의존 — validate_v3만으로 출고 판정 ⚠️

**현상:**
기획안의 품질 판정 경로: validate_v3 → P0 위반 0건 → PASS → 출고.

**빠진 관점:**

| 품질 축 | validate_v3가 잡는가? | 예시 |
|---------|---------------------|------|
| 구조적 결함 (스키마) | ✅ | 필수 필드 누락, 타입 오류 |
| 반복 패턴 (R27~R33) | ✅ | opponent 독점, solution 템플릿 |
| **서사 품질** | ❌ | 뻔한 전개, 감정선 부재, 긴장감 없음 |
| **장르 정합성** | ❌ | 투자물인데 투자 논리 없음 |
| **수치 현실성** | ❌ | 1억 → 1조를 3블록 만에 |
| **NPC 일관성** | ❌ | 같은 NPC가 2번 죽음 |
| **시간축 정합** | ❌ | 1년 안에 30년 분량 이벤트 |

**왜 이게 중요한가:**
- validate_v3 PASS한 TR이 런타임에서 REJECT당하면 → 전처리 전체가 무의미
- 런타임의 Director + Advisory 체인(14개)이 잡는 결함을 전처리에서 사전 차단 못 하면 → Stage 2~4에서 고통
- 최소한 **장르 가드 사전 적용 + 수치 교차검증** 정도는 전처리에서 해야 함

**심각도:** **P1 — 단일 품질 게이트 위험**

### F-05. 동시 생산 설계 부재 — 1공장 1라인 ⚠️

**현상:**
기획안은 1개 작품의 생산 흐름만 기술. 복수 작품 동시 생산 시 고려사항 없음.

**실제 현황:**
- `작품별/` 디렉토리에 02, 05, 08 등 복수 작품 존재
- 소재 뱅크(material_bank.db)는 공유 자원
- LLM API 콜은 rate limit 공유

**빠진 것:**
- 작품 A의 §D 진행 중에 작품 B의 §C를 동시 진행 가능한가?
- batch_log가 작품별로 분리되니 충돌은 없겠으나, LLM API는?
- progress.json이 작품별이므로 상태 추적은 가능한가?

**심각도:** **P2 — 향후 확장 시 이슈**

## PASS 2 — 완성도 보강 (F-01, F-02 해소)

### 보강 A: 운영자 SOP — 신규 작품 1개 생산 전체 절차

```
┌─────────────────────────────────────────────────────────┐
│  신규 작품 생산 SOP (Standard Operating Procedure)        │
│  예상 소요: ~20시간 (§D가 60%)                            │
│  투입: 작품 컨셉 1매 + material_bank.db 접근 + LLM API    │
│  산출: TR 70블록 JSON + BI JSON → treatments/ + bible/    │
└─────────────────────────────────────────────────────────┘

■ STEP 0. 작업 공간 생성 (~5분)
  ├── 전처리_ssot/작품별/_template/ 복사 → 작품별/NN_work_id/
  ├── work_config.yaml 작성:
  │     work_id: "fallen_prince_buys_joseon"
  │     title: "몰락한 왕자가 조선을 사다"
  │     genre: alt_history
  │     profile: alt_history  # SSOT 통합오더 §0A 프로파일명
  │     total_blocks: 70
  │     protagonist: {name: "이선", origin: "환생"}
  └── progress.json 초기화: {"current_step": "STEP_1", "blocks_done": 0}

■ STEP 1. 하네스 읽기 (~30분)
  ├── docs/blockguide/SSOT_blockguide-integrated-order.md 통독
  │     → 현재 작품의 단계 판정 (신규 → Planning)
  ├── docs/blockguide/treatment-planning-harness.md 통독
  │     → 11대 원칙(A~K) + 18단계 설계 순서 + 25항 출구 게이트
  └── 장르 프로파일 확인:
        → modules/core/stage0/preset_registry.py에서 해당 장르 필드 확인
        → modules/core/genre_schema_builder.py에서 genre_ext 구조 확인

■ STEP 2. 소재 조회 (~1시간)
  ├── 실행: python test_material/query_material_bank.py
  │     → 키워드: 장르 핵심어 (예: "조선", "왕위", "파벌")
  │     → 섹터: 해당 도메인
  │     → 연도: 배경 시대
  ├── 수집 최소 기준:
  │     역사 이벤트: 10건+ (각 아크 1~2건 배정용)
  │     NPC 원형: 8명+ (opponent 최소 8명)
  │     위기 시나리오: 5건+ (아크 전환 위기용)
  └── 출력: 작품별/NN/소재_수집.json (자유 형식, Phase 0 입력용)

■ STEP 3. Phase 0 설계 (~2시간) ★ P-1, P-2 핵심 ★
  ├── 하네스: treatment-planning-harness.md 18단계 순서 실행
  ├── 필수 산출물:
  │     ├── opponent_allocation_matrix (P-1)
  │     │     7아크 × 최소 2~3명/아크 = 최소 8명 고유 opponent
  │     │     동일 opponent 상한: 전체의 25% (70블록 중 17블록)
  │     ├── weakness_predesign (P-2)
  │     │     opponent별 최소 2종 weakness × 8명 = 16종+
  │     │     아크 내 중복 금지
  │     ├── sector_roadmap
  │     │     70블록 × business_sector 배정
  │     │     아크당 최소 2섹터
  │     ├── npc_timeline
  │     │     NPC별 등장 블록 + 역할 변화
  │     └── foreshadow_map
  │           복선 10건+ × 회수 블록 지정
  ├── LLM 실행: Phase 0 프롬프트 1회 (하네스 §2.1~2.18 순서)
  ├── 사람 검토: opponent 배치 균등성 + weakness 다양성 수작업 확인
  └── 출력: 작품별/NN/phase0_design.json

■ STEP 4. TR 생산 — 배치 순차 (~12시간, 전체의 60%)
  ├── 배치 크기: 3블록 (Arc 전환 시 강제)
  ├── 배치 1개 사이클 (~30분):
  │     ┌─ 4a. 패턴 피드백 생성 (P-3)
  │     │    blocks_so_far = 이전 배치 전부 로드
  │     │    build_pattern_feedback(blocks_so_far) 실행
  │     │    opponent 빈도 + weakness 종류 + solution 말미 + sector 분포
  │     │
  │     ├─ 4b. 프롬프트 조립
  │     │    phase0_design.json (전체)
  │     │    + 패턴 피드백 (4a 결과)
  │     │    + "Block X~Y 생산" 지시
  │     │    + treatment-production-harness-v2.md §3 규칙 인용
  │     │
  │     ├─ 4c. LLM 생성 → batch_NNN_candidate.json
  │     │
  │     ├─ 4d. Python auto-fix
  │     │    python scripts/tr_batch_harness.py --input batch_NNN_candidate.json
  │     │    → batch_NNN_fixed.json
  │     │
  │     ├─ 4e. validate_v3 검사
  │     │    python tools2/apply_v3.py batch_NNN_fixed.json
  │     │    → P0 위반 0건이면 PASS
  │     │    → P0 위반 있으면 → 4a로 복귀 (동일 배치 재생산)
  │     │
  │     └─ 4f. 배치 로그 기록
  │          작품별/NN/batch_log/batch_NNN_candidate.json
  │          작품별/NN/batch_log/batch_NNN_fixed.json
  │          작품별/NN/batch_log/batch_NNN_audit.md (검증 결과)
  │
  ├── Arc 전환 규칙 (P-5):
  │     Arc N 마지막 배치 → Arc N+1 첫 배치는 반드시 3블록 안전 모드
  │     배치 크기 5블록 승격은 Arc 내 3배치 연속 PASS 후
  │
  ├── 실패 처리:
  │     P0 위반 → 같은 블록 범위로 재생산 (candidate 번호 증가)
  │     3연속 실패 → Phase 0 해당 Arc 섹션 재설계 검토
  │
  └── progress.json 업데이트: {"current_step": "STEP_4", "blocks_done": N}

■ STEP 5. TR 병합 + 전체 검증 (~30분)
  ├── batch_001~NNN의 fixed.json 병합 → tr_block_070_draft.json (임시)
  ├── 전체 validate_v3 재실행 (배치별 PASS여도 전체 병합 시 새 패턴 발생 가능)
  ├── P0 위반 발생 시: 해당 블록이 속한 배치로 돌아가 STEP 4 재실행
  └── 출력: 작품별/NN/tr_block_070_draft.json

■ STEP 6. BI 생산 (~2시간)
  ├── 하네스: bi-production-harness-v1.md 5-Phase 실행
  │     Phase 0: Source fixation (TR + Phase0 UTF-8 파싱 확인)
  │     Phase 1: Skeleton (ProjectData/HUD/WorldState 코어)
  │     Phase 2: Deterministic sync (plot_roadmap, npc_timeline TR에서 복사)
  │     Phase 3: UTF-8 save + corruption detection
```
