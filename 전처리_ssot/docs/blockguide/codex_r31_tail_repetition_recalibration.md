> 적용 대상: `treatment-production-harness-v2.md`, `TF-BH1_block_harness_reinforcement.md`, `codex_chaebol_allowance_zero_failed_vs_retry_comparison_order.md`

## 0. 문제 잠금

현행 `R31`은 아래처럼 읽힌다.

- `solution` 말미 20자가 5블록 이상 동일하면 `P0`

이 규칙은 실패 TR을 잡는 데는 성공하지만, 현재 골든 TR도 같이 걸린다.

즉:

- 실패 TR을 잡는 기능은 있음
- 그러나 **좋은 재시도본까지 P0로 날려 버리는 true-fail**이 발생함

따라서 `R31`은 유지가 아니라 **재조정** 대상이다.

## 1. 직접 실측

실측 대상:

- 실패 TR: `treatments/02_chaebol_allowance_zero_tr_block_070_draft.json`
- 개선 TR: `treatments/02_chaebol_allowance_zero_tr_block_070_draft.json`

### 1.1 tail 반복 통계

| 항목 | 실패 TR | 개선 TR |
| ---- | ------- | ------- |
| `tail-10` 고유값 | 1종 | 8종 |
| `tail-15` 고유값 | 1종 | 8종 |
| `tail-20` 고유값 | 27종 | 8종 |
| `tail-20` 최다 반복 | 14블록 | 57블록 |
| 대표 tail | `...자기 쪽으로 당긴다.` | `...반복 수익과 통제권으로 재정의한다.` |

해석:

- 실패 TR은 **짧은 tail**이 완전히 동일하다.
- 개선 TR은 짧은 tail이 8종으로 늘었지만, 특정 종결 문장이 `57블록` 반복된다.
- 따라서 `tail-20 >= 5 -> P0`는 실패보다 개선 TR을 더 세게 때릴 수 있다.

### 1.2 solution 구조 통계

| 항목 | 실패 TR | 개선 TR |
| ---- | ------- | ------- |
| 평균 solution 길이 | 86.50자 | 265.01자 |
| 문장 수 분포 | `1문장` 70/70 | `4문장` 67/70, `3문장` 3/70 |
| 반복 특징 | 한 문장 템플릿 + 동일 결말 | 다문장 전개 + 반복 결말 |

핵심 차이:

- 실패 TR은 `solution` 전체가 사실상 **한 문장 템플릿**
- 개선 TR은 결말 문장은 반복되지만, 앞단의 전개와 실행 문장은 더 길고 다층적

즉 `tail` 단독 지표는 구조 품질을 충분히 설명하지 못한다.

## 2. 결론

### 2.1 현행 R31 판정

| 항목 | 판정 |
| ---- | ---- |
| 실패 TR 탐지 | 성공 |
| 개선 TR 허용 | 실패 |
| 실무 적용성 | 낮음 |

결론:

- 현행 `R31`은 실패 탐지 규칙으로는 작동한다.
- 하지만 **출고 게이트 규칙**으로는 과잉이다.

### 2.2 단순 완화안 기각

아래 단순 완화안은 모두 기각한다.

1. `tail-20 >= 10`으로만 완화
   - 실패 TR `14`라 계속 걸림
   - 개선 TR `57`이라 역시 걸림

2. `tail-20 >= 30`으로만 완화
   - 실패 TR은 통과해 버릴 수 있음
   - 개선 TR만 계속 걸릴 수 있음

3. `tail-15`만 사용
   - 실패 TR도 강하게 걸리지만
   - 개선 TR도 여전히 짧은 결말 반복으로 과잉 검출될 가능성이 큼

따라서 **tail 길이 임계값만 만지는 방식은 해법이 아니다.**

## 3. 재조정 원칙

`R31`은 한 개 규칙이 아니라 `Hard FAIL`과 `Cadence Warning`으로 분리한다.

### 3.1 R31-Hard (`P0`)

아래 3개를 동시에 만족하면 `P0`로 본다.

1. `tail-20 top repetition >= 10`
2. `1문장 solution 비율 >= 80%`
3. `avg_solution_chars < 140`

적용 결과:

- 실패 TR: `14 / 100% / 86.50` -> `P0`
- 개선 TR: `57 / 0% / 265.01` -> `P0 아님`

핵심 의미:

- **짧고, 한 문장이고, 같은 결말이 반복되는 solution 루프**만 hard fail로 잡는다.

### 3.2 R31-Soft (`P1`)

아래 중 하나면 `P1 경고`로 본다.

1. `tail-20 top repetition >= 20`
2. 특정 종결 문장이 전체의 `40%` 이상을 차지

단, 아래를 함께 적는다.

- 다문장 solution이 유지되면 이는 `구조 붕괴`가 아니라 `cadence 반복` 경고다.
- 즉, `P1`은 보강 대상이지 출고 차단 자동사유가 아니다.

적용 결과:

- 실패 TR: `P0`가 이미 떠서 `P1` 의미 없음
- 개선 TR: `57/70 = 81.4%` -> `P1 경고`

### 3.3 R31-Companion Rule

`R31`은 단독으로 `P0`를 만들기보다 아래 규칙과 함께 읽는다.

- `R27` 밀도
- `R30` weakness 다양성
- `R29` opponent 다양성

운영 원칙:

- `R31-Hard`는 단독 `P0` 가능
- `R31-Soft`는 단독 `P0` 금지
- `R31-Soft + R27 저밀도`는 `P0 승격 후보`

## 4. 문서 반영안

### 4.1 `treatment-production-harness-v2.md`

현행 `R31`을 아래처럼 바꾼다.

```text
31. solution 구조 템플릿 반복 금지 (교정판)
    - R31-Hard (P0):
      아래 3개를 모두 만족하면 P0 위반.
      1) solution 말미 20자 최다 반복 >= 10블록
      2) 1문장 solution 비율 >= 80%
      3) avg_solution_chars < 140

    - R31-Soft (P1):
      아래 중 하나면 P1 경고.
      1) solution 말미 20자 최다 반복 >= 20블록
      2) 특정 종결 문장 점유율 >= 40%

    - 해석:
      같은 결말 cadence 자체는 경고 사유가 될 수 있지만,
      다문장 전개와 충분한 밀도가 유지되면 자동 P0는 아니다.
```

### 4.2 `TF-BH1_block_harness_reinforcement.md`

아래 내용을 추가한다.

- 현행 `R31`은 실패 TR 탐지에는 성공하지만 현재 개선 TR을 true-fail 시킨다.
- 따라서 `tail-20 >= 5 -> P0`를 정본 규칙으로 확정하지 않는다.
- `Hard FAIL`과 `Cadence Warning` 분리안을 채택한다.

### 4.3 `codex_chaebol_allowance_zero_failed_vs_retry_comparison_order.md`

비교 오더에서는 아래처럼 적는다.

- 현재 골든 TR의 `R31` FAIL은 비교 패배가 아니라 **하네스 규칙 재조정 이슈**
- 비교 결론은 유지하되, `R31` false-fail 여부를 문서 하단 오픈 이슈로 분리

## 5. 실행 판정

### 5.1 즉시 채택할 것

- `R31-Hard / R31-Soft` 분리
- `tail` 단독 `P0` 폐기
- 다문장/밀도 정보를 같이 보는 구조 채택

### 5.2 보류할 것

- 전체 solution 골격 정규화 코드를 바로 정본 규칙으로 승격하는 것
- corpora 전체 재측정 없이 다른 작품군에 동일 임계값을 확정하는 것

이 문서는 **`chaebol_allowance_zero` 실측 기반 1차 재조정안**으로 본다.

## 6. 최종 권고

최종 권고는 아래와 같다.

1. 비교 결론은 유지한다.
   - 재시도본은 실패본보다 명백히 낫다.
2. `R31`은 현행 상태로 정본화하지 않는다.
   - 현재 개선 TR을 true-fail 시키기 때문이다.
3. 하네스 반영은 `Hard FAIL / Soft Warning` 이원화로 간다.
   - 실패 TR은 계속 잡고
   - 개선 TR은 `P1 경고`로 내려 보강 대상으로 다루는 방식이 가장 실무적이다.
