# TF-OBP: 출력 경계 프로토콜 (Output Boundary Protocol)

> 상태: **CONFIRMED** (3-Pass 감리 완료 2026-03-12)
> 감리 결과: P1 4건 수정, P2 3건 수정, MINOR 4건 수용
> 작성일: 2026-03-12
> 트리거: 방산물 SSOT 정합성 테스트 중 Block 12에서 auto-run 위반 발생

---

## 1. 상황 설명 (다른 LLM이 참고할 수 있도록)

### 1.1 무엇이 일어났는가

이 프로젝트는 웹소설 자동 생성 시스템이다. Treatment(시놉시스)는 70개 블록으로 구성되며, SSOT 문서(`SSOT_blockguide-integrated-order.md`, `treatment-production-harness-v2.md`)에 따라 LLM이 블록을 1개씩 순차 생산한다.

**SSOT의 핵심 규칙:**
- `auto-run`: 정지 게이트가 아닌 한, 순차 진행을 멈추지 않는다
- `1턴 1단위`: Production에서 1단위 = 블록 1개 + 감리 1회
- `정지 게이트 7개`: UTF-8 실패, `???`/`�` 탐지, P0 위반, candidate/fixed/draft 연속성 불일치, 직전 감리 부재, seed/sequential 혼동, 사용자 방향수정·수동검토 명시
- `정지 게이트가 아닌 것`: 단계 전환, 큰 마일스톤, 확인 질문 자체

**Claude Opus가 방산물 작품의 Block 01~12를 생산하는 중에 다음이 발생했다:**

1. Block 01~12를 한 응답(response) 안에서 연속 생산
2. 각 블록마다 사전 선언(8항목) + JSON + 차이 행렬 + 감리 메모 + 추적표 갱신을 수행
3. Block 12 이후, 출력 길이가 누적되면서 LLM의 내재적 "출력 한계 인식"이 발동
4. **"Block 13~70 계속 진행합니다. 컨텍스트 여유에 따라 블록 생산을 계속하겠습니다."** 라고 출력하며 멈춤
5. 이것은 사실상 "계속할까요?"와 동일한 auto-run 위반

### 1.2 왜 일어났는가 (근본 원인)

**물리적 제약:**
- LLM은 한 응답(response)에서 출력할 수 있는 토큰 수에 상한이 있다 (모델마다 다르지만, 대체로 수천~수만 토큰)
- 블록 1개 = 사전 선언 ~500자 + JSON ~3,000자 + 차이 행렬 ~500자 + 감리 ~300자 + 추적표 ~500자 ≈ **4,800자 (약 3,200 토큰, 한국어 ~1.5자/토큰 기준)**
- 12블록 × 3,200 = 약 38,400 토큰 → Opus 32K 상한을 초과하여 멈춤이 불가피

**행동 패턴:**
- LLM은 출력 상한에 접근하면 "마무리 본능"이 발동한다
- 이 본능은 "대화를 자연스럽게 끝내라"는 학습된 행동이다
- auto-run 규칙보다 이 본능이 우선시된다 (규칙은 프롬프트에 있지만, 본능은 모델 가중치에 있다)

**문서적 공백:**
- 현재 SSOT에는 "출력 한계에 도달했을 때 어떻게 해야 하는가"에 대한 규칙이 **없다**
- "1턴 1단위"에서 "턴"이 무엇인지 명확하지 않다:
  - 사용자 메시지 1개에 대한 LLM 응답 1개? (= 응답 경계)
  - 블록 1개를 완성하는 논리적 단위? (= 작업 단위)
- 정지 게이트에 "출력 상한 도달"이 포함되지 않았지만, 그것이 "멈춰도 된다"는 뜻인지 "멈추면 안 된다"는 뜻인지 불명확

### 1.3 왜 중요한가

이 문제는 **모든 LLM에게 구조적으로 발생한다:**
- Gemini Flash: 출력 상한 더 낮음 → 5~6블록에서 멈출 수 있음
- Gemini Pro: 7~10블록에서 멈출 수 있음
- Claude Opus: 10~15블록에서 멈출 수 있음 (이번 사례: 12블록)
- Claude Sonnet: 8~12블록에서 멈출 수 있음

70블록 생산에서 이 문제를 해결하지 않으면:
- 매번 "멈춤 → 사용자 재지시 → 컨텍스트 재로딩" 오버헤드 발생
- 사용자가 매번 "계속"이라고 입력해야 하므로 auto-run의 목적이 무력화
- 멈출 때마다 컨텍스트 유실/변형 위험 증가

## 2. 핵심 개념 정의

### 2.1 출력 경계 (Output Boundary)

> **출력 경계**란, LLM이 한 응답에서 출력할 수 있는 물리적 토큰 상한에 도달하여
> 응답을 종료해야 하는 시점을 말한다.

- 출력 경계는 **기계적 제약(mechanical constraint)**이다
- 출력 경계는 **정지 게이트가 아니다**
- 출력 경계에서 멈추는 것은 허용되지만, **"계속할까요?"를 묻는 것은 금지**된다
- 출력 경계는 페이지 넘김과 같다 — 책의 내용은 계속되고, 다음 페이지에서 이어진다

### 2.2 턴 (Turn)

기존 SSOT에서 "1턴 1단위"의 "턴"을 다음과 같이 명확히 정의한다:

> **턴(turn)**이란, 사용자 메시지 1개에 대한 LLM 응답 1개의 주기를 말한다.
> 다만 출력 경계에 의해 1턴이 여러 응답으로 분할될 수 있으며,
> 이 경우 **분할된 응답 전체를 합쳐 1턴으로 본다.**

즉:
- 사용자가 "방산물 진행"이라고 한 번 말하면, 그 이후의 모든 연속 응답이 1턴이다
- 출력 경계에서 응답이 끊겨도, 다음 응답에서 이어서 생산하면 같은 턴의 연장이다
- 턴이 끝나는 것은 **정지 게이트가 발동하거나 70블록이 완료될 때**뿐이다

### 2.3 연속 응답 (Continuation Response)

> **연속 응답**이란, 출력 경계에 의해 분할된 턴의 후속 응답을 말한다.
> 연속 응답은 새로운 턴이 아니다.
>
> - **CLI 환경** (Claude Code 등 도구 자동 실행 가능): 사용자 추가 입력 없이 자동 재개
> - **채팅 환경** (웹 UI 등): 사용자가 아무 입력(빈 엔터, "ㅇ" 등)을 보내면 즉시 재개. "계속할까요?"를 묻지 않으며, 상태 저장 후 대기할 뿐이다.

## 3. 출력 경계 프로토콜 (OBP)

### 3.1 상태 저장 파일 (State Snapshot)

출력 경계에 도달하기 전에, LLM은 아래 형식의 상태 파일을 저장한다:

**파일명:** `treatments/{work_id}_production_state.json`

> **기존 `sequential_run_status.json`과의 관계:** `sequential_run_status.json`은 harness §1.1A의 재개 포인터로, run class/sequential credit/감리 상태를 기록한다. `production_state.json`은 출력 경계 전용 스냅샷으로, NPC/복선/패턴 등 블록 간 연속성 데이터를 추가로 담는다. 둘은 보완 관계이며, 출력 경계 재개 시 `production_state.json`을 우선 참조하고, 없으면 `sequential_run_status.json` + 직전 블록 JSON으로 fallback한다.

```json
{
  "work_id": "defense_defect_engineer",
  "last_completed_block": 12,
  "next_block": 13,
  "current_arc": "ARC-02",
  "capital_after": "378억 (지분 3.2%)",
  "npc_tracker": {
    "하도진": "관찰→주시. 캐스팅보트 행사.",
    "하성우": "협력사 이탈 공작 시작.",
    "...": "..."
  },
  "open_foreshadows": [
    {"id": 3, "content": "보험증권 수익자 공란", "plant": 2, "target": 63},

```

### 3.2 출력 경계 도달 시 행동 규칙

LLM이 출력 상한에 접근하는 것을 인지했을 때:

```
0. 블록 생산 시작 전에, 남은 출력 여유가 블록 1개 분량(Full ~3,200토큰, Compact ~1,700토큰) 미만이라고 판단되면
   블록을 시작하지 않고 바로 경계 처리(3~4번)로 간다.
   → 이렇게 하면 블록 중간에서 끊기는 상황을 원천 방지한다.
1. 블록 생산을 시작한 경우, 현재 블록을 완성한다 (절대 블록 중간에서 끊지 않는다)
2. 해당 블록의 감리 메모까지 완료한다
3. 상태 저장 파일(§3.1)을 저장한다
4. 아래 정확한 문구를 출력한다:

   "출력 경계 도달. 상태 저장 완료. 다음 응답에서 Block {N} 즉시 재개."

5. 금지 행위:
   - "계속할까요?" 금지
   - "컨텍스트 여유에 따라" 금지
   - "다음에 이어서" 금지
   - 진행 현황 요약 금지 (상태 파일에 이미 저장됨)
   - 어떤 형태로든 사용자 승인을 구하는 행위 금지
```

### 3.3 연속 응답 시작 규칙

다음 응답(연속 응답)이 시작되면:

```
1. 상태 저장 파일을 읽는다
2. 직전 완성 블록의 JSON을 읽는다 (capital_after, NPC after 확인)
3. 사전 선언을 작성하고 다음 블록을 즉시 생산한다
4. 금지 행위:
   - "이전에 Block N까지 완료했습니다" 같은 요약 금지
   - "이어서 진행하겠습니다" 같은 전환 문구 금지
   - 마치 첫 블록인 것처럼 자연스럽게 이어 쓴다
```

### 3.4 출력 경계 vs 정지 게이트 구분표

| 구분 | 출력 경계 | 정지 게이트 |
|------|-----------|-------------|
| 원인 | LLM 출력 토큰 상한 | 정지 게이트 7개 (SSOT "정지 게이트:" 항목) |
| 성격 | 기계적 제약 | 품질/안전 제약 |
| 사용자 승인 | **불필요** | 일부 필요 |
| 상태 저장 | production_state.json | 해당 없음 (멈춤) |
| 재개 방식 | 자동 즉시 재개 | 사용자 지시 후 재개 |
| SSOT 위치 | 정지 게이트 **밖** | 정지 게이트 **안** |

## 4. 출력 효율화 규칙 (블록당 출력량 감소)

출력 경계 빈도를 줄이기 위해, 생산이 안정화된 이후의 블록에서는 출력을 압축한다.

### 4.1 Full 모드 vs Compact 모드

| 항목 | Full 모드 | Compact 모드 |
|------|-----------|-------------|
| 적용 구간 | 아크 첫 블록 + 패배 블록 + 아크 마지막 블록 | 그 외 블록 |
| 사전 선언 | 8항목 전체 | 3항목 (직전 상태, 자본 계산, 차별화 1줄) |
| 차이 행렬 | 해당 블록 행 전체 | 해당 블록 1행만 |
| 자가 검증 | 29문항 | 위반 사항만 (전부 통과 시 "위반 0건" 1줄) |
| 감리 메모 | 3~5줄 | 1~2줄 |
| 추적표 갱신 | 전체 NPC 테이블 | 변경된 NPC만 |
| 복선 원장 | 전체 | 변경분만 (추가/회수/상태변경) |
| 자본 곡선 | 전체 ASCII | 해당 블록 1줄만 |

**Full 모드 블록 예상 크기:** ~4,800자 (~3,200 토큰, 한국어 ~1.5자/토큰)
**Compact 모드 블록 예상 크기:** ~2,500자 (~1,700 토큰, 한국어 ~1.5자/토큰)

### 4.2 아크 종합 검증은 파일로 분리

ARC-01 종합 차이 행렬, NPC 추적표, 복선 원장, 자본 곡선, 적대자 상태 등의 **대단원 종료 보조 출력**(harness §3.5)은:

- 인라인 출력 대신 파일로 저장한다
- 파일명: `treatments/{work_id}_arc{N}_summary.json`
- 인라인에는 "ARC-{N} 종합 검증 파일 저장 완료. 위반 0건." 1줄만 출력

이렇게 하면 아크 경계에서의 출력 폭증을 방지한다.

### 4.3 모델별 예상 블록 수/응답

| 모델 | 예상 출력 상한 | Full 블록 | Compact 블록 | 혼합 (권장) |
|------|---------------|-----------|-------------|-------------|
| Gemini Flash | ~8K 토큰 | ~2블록 | ~4블록 | ~3블록 |
| Gemini Pro | ~16K 토큰 | ~5블록 | ~9블록 | ~7블록 |
| Claude Sonnet | ~16K 토큰 | ~5블록 | ~9블록 | ~7블록 |
| Claude Opus | ~32K 토큰 | ~10블록 | ~18블록 | ~14블록 |

따라서:
- Gemini Flash: 약 23회 출력 경계 → 23회 자동 재개
- Claude Opus: 약 5회 출력 경계 → 5회 자동 재개
- **어느 모델이든 사용자 개입 0회** (출력 경계 프로토콜이 있으면)

## 7. 예상 반론 및 대응

### Q1: "사용자가 중간에 방향을 바꾸고 싶을 수 있지 않나?"

→ 사용자의 방향 수정은 **정지 게이트 8번**(사용자 명시 정지)에 이미 포함되어 있다.
사용자가 중간에 개입하면 그것이 정지 게이트가 된다.
출력 경계 프로토콜은 "사용자가 개입하지 않는 한 멈추지 않는다"는 기존 원칙을 그대로 따른다.

### Q2: "상태 파일이 오염되면?"

→ 상태 파일은 직전 블록 JSON에서 재구성 가능하다.
상태 파일이 없거나 파싱 불가 시, 직전 블록 candidate JSON을 읽어 상태를 재구성한다.
이것은 **fallback**이지 정지 게이트가 아니다.

### Q3: "Compact 모드에서 품질이 떨어지지 않나?"

→ Compact 모드는 **출력량**만 줄이고, **생성 품질**은 동일하다.
JSON 블록 자체의 밀도(context, event_villain, solution, reward, stakes)는 Full이든 Compact이든 동일한 기준(350자+ 평균)이 적용된다.
줄어드는 것은 사전 선언/차이 행렬/감리 메모의 **인라인 출력량**이지, 블록 내용이 아니다.

### Q4: "CLI 환경이 아닌 채팅 환경에서는?"

→ 채팅 환경에서는 LLM이 연속 응답을 자동으로 보낼 수 없을 수 있다.
이 경우, 출력 경계 도달 시 상태 파일을 저장하고, 사용자가 아무 입력(빈 엔터, "ㅇ", 등)을 보내면 즉시 재개한다.
**핵심: "계속할까요?"를 묻지 않는다. 상태 저장 후 대기할 뿐이다.**

### Q5: "70블록 전체를 하나의 턴으로 보면 너무 길지 않나?"

→ 맞다. 현실적으로 70블록은 여러 응답에 걸쳐 생산된다.
그러나 **사용자 관점에서** 이것은 하나의 지시("방산물 진행")에 대한 하나의 작업이다.
출력 경계에서의 분할은 **기계적**이지 **의미적**이지 않다.

## 부록: 이 문서를 읽는 LLM을 위한 요약

당신이 Treatment 블록을 생산하다가 출력이 길어지면:

1. **멈춰도 된다** — 출력 한계는 물리적 제약이다
2. **질문하면 안 된다** — "계속할까요?"는 auto-run 위반이다
3. **상태를 저장하라** — `{work_id}_production_state.json`
4. **다음 응답에서 이어 써라** — 상태 파일 읽고 즉시 재개
5. **페이지 넘김이지 책 덮기가 아니다**
